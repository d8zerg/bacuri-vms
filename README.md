# Bacuri VMS 

Open-Source VMS Platform

Bacuri VMS Basic - первая поставка для одной локальной площадки. В репозитории уже есть управление, обнаружение камер ONVIF, приём RTSP, запись, медиавыдача и тревоги. В плане выпуска предусмотрены PTZ и события оборудования, единое рабочее место с планом объекта, обработка тревог, управление сроком хранения, проверяемый экспорт и автономное обслуживание узла.

До шага 8.3 включительно сценарии выполняют автоматические тесты. Только после успешной квалификации подписанного комплекта администраторы и операторы проходят финальные задания на том же комплекте в 9.1. [План разработки](docs/devplan-basic.md#6-контрольные-точки-и-последовательность) · [Критерии качества](docs/basic-quality.md) · [Паспорт испытаний](docs/basic-test-profile.md)

Для всех компонентов, средств сборки, тестов и поставки действует единая политика поддерживаемых технологий. Выбранные технологии и источники точных версий перечислены в архитектуре. [Стек платформы](docs/architecture.md#3-топологии-и-базовый-стек) · [Правила выбора и обновления](docs/adr/015-technology-lifecycle.md)

## Локальный стенд

Требуются Linux x86-64, нативный Docker Engine, плагин Docker Compose и Go Task. [Установка Go Task](https://taskfile.dev/docs/installation/)

```sh
task check
```

Команда собирает оптимизированные службы, проверяет Debug-сборки GCC и Clang, выполняет CTest с ASan/UBSan и TSan, запускает статический анализ и проверяет контракты и типы TypeScript. Затем она запускает Compose-стенд, применяет схемы хранилищ и проверяет запись, эфир, архив и тревоги. CMake и Ninja работают в контейнере без сети. Результаты сохраняются в `build/`.

Для полного прогона используйте рабочую копию с полной историей Git. В отчёте `task check:report` откройте `coverage/cpp/index.html`, `coverage/web/index.html` и `workspace/coverage/index.html`, чтобы увидеть непокрытые строки. В `secrets/` лежат отдельные результаты Gitleaks для истории, индекса и рабочих файлов. [Обязательные проверки кода](docs/basic-quality.md#автоматические-проверки-кода)

## Сборка и обновление зависимостей

При подготовке образа Conan 2 устанавливает Boost (заголовки), nlohmann/json и тестовый GoogleTest/GoogleMock. Рецепт задаёт версии, общий lockfile закрепляет ревизии рецептов. Профили фиксируют архитектуру, C++23, компилятор и ABI стандартной библиотеки. Release собирает службы, Debug включает тестовые цели. Два инструментированных пресета используют зависимости Clang Debug и применяют соответствующий санитайзер к сборке проекта. [Рецепт](conanfile.py) · [Lockfile](conan.lock) · [Пресеты CMake](CMakePresets.json)

GStreamer с загружаемыми плагинами, GLib, OpenSSL, libsodium, клиенты PostgreSQL и SQLite, gRPC, Protobuf и генераторы берутся из одного снимка Debian. Клиент Conan закреплён версией и SHA-256, базовые Docker-образы - digest. Сеть нужна при подготовке образа. Компиляция использует установленные в образе пакеты и сгенерированные Conan конфигурации CMake. При смене инструментария или переходе со старой сборки `task build` заново конфигурирует выбранный пресет. При повторном запуске с теми же зависимостями Ninja использует ранее собранные объекты. [Dockerfile](Dockerfile) · [ADR-010. Зависимости сборки](docs/adr/010-build-dependencies.md)

При обновлении библиотеки изменить рецепт и выполнить `task deps:lock`. Проверить изменения прямых и транзитивных зависимостей в lockfile, затем запустить `task check:report` и `task build:repro`. На Release-файлах общий прогон также проверяет путь от наблюдения до воспроизводимого кадра тревоги в Chrome и Firefox. После успешного прогона отчёт в `build/reports/check-*/` содержит версии инструментов, перечень пакетов Debian, граф Conan с идентификаторами фактических пакетов для каждого профиля и SHA-256 четырёх Release-файлов.

### Регрессионная проверка ядра

`task regression:check` копирует исходники и историю Git в новый каталог, использует отдельный проект Compose с пустыми томами, выполняет `task check:report`, проверку сохранности хранилища и независимую Release-сборку. В `build/reports/regression-*/` сохраняются ревизия, хеш состава исходников, материалы сценариев, результаты восстановления и коды завершения. Для рабочей копии с изменениями сохраняется также её точное содержимое. Аппаратный прогон на выделенной IP-камере имеет собственный протокол.

`task deps:check` сверяет установленные деревья npm и графы Conan с lock-файлами, проверяет версии сред исполнения и сканирует образы продукта, сборки и тестов. Для подготовки нужны закреплённые образы и базы Trivy. Для временных образов и баз используйте дисковую файловую систему каталога сборки. Само сканирование выполняется без сети. Для автономного повтора решения по сохранённому снимку используется команда

```sh
python3 tools/lifecycle/policy.py "$report/snapshot" "$report/replay.json"
```

Здесь `report` - каталог проверки зависимостей. В `blocking.json` перечислены причины отказа и затронутые версии. Для нового сканирования с сохранёнными базами и уже загруженными образами выполнить `python3 tools/lifecycle/scan.py --offline-from "$report/snapshot"`. При новом сканировании действует текущий срок актуальности сведений. Входы и их SHA-256 перечислены в `snapshot/inputs.json`. Для обновления сведений о сопровождении выполнить `task deps:refresh`. Команда получает ревизии обеих официальных баз и сведения о сопровождении. После проверки изменений повторить серию. [Состав доказательств](docs/basic-test-profile.md#регрессия-ядра)

`task stand:check-postgres-upgrade` создаёт отдельный том со схемой Basic, архивным каталогом и ожидающей тревогой в PostgreSQL 17.11. На физической копии с PostgreSQL 17.12 пересобирает индексы схем приложения, запускает pg_amcheck и сравнивает результаты запросов. Затем создаёт новую полную копию, проверяет её pg_verifybackup, запускает восстановленный сервер и повторяет сравнение. [Указания к обновлению PostgreSQL](https://www.postgresql.org/docs/release/17.12/)

### Сопровождение системных пакетов

`task packages:build` выгружает Debian-пакеты, исходные архивы и патчи, файлы `.buildinfo`, контрольные суммы, Gitleaks и gosu в отдельный каталог отчёта. Контейнеры сборки, записи и PostgreSQL используют те же стадии Dockerfile. Локальные ревизии libxml2 и libsoup сохраняют ABI ветки Debian 13. Исправление libxml2 взято из стабильной ветки Ubuntu на той же исходной версии библиотеки. Для libsoup применяются два исправления GNOME. [Уведомление Ubuntu](https://ubuntu.com/security/CVE-2026-6653) · [Исправление обработки содержимого](https://gitlab.gnome.org/GNOME/libsoup/-/commit/b91bbd7d7888c85b17a8b33173caa806dff51681) · [Исправление сжатия](https://gitlab.gnome.org/GNOME/libsoup/-/commit/dbd0417ea3a569135e9a9344b7812076b7b178f1)

Для веб-сервера каталога UI Kit и прототипа используется один образ с подписанным исправлением Brotli из стабильной ветки Alpine. Гейт сопоставляет каждый сервис Compose с проверяемым образом или идентичной конфигурацией его сборки. Для Gitleaks и gosu проверяются хеш установленной утилиты и версия Go из метаданных сборки.

При обновлении проверить версию в подписанном архиве Debian. Если исправление уже входит в пакет поставщика, вернуть его в образы и удалить локальное правило. Для нового переноса закрепить версию и контрольную сумму источника в Dockerfile, обновить список исправлений и версий в `packaging/maintenance/policy.json`, выполнить `task packages:build`, затем `task regression:check`. При несовпадении патча, байтов библиотеки или исходной версии гейт блокирует комплект. [ADR-016](docs/adr/016-system-backports.md)

## RTSP-эмулятор с веб-камерой

`task webcam:up` открывает `/dev/video0` через V4L2. Один захват питает два H.264-кодера. По умолчанию на хосте доступны `rtsp://127.0.0.1:8555/main` и `rtsp://127.0.0.1:8555/sub`. При регистрации в ядре используйте `rtsp://webcam:8554/main` и `rtsp://webcam:8554/sub`. Эмулятор работает в отдельном профиле Compose и может работать одновременно с синтетической камерой.

Устройство выбирается переменной окружения `BACURI_WEBCAM_DEVICE`, порт хоста - `BACURI_WEBCAM_PORT`. Например, `BACURI_WEBCAM_DEVICE=/dev/video2 task webcam:up`. Контейнер получает доступ к выбранному устройству и его группе. `task webcam:check` проверяет оба профиля, останавливает чтение очереди просмотра и прерывает тестовые TCP-соединения. После работы выполните `task webcam:down`, чтобы освободить камеру. Для автоматического прогона на машине без камеры используется `task ingest:check`.

После применения конфигурации процесс записи открывает оба профиля. Команда `docker compose logs -f recorder` показывает события `rtsp_ingest` с идентификатором точки, профилем, разрешением, числом кадров и переподключений. Поля `gap_begin_us` и `gap_end_us` задают границы потери по шкале приёма UTC. У открытого пропуска конец равен `null`. Для каждого подключённого потребителя поле `queues` содержит текущую и пиковую глубину, байты и число сброшенных кадров. [Матрица совместимости и правила приёма](docs/rtsp-compatibility.md)

## Сервер управления

`task control:up` запускает API на `https://localhost:8443/api/v1`. Порт задаётся через `BACURI_HTTPS_PORT`, разрешённые сети камер - через список CIDR в `BACURI_CAMERA_NETWORKS`. HTTPS использует Boost.Asio, Boost.Beast и OpenSSL. Мастер «Камеры» получает адреса профилей через ONVIF или принимает адреса вручную. Для открытых потоков синтетического стенда требуется явное исключение по IP. Настройки доверия, исключений и подключения к сегменту описаны в инструкции. [Подключение камер](docs/rtsp-compatibility.md#мастер-подключения)

При первом запуске стенд создаёт локальный сертификат и отдельные ключи шифрования ядра и узла записи. Публичный сертификат можно получить командой `docker compose exec -T core cat /identity/tls.crt` и использовать для проверки TLS. Том каждого ключа требуется сохранять вместе с соответствующей базой. Процессы работают под разными UID и передают снимки конфигурации через gRPC по Unix-сокету. Узел восстанавливает последнюю применённую версию из зашифрованного снимка в SQLite.

Для создания учётной записи используйте `task control:create-user USERNAME=admin ROLE=administrator`, передав пароль одной строкой через stdin. Перед первым входом администратора выполните `task control:enroll-admin USERNAME=admin` в локальной консоли. Откройте `/cameras` по доверенному HTTPS, введите пароль и код, затем подтвердите регистрацию и вход ключом WebAuthn. Для оператора укажите `ROLE=operator` и выдайте доступ к зарегистрированной точке командой `task control:grant-point USERNAME=operator POINT=<UUID>`. Для входа браузер отправляет JSON в `POST /api/v1/session` с текущим HTTPS Origin. Запись конфигурации использует сессионную cookie и CSRF-токен. [Контракты и модель доступа](docs/adr/001-api-contracts.md)

## Рабочее место администратора и оператора

После `task control:up` откройте [рабочее место Bacuri VMS](https://localhost:8443/). Администратору доступен раздел «Камеры». Введите имя и адреса основного и дополнительного потоков. После применения конфигурации клиент проверит свежий блок записи и кадр дополнительного потока. Выберите «Создать тестовую запись», откройте новый фрагмент и подтвердите результат после появления кадра.

В «Мониторинге» оператор выбирает разрешённую точку, смотрит эфир и открывает запись из карточки тревоги. «К выбранной тревоге» возвращает фокус в ленту. Адрес страницы сохраняет площадку, точку и контекст просмотра. Для тестового источника адреса внутри Compose - `rtsp://rtsp-camera:8554/main` и `rtsp://rtsp-camera:8554/sub`. Учётные записи и права выдаются командами из раздела «Сервер управления».

## Запись архива

После `task control:up` зарегистрируйте камеру через реестр. Узел записи сохраняет основной H.264-поток без перекодирования в именованном томе `archive-data`. Каждый каталог `/archive/recorder/blocks/<UUID>` содержит самостоятельный фрагментированный MP4 с индексом и `manifest.json`. Манифест связывает файл с точкой, каналом, версией привязки и полуоткрытым интервалом UTC. [Формат и порядок фиксации](docs/basic-domain-model.md#запись-и-сверка-на-томе)

`task archive:status` читает журнал работающего узла. Поле `committed` показывает число локально зафиксированных блоков, `pending` - число неподтверждённых изменений каталога, `missing`, `corrupt` и `rejected` - число отсутствующих каталогов блоков, повреждений и отказов регистрации. `last_commit_utc_us` содержит время последней локальной фиксации. Узел продолжает запись по сохранённой конфигурации при недоступности ядра или PostgreSQL.

`task archive:check` проверяет запись и декодирование с синтетической камеры, исключительное владение томом, восстановление после остановки процесса и возврата базы, повторную регистрацию, конфликт манифеста, пропажу и повреждение медиа. Сценарий использует временную базу и отдельный каталог тома.

## Поиск и воспроизведение архива

После `task control:up` откройте `https://localhost:8443/archive/`, войдите в локальную учётную запись, выберите площадку, точку и границы UTC. Поиск показывает запись, подтверждённый пропуск с причиной, ожидающий регистрации блок и интервал с неизвестным покрытием. Кнопка «Воспроизвести» открывает запись, поле «Позиция (UTC)» позволяет перейти к кадру. Для поиска и открытия доступны интервалы до одного часа. Один браузер может открыть до 16 медиасеансов одновременно.

В манифест входят целые блоки H.264, начиная с ключевого кадра. При выборе позиции внутри блока плеер загружает его и перематывает до нужного кадра. Если интервал начинается или заканчивается внутри блока, для просмотра этого блока расширьте запрос до его границ. Сеанс истекает через пять минут или раньше при завершении браузерного сеанса.

`bacuri-vms-media` читает архив с тома, подключённого только для чтения. Ядро проверяет права по PostgreSQL и передаёт фрагменты через тот же HTTPS-источник. `task playback:check` запускает изолированную базу и браузеры в Compose, выводит задержку до отображения первого кадра и ошибку позиционирования. Эталон состоит из цветных кадров с известным временем, смены разрешения и секундного разрыва. [Формат сегментов MSE](https://www.w3.org/TR/mse-byte-stream-format-isobmff/)

## Тревоги и переход к записи

После `task control:up` откройте [ленту тревог](https://localhost:8443/alerts/). Оператор видит последние 100 тревог по своим точкам. Список обновляется по WSS. Ссылка «Открыть запись» ставит архивный плеер на кадр события. Если блок ещё регистрируется, кнопка «Проверить запись ещё раз» повторно проверяет тот же интервал.

Локальный тестовый источник создаёт наблюдение `motion` для уже настроенной точки и версии привязки. Подставьте UUID точки вместо `POINT_UUID` и действующую версию вместо `1`. Сохраните сообщение для повторной отправки.

```sh
task observation:sample POINT=POINT_UUID REVISION=1 > motion.json
task observation:submit < motion.json
task observation:submit < motion.json
```

Первый ответ - `REGISTRATION_STATE_COMMITTED`, повторный - `REGISTRATION_STATE_REPLAYED`. Эмулятор и ядро используют часы одного Linux-хоста. Для проверки записи дождитесь публикации архивного блока. Полный сценарий с изолированной базой, отказами и двумя браузерами запускает `task alerts:check`.

## Прямой эфир

После `task control:up` откройте [прямой эфир](https://localhost:8443/live/), войдите, выберите площадку и точку наблюдения, нажмите «Смотреть». Оператору требуется право на точку. Кнопка «Остановить» закрывает медиасеанс. После обрыва связи нажмите «Смотреть» для нового подключения.

Ядро согласует WebRTC через HTTPS. Процесс `bacuri-vms-media` получает дополнительный H.264-поток от узла записи через Unix-сокет и отправляет его браузеру по DTLS-SRTP без перекодирования. На Linux-хосте браузеру нужен прямой UDP-маршрут до адреса контейнера в сети `live-media`. Профиль стенда использует локальные ICE-кандидаты. Для просмотра требуется поддержка WebRTC H.264. Тестовый образ Firefox содержит OpenH264 с проверкой контрольной суммы.

`task live:check` выводит задержку до первого декодированного кадра, число и длительность пропусков архива и время до последнего видеопакета при отзыве и истечении доступа. По умолчанию используется синтетическая RTSP-камера. Для проверки с веб-камерой выполните `task webcam:up`, затем `task live:check CAMERA=webcam`. После проверки `task webcam:down` освобождает устройство.

## Прототип интерфейса

Команда `task prototype:up` запускает прототип на [http://127.0.0.1:8088](http://127.0.0.1:8088). Для остановки используйте `task prototype:down`. Порт можно задать через `BACURI_PROTOTYPE_PORT`.

Проверки `task docs:check` и `task prototype:check` входят в `task check`. При `task check:report` снимки и материалы браузерных ошибок сохраняются в каталоге `prototype/artifacts` отчёта. Отдельный запуск `task prototype:check` печатает путь к своему отчёту.

Прототип использует тестовое видео и смоделированные состояния связи, записи и тревог. [Сценарии и протокол проверки](docs/basic-ui.md)
