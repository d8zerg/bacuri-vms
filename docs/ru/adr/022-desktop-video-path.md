# ADR-022. Путь видео и карты настольного клиента

[English version](../../adr/022-desktop-video-path.md)

**Статус** - Принято для Linux. Windows и macOS решаются на своих стендах.

**Контекст.** Настольный клиент показывает эфир и архив до 16 камер на одном экране рядом с картой. Кадр должен попадать на экран без копирования через системную память, интерфейс должен оставаться отзывчивым под нагрузкой, а пост должен продолжать работу при отказе GPU или его декодера. Qt Quick умеет рисовать через разные графические API, GStreamer даёт аппаратные и программные декодеры, MapLibre Native for Qt даёт модуль Qt Location и библиотеку ядра.

**Варианты.**

| Вариант | Оценка |
| --- | --- |
| Декодирование в системную память и загрузка каждого кадра | Работает везде, но даёт одно копирование на кадр и 4-6 ядер CPU на 16 камер 1080p |
| Аппаратное декодирование в память OpenGL и `qml6glsink` | Ноль копирований через системную память, 2,4 ядра CPU на 16 камер. Требует графический API OpenGL у Qt Quick |
| Собственный узел RHI с импортом поверхностей декодера | Работает с любым графическим API, но требует импорта памяти декодера для каждой платформы до первого полезного экрана |
| Карта через модуль Qt Location из MapLibre | Требует закрытых заголовков Qt Location, которых нет в Debian, исходники модуля под LGPL или GPL |
| Карта через ядро MapLibre и собственный элемент Qt Quick | BSD-2-Clause, без зависимости от Qt Location, карта рисуется в буфер кадра OpenGL той же сцены |

**Решение.** На Linux клиент использует Qt Quick на OpenGL. Каждая ячейка декодирует через NVDEC, когда он доступен, и передаёт кадр в памяти OpenGL в `qml6glsink`. Карту рисует собственный элемент `QQuickFramebufferObject` поверх ядра MapLibre Native for Qt, собранного из закреплённого выпуска без интеграции с Qt Location.

| Ситуация | Поведение |
| --- | --- |
| Аппаратный декодер доступен | NVDEC, кадры остаются в памяти GPU |
| Аппаратного декодера нет при запуске | Программный декодер, одна загрузка на кадр |
| Аппаратный декодер отказал во время воспроизведения | Ячейка пересобирает конвейер с программным декодером и продолжает с последнего показанного кадра. Окно, раскладка и остальные ячейки продолжают работу |
| GPU отсутствует | Программный декодер и программный OpenGL через Mesa. Пост работает с меньшей плотностью |
| Графическое устройство потеряно во время отрисовки | Клиент перезапускается в режиме программной отрисовки и восстанавливает пост: раскладки, тревоги, позицию архива и фокус |

Поддерживаемая плотность указывается для каждого стенда по измеренным прогонам: на эталонном стенде 16 камер 1080p 25 к/с занимают 2,4 ядра CPU с NVDEC, сцена рисуется не дольше 4,3 мс по p99, карта добавляет 0,2 мс на кадр.

**Обоснование и последствия.** Путь через OpenGL уже сейчас даёт ноль копирований на эталонном стенде, а собственный узел RHI отложил бы первый рабочий экран из-за импорта поверхностей для каждой платформы. Решение привязывает клиент к графическому API OpenGL у Qt Quick на Linux. Для Windows и macOS нужно отдельное решение: в GStreamer есть приёмники Direct3D 11 и Metal, элемент карты должен следовать выбранному API. Сейчас у каждой ячейки свой декодер, поэтому запуск 16 аппаратных ячеек и перемотка всех сразу медленнее, чем с программным декодированием. Для синхронного архива нужны общий контекст декодера и кэш опорных кадров. Элемент карты избавляет клиент от кода под LGPL и GPL. **Проверка.** `task desktop:video` прогоняет эталонные записи H.264 и H.265, живые камеры, карту рядом с 16 ячейками, отказ декодера во время воспроизведения и стенд без доступа к GPU. Каждый прогон проверяет первый кадр, кадр после перемотки или после отката, память на выходе декодера и отсутствие ошибок. `task desktop:passport` привязывает результаты к измеренному стенду.
