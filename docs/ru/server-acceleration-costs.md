# Стоимость серверных задач

[English version](../server-acceleration-costs.md)

Реестр определяет единицу работы, расход ресурсов и поведение при вытеснении для задач из [ADR-025](adr/025-server-acceleration.md). Строку измерений выбирают по входному кодеку, разрешению, операции и способу выполнения. [Измерения на CPU](../../tests/acceleration/cpu.csv) и [измерения на NVIDIA](../../tests/acceleration/nvidia.csv) охватывают H.264 Main и H.265 Main, 8 бит, 4:2:0, каждый в разрешениях 1920x1080 и 2560x1440 (2K) при 25 кадрах/с. Числа относятся к одному эталонному узлу.

Запись исходного потока камеры занимает ноль сессий декодера и кодера. Общий декодер или уже сформированный профиль учитывается один раз на фактический конвейер. Каждый отдельно кодируемый выход занимает свою сессию кодера. В RSS и видеопамять входят затраты процесса и драйвера. Для расчёта плотности измеряют прирост памяти при добавлении второй задачи в тот же процесс.

## Как читать измерения

Эталонный узел оснащён AMD Ryzen 9 3900X и GeForce RTX 4070 Ti с драйвером 595.99.02. В обоих режимах используется GStreamer 1.26.2. Каждая строка - один изолированный прогон операции на входном профиле, включая запуск процесса. Задания в очереди занимают ноль сессий декодера и кодера.

Эфир с одной маской при 25 кадрах/с

| Вход | Ядра CPU, программная обработка | Ядра CPU, обработка с NVIDIA | Видеопамять NVIDIA, МиБ |
| --- | ---: | ---: | ---: |
| H.264 Main 1920x1080 | 0,38 | 0,23 | 245 |
| H.265 Main 1920x1080 | 0,48 | 0,23 | 259 |
| H.264 Main 2560x1440 | 0,55 | 0,30 | 286 |
| H.265 Main 2560x1440 | 0,79 | 0,32 | 306 |

| Поле | Единица измерения и смысл |
| --- | --- |
| `cpu_cores_at_25fps`, `peak_rss_mib` | Пользовательское и системное процессорное время, делённое на шесть секунд исходного видео, и пик резидентной памяти процесса в МиБ. Учитывается также работа CPU при использовании NVIDIA. |
| `dec_sessions`, `enc_sessions`, `sampled_vram_mib` | Число сессий, требуемых аппаратными элементами декодирования и кодирования в конвейере, и наибольшее показание видеопамяти процесса в МиБ. Лимиты устройства измеряет отдельная проверка узла. Между отсчётами возможен более высокий кратковременный пик. |
| `dec_ms_per_input_frame`, `enc_ms_per_input_frame`, `sm_ms_per_input_frame` | Оценка времени занятости декодера, кодера и вычислительных блоков GPU по отдельности. При 25 кадрах/с каждый средний процент загрузки умножается на 0,4 мс. Блоки могут работать одновременно. При значении ниже разрешения счётчика отображается ноль. Пустое поле означает, что драйвер не выдал показание. |
| `input_frames`, `output_frames`, `motion_samples`, `wall_s`, `gpu_samples` | Число входных и проверенных выходных кадров, отсчёты движения, длительность прогона и число действительных замеров GPU. Для редких выходных кадров время на входной кадр умножают на `input_frames / output_frames`, чтобы получить стоимость одного изображения. |

Например, эфир с маской занимает на NVIDIA одну сессию декодера и одну сессию кодера. Для минуты экспорта с маской при 25 кадрах/с берут строку `export-mask` для данного профиля и применяют её к 1500 кадрам, обе сессии заняты одновременно. При переходе к произвольному кадру учитывают все кадры, которые придётся декодировать от предшествующей точки произвольного доступа. Файловый ввод-вывод, упаковку в контейнер, звук, транспорт и подпись доказательств учитывают отдельно. Прогон измеряет обработку при подаче 25 кадров/с. Предельную скорость экспорта, задержку холодного поиска и плотность параллельных задач измеряют отдельными прогонами.

Для модели число вызовов в секунду умножают на измеренные секунды CPU или миллисекунды соответствующего блока GPU на вызов. Добавляют пиковую рабочую память каждого параллельного вызова и память весов один раз на загруженный экземпляр модели. Фиксируют хеш модели, размер входного тензора, размер пакета, частоту выборки, устройство, точность и бэкенд. На одних и тех же выбранных кадрах сравнивают обработку с выключенным и включённым выводом. Стоимость модели сохраняют отдельно для CPU, CUDA и OpenVINO. До измерения дополнительная стоимость модели неизвестна, выделять ей бюджет этого бэкенда нельзя.

## Как воспроизвести

```sh
task acceleration:cost BACKEND=cpu
task acceleration:cost BACKEND=nvidia
```

Команды выполняют по очереди на свободном узле. Команда для CPU работает и на узле без GPU. Для NVIDIA используется устройство 0 с аппаратными видеокодеками, вычислениями и счётчиками загрузки по процессам. Каждая команда проверяет четыре сгенерированные записи fMP4 профиля Main (150 кадров, GOP 25, без B-кадров), запускает каждую операцию в отдельном процессе и сохраняет полный отчёт в `build/acceleration/<backend>.csv`. Генерация исходных записей вынесена за пределы измерения.

Источник - тестовые полосы SMPTE. Целевой битрейт при подготовке записи составляет 6 Мбит/с, для эфира H.264 - 2 Мбит/с. Для экспорта задан фиксированный параметр квантования 16. Маска закрывает центральную четверть площади кадра. Полночастотные конвейеры должны выдать 150 кадров, извлечение опорных кадров и миниатюр - по шесть изображений, анализ движения - 150 кадров и 22 отсчёта с серверным интервалом выборки 250 мс. На NVIDIA работают NVDEC и, для перекодируемых выходов, NVENC. При перекодировании без маски в исходном размере поверхности передаются через память CUDA. Маска, изменение размера и расчёт движения в этом прогоне выполняются на CPU. Счётчики NVIDIA для процесса снимаются с интервалом одна секунда. Перед назначением бюджета узла измерения повторяют на его драйвере, записях и целевых операциях.

## Фоновая проверка узла

При запуске медиасервис ставит проверку в очередь. Каждая проба выполняется отдельно в процессе с низким приоритетом и ограничением в 12 секунд. Сеанс эфира или чтение архива прерывает текущую пробу. Проверка ждёт освобождения узла и повторяет её. Регистратор продолжает запись. Видеопробы NVIDIA также ждут, пока драйвер сообщает об открытых сессиях кодирования или занятости декодера. На загруженном узле состояние `waiting` может сохраняться длительное время.

Администратору площадки доступны следующие операции по базовому адресу `/api/v1/sites/{siteId}/nodes/{nodeId}/acceleration/probe`. Для операций записи используется CSRF-токен сессии.

| Запрос | Результат |
| --- | --- |
| `GET` | Идентификатор, причина и состояние проверки, число завершённых и общее число проб по этапам, последний сохранённый результат и признак `stale`. |
| `POST` | Поставить проверку в очередь или получить уже идущую. При подготовке к выходу из режима «Только CPU» передать необязательное тело `{"reason":"prepare_gpu"}`. |
| `DELETE /{probeId}` | Отменить указанную проверку. Прежние измерения и текущий режим остаются доступны. |

Этапы проверки охватывают инвентаризацию, декодирование, кодирование, вывод и прикладные операции. Для каждого поддерживаемого видеобэкенда используется синтетический поток H.264 Main или H.265 Main, 1920x1080 при 25 к/с. На 16 входных кадрах проверяются маскирование, уменьшение до 720p, экспорт с маской и анализ движения для эфира и архива. Для извлечения опорного кадра и миниатюры используется кадр произвольного доступа. Результат содержит имена элементов кодеков, время в микросекундах, число кадров и измеренную скорость. Бюджет одного потока при 25 к/с равен 0 или 1. Время пробы включает запуск конвейера. Для кодирования и декодирования используется медиана трёх независимых запусков. Все три измерения доступны в `elapsed_samples_us`. Для CPU, CUDA и каждой доступной цели OpenVINO выполняются 32 прогона ReLU по 256 значениям FP32 с проверкой каждого результата. Стоимость прикладных моделей измеряется отдельно по методике выше.

Проверка удерживает одновременно до 16 аппаратных сессий кодирования для каждого кодека. Поле `verified_sessions` показывает, сколько сессий реально работали одновременно. При `reached_ceiling: true` это нижняя граница. На эталонной RTX 4070 Ti оба прогона подтвердили 12 сессий H.264 и 12 сессий H.265 при раздельной проверке кодеков. При общей видеопамяти или отсутствии показания драйвера узел возвращает `memory_bytes: null`. Неподдерживаемые операции, ошибки и превышения времени обозначаются отдельными состояниями. После завершения этапов и успешных обязательных проб CPU медиасервис атомарно сохраняет модель устройства, драйвер, отпечаток оборудования, результаты и время измерения UTC. Узел сверяет признаки оборудования и драйвера каждые 15 секунд и запускает новую проверку при изменении. В это время прежний результат доступен с `stale: true`.

Приёмочный прогон выполняется дважды на свободном узле. Должны совпасть подтверждённое число аппаратных сессий и бюджет одного потока декодирования и кодирования. Измеренная скорость может отличаться. Конфигурации «Только CPU» достаточно штатных кодеков. Для NVIDIA используются NVIDIA Container Toolkit и дополнительный файл Compose для NVIDIA. Для VA-API медиасервису, рекордеру и ядру нужен доступ к устройству рендеринга и соответствующий драйвер. Оба дополнительных файла Compose открывают выбранное оборудование этим трём сервисам. Дополнительный файл Compose для VA-API подключает окружение с драйверами Mesa и Intel. В нём задаются устройство рендеринга и числовой идентификатор его группы на хосте. OpenVINO подключается по наличию. Медиасервис загружает `libopenvino_c.so` или установленную библиотеку, указанную в `BACURI_OPENVINO_LIBRARY`.

```sh
task acceleration:check BACKEND=cpu
task acceleration:check BACKEND=nvidia
BACURI_RENDER_DEVICE=/dev/dri/renderD128 BACURI_RENDER_GID=$(stat -c %g /dev/dri/renderD128) task acceleration:check BACKEND=vaapi
task live:check
```

## Настройка ускорения узла

Новый узел площадки получает режим «Только CPU» (`cpu_only`) и ревизию 0. Площадка хранит режим и ручной выбор задач в PostgreSQL. Участники площадки могут читать настройку, администратор может проверить и применить выбор. Базовый адрес запросов - `/api/v1/sites/{siteId}/nodes/{nodeId}/acceleration`.

| Запрос | Действие |
| --- | --- |
| `GET` | Прочитать сохранённый режим, ручной выбор, ревизию и ожидаемое назначение каждой задачи с причиной. Заголовок `ETag` содержит ревизию настройки в кавычках. |
| `POST /preview` | Проверить предложенный выбор. Ответ содержит назначения, резерв на устройствах и список отклонённых задач `rejected_tasks`. Сохранённая ревизия доступна для следующих правок. |
| `PUT` | Повторно проверить выбор на текущем оборудовании и сохранить, если хватает бюджета. В `If-Match` передаётся полученный `ETag`. При параллельном изменении сервер возвращает HTTP 412. |

Например, для проверки ручного выбора масок эфира и экспорта передайте `{"mode":"manual","gpu_tasks":["live_mask","export"]}`. Если выбранный вид задачи не поддерживается или превышен бюджет, предпросмотр возвращает `applicable: false`. Попытка применения даёт HTTP 409 с кодом `acceleration_budget_exceeded` и списком отклонённых задач. Для режима «Авто» передайте только `{"mode":"auto"}`. Назначения вычисляет сервер. Возврат в «Только CPU» доступен и при отключённом медиасервисе. Изменение и запись аудита сохраняются одной транзакцией. В журнале площадки видны узел, инициатор, ревизия, прежние и новые значения режима и списка задач.

Для режима с GPU нужен завершённый замер на текущем устройстве и драйвере. Если замера нет, оборудование изменилось или обнаружен только CPU, сервер возвращает соответственно `acceleration_probe_required`, `acceleration_probe_stale` или `acceleration_device_unavailable`. При выходе из «Только CPU» сервер запускает фоновую проверку или присоединяется к уже запущенной. Свежий завершённый замер позволяет сразу применить режим. Предпросмотр из «Только CPU» также запрашивает проверку, если актуального результата нет. Ход проверки доступен по `/probe`. После завершения можно повторить предпросмотр.

Расчёт бюджета учитывает по одной эталонной задаче каждого выбранного вида при 1080p. Полночастотные операции резервируют 25 кадров/с, опорные кадры и миниатюры - по одному изображению в секунду. Для каждого вида учитывается худший результат двух входных кодеков, скорость декодера, скорость выходного кодера H.264 при перекодировании и время всего конвейера. Миллион единиц времени в секунду соответствует полному бюджету устройства. Все выходы H.264 делят подтверждённый лимит сессий кодирования. Сумма резервов видеопамяти должна помещаться в выделенную память. Измерение включает память, уже занятую на устройстве во время пробы. При общей памяти, недоступном показании или старом замере без данных о памяти на устройстве размещается одна проверенная задача. Для анализа эфира и архива базовая обработка видео учитывается отдельно. Для конкретной модели аналитики и бюджета 2K нужны собственные измерения.

При нескольких GPU сервер проверяет варианты размещения между ними и для одного и того же набора задач выбирает вариант с наименьшим суммарным временем. В порядке приоритета идут маски и профили эфира, анализ эфира, экспорт, анализ архива, опорные кадры и миниатюры. Если задача не помещается, сервер показывает ожидаемое назначение на CPU с причиной `unsupported` или `budget_exceeded`. Назначения описывают бюджет настройки.

### Экран узла

Откройте «Узел» в меню площадки под учётной записью администратора. При выходе из «Только CPU» форма запускает фоновую проверку или присоединяется к уже работающей. Можно переключаться между разделами и вернуться, чтобы узнать состояние. Отмена останавливает выбранную проверку и сохраняет предыдущий замер и действующий режим. При отключённой анимации ход текущего этапа отображается текстом.

В режиме «Вручную» отметьте виды задач. Форма показывает измеренную стоимость, ожидаемое устройство, причины назначения и свободный бюджет каждого GPU. Снимите часть флажков, если набор не укладывается в бюджет. В режиме «Авто» назначения доступны для чтения. Столбец «Работающие задачи» показывает текущее число задач каждого вида по устройству и причине, в том числе пути через CPU и очередь. Если исполнитель ещё удерживает прежнее разрешение на GPU, строка показывает освобождаемое устройство. Для задач без активных назначений отображается «Нет активных задач». После устранения причины предупреждения нажмите «Проверить снова».

Нажмите «Применить изменения» для сохранения режима. При конкурентном изменении форма загружает новую ревизию, сохраняя черновик для проверки и повторного применения. Перейти на «Только CPU» можно и при недоступном медиасервисе.

## Планирование работающих задач

Медиасервис раз в секунду читает сохранённую политику через локальный сокет авторизации Core. Пока политика недоступна или стартовая проверка ещё не подтвердила оборудование, используется CPU. Каждый работающий экземпляр задачи занимает свою долю эталонного бюджета. При равном приоритете сохраняется порядок поступления. Задача остаётся на текущем GPU, пока укладывается в его бюджет. Для новой задачи планировщик предпочитает свободное устройство, затем размещение из предпросмотра в ручном режиме и далее устройство с меньшим измеренным временем обработки.

Исполнитель последовательно вызывает внутренний RPC `NodeAcceleration.ScheduleTask` с уникальным UUID запуска и видом задачи. Для запуска GPU-конвейера нужны идентификатор устройства и разрешение. Исполнитель обновляет его не реже раза в секунду и прекращает использование GPU в течение четырёх секунд от **начала** последнего успешного запроса с назначением GPU. Получив CPU или очередь, исполнитель закрывает конвейер и подтверждает освобождение разрешения сообщением `RELEASED`. До подтверждения или истечения срока ресурсы остаются зарезервированными. Фоновое задание без свободного CPU может указать `wait_for_gpu`. Для эфира всегда доступен CPU. После завершения конвейера исполнитель отправляет `FINISHED`. Подтверждение для прежнего разрешения не освобождает новое. Временные метки и контрольную точку сохраняет исполнитель.

| Сообщение исполнителя | Действие узла |
| --- | --- |
| `SESSION_LIMIT` | Уменьшает лимит кодирования до числа остальных зарезервированных сессий и перераспределяет их по приоритету. Новый эфир может получить сессию после её освобождения экспортом. Декодирование остаётся доступным. |
| `DEVICE_LOST`, `DRIVER_RESET`, `ENCODER_ERROR` | Приостанавливает выдачу ресурсов неисправного устройства, отзывает его разрешения и публикует предупреждение. Другие GPU продолжают работу. После освобождения разрешений отдельный процесс проверяет отказавшую операцию на входах H.264 и H.265. |
| Восстановление | Интервал между проверками составляет не менее 30 секунд. На свободном устройстве проверяется доступная ёмкость кодера. При работе на сниженном лимите проверяется одна дополнительная сессия. Внутри проверки операции проба со статусом `busy` повторяется до трёх секунд, пока обновляется показание загрузки после предыдущего кодека. Если проверка не прошла, ограничение сохраняется. |

Принудительный переход на CPU или в очередь вступает в силу при следующем опросе. После вытеснения задача проводит не менее 30 секунд вне GPU до повторного назначения. Если кодер не открылся из-за лимита сессий, попытку можно повторить после освобождения сессии менее приоритетной задачей. При перезапуске планировщик дожидается истечения прежних разрешений и повторно проверяет устройство. Запись исходного потока работает независимо.

Администратору площадки доступно поле `scheduler` в ответе `GET /acceleration/probe` узла. В нём видны число задач, резервы устройств, действующие предупреждения и последние 64 решения. Медиасервис также пишет структурированные события в журнал процесса. В Prometheus доступны `bacuri_acceleration_tasks`, `bacuri_acceleration_encoder_sessions`, `bacuri_acceleration_memory_bytes`, `bacuri_acceleration_time_ppm`, `bacuri_acceleration_device_warning` и `bacuri_acceleration_transitions_total`. Показатели устройства отражают резервы, включая отозванные разрешения до освобождения. Счётчики переходов сгруппированы по пути и причине. Раз в десять секунд отдельный процесс читает аппаратные счётчики. Для поддерживаемых устройством показателей публикуются фактически открытые сессии `bacuri_acceleration_observed_encoder_sessions`, занятая видеопамять `bacuri_acceleration_observed_memory_bytes` и доля времени работы движка `bacuri_acceleration_engine_busy_ratio`.

Команда `task acceleration:check BACKEND=nvidia` проверяет RPC исполнителя при полном измеренном бюджете эфира и сообщении о сбросе драйвера. На потребительском GPU NVIDIA с измеренным пределом сессий стенд также занимает физические сессии NVENC, проверяет отказ при следующем открытии и повторяет открытие кодера эфира после освобождения сессии экспортом. Стенд записывает последовательные секундные сегменты камеры и обрабатывает те же кадры с серверной маской на назначенном устройстве.

## Обработка видео в сервисах узла

Исполнитель открывает проверенный декодер H.264 или H.265 из разрешения и сверяет идентификатор физического устройства. В режиме CPU он явно выбирает программный декодер. После обработки кадра исполнитель сообщает устройство и идентификатор разрешения. На экране «Узел» появляется подтверждённый путь `running_device_id`. В журнале исполнителя сохраняются UUID задачи, её вид, устройство и видеобэкенд.

| Задача | Работа с устройством и восстановление |
| --- | --- |
| Маски и профили эфира | При смене кодеков медиасервис сохраняет соединение WebRTC и часы RTP. Он повторно декодирует сжатые кадры от сохранённого опорного кадра и пропускает уже переданные изображения до входа нового кодера. Первый новый кадр открывает следующую группу. Маска накладывается до кодирования. Совместимый поток без масок передаётся напрямую. |
| Экспорт выбранного интервала и совместимое архивное воспроизведение | Исполнитель берёт входной кодек из подписанного манифеста и пишет отдельный клип H.264 для каждого исходного блока. При прерывании он закрывает кодеки и заново формирует на CPU только незаконченный клип. Сохраняются предыдущие клипы, границы выборки и маски. При экспорте оригинала копируется проверенная запись. |
| Опорные кадры, миниатюры и анализ движения в архиве | Рекордер извлекает первый кадр блока и его время представления. Миниатюра на CPU может использовать этот декодированный кадр. Миниатюра на GPU использует назначенный декодер. При анализе всех кадров рекордер сверяет начало с опорным кадром, индексирует время представления и сохраняет изображения 64x48 для поиска. Каталог принимает индекс после проверки всего блока. |
| Живой анализ движения | При смене кодека рекордер сохраняет интервал выборки и предыдущее изображение детектора. Наблюдения движения и образцы архивного индекса содержат видеобэкенд (`cpu`, `nvidia` или `vaapi`). Подключение вывода моделей относится к [исполнителю моделей аналитики](../devplan-analytics.md#шаг-14-исполнитель-моделей). |

Функциональный стенд подаёт 96 пронумерованных кадров при 25 к/с, сверяет номера по пикселям и порядок показа, проверяет маску, 75 кадров выбранного интервала экспорта и повторяемость архивного индекса на одном бэкенде. В прогоне с GPU стенд переключает эфир на CPU внутри группы кадров и отзывает разрешение фоновой задачи во время обработки блока. Отдельный поток из 936 кадров превышает предел в 900 кадров для повторного декодирования. Стенд сверяет непрерывность выдачи и маску при переходе этого потока на CPU. Команда для CPU - `task acceleration:check BACKEND=cpu`. Для аппаратного прогона указывают установленный бэкенд. Плотность узла, скорость обработки 2K и длительная работа проверяются по [плану квалификации узла](../devplan-acceleration.md#шаг-31-плотность-отказы-и-долгая-работа).
