| Параметр | Профиль первого прогона |

## Автономная установка и доступ

`task install:check SUITE=bookworm` и `task install:check SUITE=trixie` собирают нативный комплект с испытательным ключом и устанавливают его в чистую Debian Bookworm или Trixie amd64 в QEMU/KVM. После первой настройки проверяются версии реально запущенного сервера PostgreSQL и клиента. `task media:check:bookworm` собирает нативные службы на Debian Bookworm и прогоняет сценарии записи RTSP, выдачи WebRTC в браузерах и обработки тревог на системном GStreamer. Установочный носитель доступен только для чтения, архив размещён на отдельном ext4-диске. QEMU разрешает входящее HTTPS-соединение с браузерного стенда. Внешняя сеть отключена. После установки виртуальная машина перезагружается. Проверка сравнивает идентификаторы загрузок, состояние systemd, версии установленных пакетов и SHA-256 веб-ресурсов с подписанным составом поставки.

| Действие | Ожидаемый результат |
| --- | --- |
| Изменить Debian-пакет на копии носителя | Проверка подписи и хешей прекращает установку до изменения базы dpkg |
| Ввести пароль администратора до привязки | Требуется одноразовый код из локальной консоли. Сессия отсутствует |
| Зарегистрировать ключ и подтвердить запрос в Chrome | Администратор получает доступ к реестру камер. Повторный вход требует пароль и подтверждение ключом |
| Передать неверную подпись, затем верную с тем же запросом | Оба запроса отклонены |
| Выдать и отозвать доступ оператора | Точка появляется и исчезает в одной открытой сессии. Управление камерами остаётся закрытым |
| Назначить оператору роль администратора | Предыдущая сессия отозвана. Для входа требуется привязка ключа |

Каталог отчёта выводится командой. В `installation.json` сохранены матрица, версии браузера и испытательного окружения, в `installed.json` - фактический состав узла. В `bundle/sbom.json` перечислены пакеты, плагины, библиотеки C++ и компоненты веб-клиента. В `build-tools.json` указаны версии инструментов сборки и завершённого испытания, а также SHA-256 подписанного перечня файлов. Для сборки с ключом поставщика используйте `task release:package SIGNING_HOME=/absolute/gnupg SIGNER=<fingerprint> OUTPUT=/absolute/output` с пустым выходным каталогом. [Установка и первичная привязка](install.md) · [Восстановление конфигурации и архива](recovery.md)

## Пакетный ввод и откат каналов

Команда `task camera:commissioning` выполняет два сценария в отдельных базах. В первом браузер открывает записи двух последовательных привязок одной точки. Во втором ONVIF-эмулятор объявляет один блок с четырьмя видеовходами, по два профиля H.264 у каждого входа. Chrome сохраняет шаблон и применяет его к четырём каналам. Проверка сверяет подтверждения рекордера и наличие архивного блока у каждой точки. Протокол `batch.json` содержит исходные и фактические версии, конфликт, частичный отказ и команды изображения. Снимки показывают предварительное сравнение и результаты.

| Модель и прошивка | Возможности и проверка |
| --- | --- |
| Four-input encoder, программный эмулятор | Общий endpoint, четыре источника ONVIF, отдельные точки и записи по RTSPS. Три источника поддерживают яркость от 0 до 100. Четвёртый допускает смену профилей без настройки яркости |
| Fixed camera, программный эмулятор | Отдельная камера без Imaging обрывает HTTPS-соединение между сравнением и применением. Повтор после восстановления создаёт одну привязку. Откат отключает камеру и сохраняет записанные блоки точки |
| bacuri.vms ONVIF emulator и Camera B, программный эмулятор | Замена устройства сохраняет точку. Новая и прежняя записи открываются с привязками к соответствующим устройствам |

При подготовке обновления сервер отклоняет пару профилей от разных каналов и устаревшую версию шаблона. После потери ответа на запись яркости повтор сверяет фактическое значение. Во второй сессии меняется имя одного канала, другой вход отключается перед применением. Проверка сверяет конфликт версии, адреса, число команд записи яркости, повтор после восстановления связи и откат. Аппаратная серия для моделей и прошивок полного выпуска проводится по [профилю приёмки](release-profile.md#эталонные-устройства).

Дополнительная проверка воспроизводит конфигурацию без идентификатора физического входа. По сохранённому профилю ONVIF сервер находит прежнюю точку, меняет местами основной и дополнительный потоки и добавляет соседний вход отдельной точкой. После восстановления резервной копии проверка сравнивает все поля протоколов партии и всех версий шаблонов.

В прогоне ядра прошли 37 тестов в каждом из четырёх профилей C++ и 136 браузерных тестов. Покрытие строк составило 76,45% для C++, 84,40% для JavaScript и 84,37% для TypeScript рабочего места. Обновление схемы и откат сохранили все 32 проверенных архивных блока.

В дополнительном прогоне с инструментированным RTSP-эмулятором LeakSanitizer обнаружил утечку 320 байт в Fontconfig при выходе эмулятора. Пакетный сценарий с Core и рекордером под ASan/UBSan и отдельным RTSP-эмулятором из сборки GCC Debug прошёл.

## Управление камерой и звуковые каналы

`task camera:commissioning` проверяет обновление списка команд, выбор позиции и ограниченного патруля, зум, фокус, подсветку, очиститель и реле. Состояние входа считывается через PullPoint. Потерянный ответ не вызывает повторного движения. История команды остаётся доступна при отключении камеры, результат также находится в журнале действий.

Звуковой сценарий сравнивает переданный контрольный сигнал с отсчётами на выходе программной камеры после декодирования G.711. Отдельно проверяются приём, запись в блок архива, чтение интервала, запрет по правам и прекращение передачи микрофона. Аппаратный результат требует наблюдения положения, срабатывания контакта или независимого контроля звукового выхода для соответствующей функции. [Сценарий](../../tests/cameras/operations.py) · [Критерии аппаратной проверки](release-register.md)

В программном профиле прошли 39 тестов CTest в каждом из четырёх профилей сборки и 168 браузерных тестов в Chromium и Firefox. Для передачи речи проверены получение 1600 отсчётов на выходе устройства, прекращение речи при отзыве права и освобождение аудиодорожки браузера при отключении микрофона. Сквозной сценарий сохраняет количество отсчётов и среднюю абсолютную ошибку декодированного сигнала в `camera-operations.json`.

## Права и корпоративный вход

`task access:check` поднимает отдельный проект Docker Compose с PostgreSQL, синтетической RTSP-камерой, Chrome и Keycloak по HTTPS. Два независимых сеанса одного оператора получают одинаковые полномочия после локального и корпоративного входа. Для проверки используются две точки, группа, интервалы записи, раздельные разрешения, маска приватности и фактическая выдача WebRTC и HTTPS. [Сценарий](../../tests/access/scenario.py) · [Профиль realm](../../tests/access/realm.py)

| Изменение на площадке | Локальный вход | Корпоративный вход | Предел |
| --- | --- | --- | --- |
| Удаление точки из группы, время до последнего SRTP-пакета | 0,218 с | 0,132 с | 5 с |
| Отзыв просмотра во время передачи блока архива по HTTPS | 0,746 с | 0,778 с | 5 с |
| Отзыв экспорта во время передачи файла по HTTPS | 0,594 с | 0,594 с | 5 с |

Перед блокировкой учётной записи Keycloak стенд дождался продления действующей сессии. После блокировки Core отказал в доступе через 3,40 с, последний SRTP-пакет получен через 3,70 с при пределе 60 с. Изолированно проверены совпадающая почта у разных субъектов, обязательный второй фактор администратора (пароль и TOTP, acr 2), локальный WebAuthn при остановленном провайдере, истечение корпоративной сессии, повторный вход после запуска провайдера и исполнитель в аудите. При повторном восстановлении конфигурации сохранились привязка внешнего субъекта и записи аудита, появившиеся после создания копии. Это измерения одиночной площадки. [Управление доступом](ui.md#управление-доступом)

На подписанных комплектах проверены обновление после прерывания миграции, откат к исходной схеме, замена утраченного ключа WebAuthn и восстановление на независимом системном диске Debian. Сохранились все 39 проверенных блоков. Контрольный кадр архива воспроизвёлся через 7,37 с после остановки исходного узла, кадр новой записи - через 9,38 с. [Сценарий восстановления](../../tests/offline/operations.py)

## Профиль поставки

Приведённые ниже числа относятся к компактной площадке и сохраняются для регрессии. Для полного выпуска закреплены расширенная конфигурация автономного сервера, эталонные модели и прошивки, численные пределы нагрузки, RPO и RTO. Автоматическая квалификация охватывает каждый заявленный профиль. [Профиль полного выпуска](release-profile.md) · [Реестр требований и тестовых векторов](release-register.md)

Пределы ниже задают условия квалификации подписанного комплекта. Основания - круглосуточная запись на одной площадке, месячный горизонт расследования и измерения ядра на опорном узле. Целевой узел использует конфигурацию CPU и памяти из паспорта, Debian Trixie x86-64, сеть 1 Гбит/с и отдельный локальный том ext4 для архива. Битрейты, длительность серий, число проб и пределы заданы в [проверяемом профиле](../../tests/cameras/qualification.json). [Результаты испытаний отказов](#испытания-отказов-и-восстановления)

| Показатель | Предел и основание |
| --- | --- |
| Запись и просмотр | 8 основных потоков H.264 по 2 или 4 Мбит/с, 8 дополнительных по 0,5 Мбит/с. GOP до 1 с. Один зритель эфира и один зритель архива одновременно обслуживают наблюдение и расследование. В архив пишется основной поток |
| Объём | 30 суток по 8 камер требуют 5,184 ТБ при 2 Мбит/с и 10,368 ТБ при 4 Мбит/с. Выделить 14 ТБ после форматирования. При 20% запаса для колебаний битрейта и свободного места на видео, контейнер и индекс приходится 11,2 ТБ. 1 ТБ = 10¹² байт. Фактические накладные расходы измеряются на целевом томе |
| Ожидание оператора | p95 до 2 с для первого кадра эфира, доставки тревоги и первой страницы поиска отдельно на холодном и прогретом каталоге. Для первого кадра архива p95 до 3 с, включая поиск точки декодирования. Ошибка позиции до 1 с соответствует максимальному GOP |
| Изоляция | Ноль дополнительных пропусков по сравнению с контрольной записью, при отзыве права остановка выдачи до 5 с. На штатные запросы ожидается ноль ошибок. Преднамеренные отказы учитываются отдельно |
| Конфигурация и права | RPO до 5 минут при наличии сохранной локальной копии с таким интервалом. RTO до 5 минут от потери БД до входа и проверки разрешённой и чужой точек. Бюджет включает развёртывание копии |
| Исторический архив | RPO 0 для исправных завершённых блоков на сохранном томе. RTO до 15 минут до декодирования прежнего кадра, включая сверку каталога. Повреждение блока и полная утрата носителя учитываются отдельно по объёму фактической потери |
| Новая запись | RPO до 30 с по интервалу между блоками и RTO до 60 с от начала контролируемого отказа до первого декодированного нового блока. Предел рассчитан на кратковременные отказы протокола и исправный источник после восстановления. В регрессии малый том дал перерыв до 4,324 с и время до кадра до 5,276 с |

Серия использует синтетические H.264-кадры. Протокол хранит численные результаты отдельно от критериев. К аппаратной матрице и смешанной нагрузке применяются собственные условия прохождения. ## Результаты проверки инфраструктуры

Ниже зафиксированы выполненные проверки существующего ядра и среды сборки. Отчёт об автоматических испытаниях и протокол ручной приёмки формируются на релиз-кандидате.

В полном прогоне с Gitleaks и clang-format покрыты 2827 из 3171 строк продуктового C++ (89,15%) и 577 из 627 строк рабочего JavaScript (92,02%). Gitleaks завершил три проверки без находок. CTest прошёл на GCC, Clang, под ASan/UBSan и TSan, а также в сборке покрытия. Повторный прогон измеряет обе доли заново. [Критерии приёмки](quality.md#автоматические-проверки-кода)

Для шкалы архива и формы подключения камеры `task ui-kit:check` прошёл 44 браузерные проверки в Chromium и Firefox в светлой и тёмной темах. На форму приходятся 24 проверки. Подтверждены фокус первого ошибочного поля, состояние каждого потока, сохранение ввода и однократная отправка при повторе, обработка запоздалого ответа после изменения адреса. Для шкалы проверены границы пропуска, выбор времени и обновление каталога с сохранением позиции. Оба компонента проверены при ширине 320 CSS-пикселей и размере текста 200%. По исходным TS и TSX покрыты 510 из 538 строк (94,80%). Контрольный незагруженный модуль учтён с нулевым покрытием при проверке механизма подсчёта. Для полных экранов действует отдельный сквозной протокол. [Шкала архива](ui.md#шкала-архива-в-ui-kit) · [Форма подключения камеры](ui.md#форма-подключения-камеры-в-ui-kit)

С Conan два независимых разрешения профилей GCC и Clang дали одинаковый lockfile. После перехода с прежних каталогов CMake во всех четырёх тестовых пресетах прошёл 31 тест, включая прогоны с ASan/UBSan и TSan. Полный прогон `task check:report` завершился с кодом 0. На Release отдельная проверка тревоги в Chrome и Firefox открыла эталонный кадр 16. Команда `task build:repro` повторно собрала проект без сети в чистом каталоге того же образа. Все четыре исполняемых файла совпали побайтно. [Границы проверки воспроизводимости](adr/010-build-dependencies.md)

С чистой копии источников `task check:report` завершился с кодом 0. Прошли сборки GCC и Clang, стартовый CTest в обычных и инструментированных сборках с ASan/UBSan и TSan, а также статический анализ. PostgreSQL ответил на запрос по сети Compose. Оба H.264-профиля синтетической камеры декодировались в ожидаемом разрешении.

`task stand:check-storage` подтвердил сохранность тестовых данных PostgreSQL и архива после остановки и повторного запуска Compose. Заполнение tmpfs вернуло `ENOSPC` на границе 64 МиБ. При повторном запуске контейнера временный том был пуст.

## Протокол измерений

Базовый функциональный профиль включает управляемый источник и физическую IP-камеру. Для квалификации обязательны физические конфигурации из паспорта испытаний. Для каждого теста указываются идентификатор комплекта, ожидаемый и фактический результат и код завершения. Ошибка, пропуск обязательной строки или отсутствие устройства блокируют ручную приёмку.

В автоматической серии контрольную запись и смешанную нагрузку сравнивают на одном релиз-кандидате. Стенд использует восемь двухпоточных источников. При номинальном битрейте основного потока 2 Мбит/с выполняют контрольный и смешанный прогоны, затем повторяют оба при 4 Мбит/с. Каждый прогон записи занимает 5 минут, включая 1 минуту прогрева и 4 минуты измерений. Во время смешанного прогона одновременно работают запись, один клиент эфира, один клиент архива, поиск и тестовые наблюдения с частотой 1 событие/с. Для первого кадра, окна поиска и задержки тревоги собирается не менее 200 проб каждого вида на каждый битрейт в смешанном прогоне. Холодный поиск прогоняется отдельно с описанием начального состояния кэша.

Основные условия приёмки приведены в матрице. Предел на этом стенде - до 2 с по p95 для первого кадра эфира, отображения тревоги и первой страницы поиска. В каждом прогоне фиксируются p50, p95, p99, число проб, доля ошибок, потребление ресурсов, глубина очередей, разрывы и объём записи на диске. Стоимость хранения рассчитывается из фактического объёма за единицу времени и ёмкости выбранного носителя. Для каждого сценария отказа фиксируются начало отказа, первый обнаруженный пропуск, момент возвращения проверенной операции и объём невосстановимых данных.

| Поле результата | Что записать |
| --- | --- |
| Воспроизводимость | Ревизия проекта, версии образов и пакетов, оборудование, тип файловой системы, конфигурация сети и источник |
| Нагрузка | Число потоков и клиентов, измеренный битрейт, GOP, частота событий, длительность, объём выборки и условия запуска |
| Наблюдение | Ожидаемый результат, фактический результат, метрики и ссылки на артефакты |
| Сбои | Причина, диапазон пропуска, проверенные копии, потеря данных, длительность восстановления записи, архива и конфигурации |

## Регрессия ядра

Контрольный прогон на Linux x86_64 с ext4 и Docker Engine прошёл все автоматические гейты. SHA-256 перечня проверенных исходников в `files.json` - `50b7f457334907838aa59e99eea5bb03416f2a6120d0d0e1b14a01bec090a8be`. Команда `task regression:check` формирует новый отчёт со своим хешем.

| Проверка | Результат на синтетической RTSP-камере и локальном стенде |
| --- | --- |
| Компиляторы, анализ и браузеры | 31 тест CTest в каждом из четырёх профилей, 8 проверок прототипа и 60 проверок UI Kit и экранов. Gitleaks, clang-format и clang-tidy прошли. Chrome и Firefox декодировали кадр, связанный с тревогой |
| Покрытие строк | C++ 3066/3409 (89,93%), JavaScript 570/627 (90,90%), TypeScript 1985/2204 (90,06%). Порог 75% выполнен отдельно для каждой области |
| Хранилище и восстановление | Шесть точек прерывания фиксации прошли в трёх профилях. При недоступной PostgreSQL подтверждённые блоки сохранились. После перезапуска Compose сохранились база и архив. Две независимые Release-сборки дали побайтовое совпадение четырёх исполняемых файлов |
| Обновление PostgreSQL | В копии данных перестроены 48 индексов. До обновления, после него и после восстановления полной копии совпали три архивные записи и ожидающая тревога |
| Сопровождение | В 12 образах, графах Conan, npm и инструментах стенда проверены 7754 записи о компонентах. Открытых блокирующих находок и временных исключений нет. В автономном прогоне получены те же решения |

В `postgres-upgrade/result.json` сохраняются образы исходной и обновлённой PostgreSQL, перечень перестроенных индексов, ключи найденных архивных блоков и ожидающей тревоги. Они должны совпасть на исходной базе, на обновлённой копии и после запуска сервера из новой полной резервной копии.

`task regression:check` проверяет функциональный профиль с синтетической RTSP-камерой. Для повтора сохраняются исходники с эталонами, ревизия Git, SHA-256 состава и признак локальных изменений. Новый каталог сборки, отдельная сеть и новые тома исключают использование данных предыдущего прогона. Результаты независимой Release-сборки и сохранности томов учитываются отдельно.

В `core/check.log` находятся результаты CTest, контрактов, ввода по RTSP, записи, эфира, тревог и поиска. В `core/workspace` сохраняются снимки Chrome и Firefox и измерения штатного клиента, в `core/recovery` - прерывания, потери и восстановление. В `core/dependencies` сохраняются фактические компоненты, роли, источники и ревизии сведений, применимые уведомления, исправленные версии и исключения. Критическое уведомление блокирует результат до обновления или успешной автоматической проверки адресной меры защиты. Пропуск сведений о сопровождении и истёкшее исключение также блокируют результат.

При автономном повторе проверяются хеши снимка и применяется момент исходной оценки. Для регрессии ядра срок актуальности снимка ограничен 30 сутками. Перед квалификацией сведения обновляются для конкретного кандидата. Для npm источником сведений служат карточка точной версии в реестре и канал исправлений проекта, для веток Node.js и PostgreSQL - сведения поставщиков. Системные пакеты проверяются по данным дистрибутива. Для компонентов внутри сторонних образов сохраняются также образ и отчёт сканера. [Политика сопровождения](adr/015-technology-lifecycle.md)

Протокол собственной RTSP-реализации физической камеры заполняется на выделенном стенде. Испытание смешанной нагрузки проводится на релиз-кандидате. [Границы аппаратного подтверждения](rtsp-compatibility.md)

### Обработка тревог и аудит

`task alerts:check` проверяет одновременное принятие одной тревоги двумя операторами, обрыв HTTPS до получения ответа и повтор с прежним ключом. Сверяются ответственный, версии и число записей истории. Проверяются отказ на чужой точке, запись результата сервисом, запрет другого действия, истечение срока, отзыв поручения и потеря права у инициатора. Поиск проверяется по тексту, идентификатору и курсору следующей страницы.

`task workspace:check` проводит дежурного от тестового события движения к пронумерованному кадру архива. Дежурный принимает тревогу, записывает результат, закрывает её, находит результат в журнале и возвращается к той же позиции архива. Прогон выполняется в Chrome и Firefox. Снимки журнала сохраняются вместе с отчётом рабочего места.

В прогоне `task camera:commissioning` ONVIF-эмулятор отправляет уведомление через PullPoint. Браузер открывает тревогу из WSS, а независимый декодер сверяет показанный кадр с блоком записи RTSP. Затем оператор закрывает эту тревогу и находит свой результат в журнале. Протокол содержит идентификаторы наблюдения, тревоги, блока и трёх записей истории.

### Восстановление установленного узла

`task maintenance:check PREVIOUS=/путь/к/отчёту` принимает сохранённый подписанный комплект и его испытательный ключ. Исходный комплект должен допускать обновление и откат по правилам установщика. Две виртуальные машины KVM используют независимые системные диски Debian Trixie amd64, общий по очереди архивный том ext4 и отдельный носитель копий. На запасной машине предварительно установлен пакет, площадка отсутствует, системный UID рекордера отличается. Источник видео - синтетическая RTSP-камера. [Порядок обслуживания](maintenance.md)

Сценарий записывает видео, создаёт тревогу и выдаёт оператору доступ к точке. Он прерывает транзакцию миграции, сверяет версию схемы и контрольную сумму копии, повторяет обновление и отдельно выполняет откат с подписанным комплектом предыдущей версии. Затем после новой копии отзывает административный ключ. После внезапного выключения исходной машины проверяет доступ по HTTPS, права, историю тревоги, отказ по прежним ключам и сессиям. Для старого кадра сверяется SHA-256 пикселей, для нового браузер декодирует кадр и проверяет наличие тестового изображения.

В `operations.json` сохраняются идентификаторы комплектов, число сохранных блоков, события аудита и сравнение с пределами профиля. Время отсчитывается с отключения работающего узла и включает загрузку подготовленного запасного. Возраст конфигурации считается от начала последней успешной копии, разрыв записи - между концом последнего завершённого блока и началом первого нового. В `diagnostics.json` сохраняются метрики, события и связанные OTLP spans для отключения камеры, остановки выдачи, накопления очереди каталога и заполнения тома.

Для архивного кадра контрольная сумма пикселей совпала после обновления, отката и замены системного диска. Повреждённая копия была отклонена до остановки служб.

| Завершённый архив | 0 блоков потеряно | 6,84 с до воспроизведения | 0 с / 900 с |

На подписанном комплекте проверены два пути обновления с разных исходных схем. В каждом прогоне после прерывания миграция завершилась повторным запуском, откат вернул исходную схему, а на запасном системном диске восстановились все 9 завершённых блоков. SHA-256 пикселей контрольного кадра совпал с исходным. От выключения исходной машины до воспроизведения новой записи прошло 8,29 с в первом прогоне и 9,17 с во втором.

### Экспорт и автономная проверка

`task export:check` открывает тревогу в Chrome и сохраняет комплект штатной кнопкой рабочего места. У синтетического источника 25 кадров в секунду. Контрольный интервал начинается и заканчивается внутри блока, включает один исходный MP4 и секунду отсутствия связи с камерой. Отдельный контейнер с отключённой сетью проверяет доверенный ключ площадки, происхождение, границы, длительности перекодированных MP4 и номера всех кадров.

Комплект сохраняется в `episode.tar`, открытый ключ - в `trusted-key.json`. Файл `browser.json` содержит контрольные манифесты, ответы при отказах и события аудита. Файл `verification.json` содержит контрольную сумму комплекта, проверенные интервалы и номера кадров. Там же находятся снимки экрана выбора и результата. Команда печатает путь к каталогу материалов. [Сценарий экспорта](../../tests/archive/export.py) · [Автономная проверка](../../tests/archive/verify_export.py)

### Срок хранения и контроль ёмкости

`task retention:check` использует изолированную PostgreSQL, управляемые часы каталога, синтетическую RTSP-камеру и отдельный том tmpfs объёмом 64 МиБ. За микросекунду до границы блок доступен в каталоге. На границе ранее выданная HTTPS-ссылка на этот блок закрывается, в том числе при остановленном рекордере. Следующий блок того же медиапотока читается по своей ссылке. После запуска рекордера проверяются файлы, строки PostgreSQL и локальный журнал. Увеличение срока и восстановление каталога проверяются с ранее истёкшим блоком.

Внешний файл на тестовом томе доводит свободный остаток до уровня предупреждения, затем до резерва. Тест сверяет состояние диагностики, появление пропуска, содержимое защищённого фрагмента по HTTPS и его контрольную сумму на диске. После освобождения места проверяется фиксация нового блока. Отчёт `capacity.json` в каталоге прогона содержит измерения ёмкости, прогноза и результат сверки.

`task test` прерывает процесс после фиксации границы очистки, после переименования каталога блока и после удаления файлов. Каждый вариант открывает том заново и проверяет, что остаётся ровно один действующий блок, а повтор очистки сохраняет его.

## Профили эфира и многоканальный просмотр

`task monitoring:check PRESET=gcc-debug` запускает Core, рекордер и службу выдачи на отдельной базе и открывает рабочее место через HTTPS в Chrome и Firefox. Оба поста получают одну общую раскладку из четырёх камер. Сценарий проверяет порядок ячеек, права на камеры, сохранение личной раскладки, конфликт редакций и видеостену. После разворота одной камеры браузер подтверждает размер декодированного кадра основного и дополнительного потоков. После возврата в сетку второй пост продолжает получать кадры. В журнал выводятся задержки, разрешения, число предъявленных и отброшенных кадров, RSS рекордера и службы выдачи. Для контрольной записи проверяются число кадров каждого GOP и разрывы по UTC.

Общий бюджет эфира задаётся переменной Core `BACURI_VIDEO_BUDGET_KBPS` в кбит/с, по умолчанию 64000. `BACURI_VIDEO_TRANSCODERS` задаёт число одновременных преобразований для эфира и архива вместе, по умолчанию 1. Значение 0 закрывает выдачу, требующую преобразования. В установленном узле обе переменные читает служба Core из `/etc/bacuri-vms/core.env`. В Compose их можно задать в окружении проекта.

Серия включает основные потоки H.264 и HEVC Main 8 бит. Для пары HEVC/H.264 проверяется выбор дополнительного H.264 без преобразования. Для пары HEVC/HEVC проверяются выдача H.264 по WebRTC и отказ второй задаче при занятом преобразователе. Исходный архивный блок и совместимая копия читаются через REST. Проверяются конфигурация декодера в fMP4, декодированные пиксели до и после маскирования, отказ при изменении политики и отказ при исчерпании бюджета. `task playback:check` воспроизводит в Chrome и Firefox соседние участки H.264 и HEVC с изменением разрешения и сверяет цвет и номер кадра при переходе и поиске. Программная серия проверяет механизмы рабочего места. Параметры установок и оборудование полного выпуска заданы в [профиле приёмки](release-profile.md).

В контрольном прогоне двух постов разворот ячейки с 640x360 до 1280x720 занял 858 мс, восстановление четырёх декодируемых ячеек - 957 мс. За контрольный интервал проверены восемь последовательных блоков записи без потерянных кадров или разрывов UTC. RSS составил 57236 КиБ у рекордера и 140956 КиБ у службы выдачи. Первый кадр совместимой копии HEVC через WebRTC получен за 1259 мс. В этой конфигурации Firefox декодировал исходный HEVC из архива, Chrome использовал совместимую копию. Прямую выдачу HEVC через WebRTC проверил приёмник GStreamer с декодированием 640x360. Оба браузера в этом прогоне объявили для WebRTC только H.264 из двух проверяемых кодеков.

## Проверка политик записи

`task recording-policies:check` запускает изолированные Core, рекордер и источник RTSPS. В верхней полосе каждого изображения закодирован порядковый номер кадра, на аудиовход подаётся контрольный тон. Проверка читает MP4 из сохранённых блоков, декодирует номера и проверяет непрерывность с учётом переполнения счётчика. По меткам манифестов сверяются 5 с перед первым событием и 10 с после последнего, включая ручную запись и повторную доставку наблюдения. Начало видео округляется к предыдущему ключевому кадру, аудио ограничивается выбранным интервалом.

После перезапуска рекордера сценарий подаёт новое событие, снимает исключение камеры и проверяет ручную запись без аудиодорожки по политике группы. Затем недельное расписание пересекается с ручным и событийным окнами. Кадры продолжаются после окончания обоих окон. В нативном тесте восемь различимых кадров H.264 проходят через рекордер с метками UTC до, внутри и после обоих вхождений повторяющегося часа Europe/Berlin. Из MP4 декодируются четыре ожидаемых номера. Отдельно проверяются весенний пропуск и интервал через полночь.

Chrome открывает действующую политику группы через камеру, сохраняет исключение и читает фактическую ёмкость. В каталоге отчёта сохраняются снимки редактора. API проверяется на недостаточные права, повтор ручного запуска и конфликт редакций. После сокращения срока проверяются видимость в каталоге, удаление файла, независимая граница другой точки и сохранение достигнутой границы при увеличении срока.

`task retention:check` заполняет отдельный том tmpfs объёмом 64 МиБ. Проверяются предупреждение, остановка на резерве, доступ к уже записанному материалу и возобновление записи после освобождения места.

## Проверка архива и расследований

`task investigations:check PRESET=gcc-debug` поднимает стенд, выполняет проверки на отдельных временных базах и формирует отчёт в `build/reports/investigations-*`. Используются программные источники с известными кадрами. Аппаратная проверка требует записи на устройстве из [матрицы квалификации](rtsp-compatibility.md#матрица-оборудования-для-выпуска).

| Сценарий | Эталон и наблюдаемый результат |
| --- | --- |
| Догрузка | На источнике H.264 номер записан в пикселях. Разрыв соединения прерывает передачу, повтор заполняет доступные интервалы. Проверяются номера декодированных кадров, отсутствие дублей и сохранение пятисекундного пропуска. Отдельная доступная минута проверяется целиком. |
| Видеоправила | Разметка двухсот эпизодов закреплена SHA-256 до выполнения. Один и тот же видеоряд проходит шесть независимых проверок: зона, исключение, линия, амплитуда, число ячеек и расписание. Один эталон может соответствовать одному срабатыванию с отклонением до секунды. Отдельно проверяются реальные команды на тестовом источнике и отсутствие действия при моделировании. |
| Целостность и удержания | На частном томе четыре точки по 5 минут, 25 кадров/с. Эталонные видео декодируются перед запуском. После достижения резерва, очистки и восстановления журнала SHA-256 сверяются у всех 20 блоков на обоих томах. В отчёт `protected-recording.json` входят объём медиа каждой копии, количество кадров и время восстановления со сверкой. |
| Поиск и просмотр | В браузере сравниваются номера четырёх декодированных кадров по пикселям, включая переход через границу соседних блоков. Одна точка имеет сдвиг часов +2 с, у другой индекс временно недоступен, введён явный разрыв. `measurements.json` содержит рассинхрон, выборку времени отклика HTTPS и время остановки выдачи после отзыва права. Проверяется обработка ранее поставленных в очередь блоков при продолжающейся записи четырёх камер. Для холодного каталога выгружаются страницы таблиц архива, их индексов и TOAST из буферов PostgreSQL временной базы. Следующий запрос измеряет прогретый каталог. Файловый кэш хоста сохраняется. |
| Дело и выдача | Дело передаётся второму оператору, отправка проверяется до и после изменения прав. Отдельный контейнер без сети проверяет обе цепочки подписей, точные кадры, маски и звуковые отсчёты. Подмена подписи приводит к отказу. |

В контрольном прогоне каждая из шести проверок детектора дала TP 100, FP 0 и FN 0. В двух сериях по 200 HTTPS-запросов p95 составил 82,49 мс для холодного каталога и 82,09 мс для прогретого. Во всех пробах синхронного просмотра номера кадров на четырёх дорожках совпали. Передача комплекта прервалась через 0,716 с после отзыва права. В пятиминутной проверке удержаний на каждом томе проверены 20 блоков общим объёмом 5 171 815 байт. Восстановление журнала и сверка обеих копий заняли 0,123 с. Сохранены все 30 000 кадров.

Измерения на компактном программном стенде относятся к указанным видео и ресурсам. Полная нагрузка и аппаратная проверка выполняются по [паспорту расширенной установки](release-profile.md).
