## Administrative operations of the full release

The target routes below are relative to `/api/v1/sites/{siteId}`. They define the contract for the implementation. The current routes are listed in the OpenAPI of the original version. A policy change requires the administrative right in the site scope, a revision check and an audit record. The response to the client contains the resource identifier, the applied revision and the permitted next actions.

| Task | Target public API and result | Local operation |
| --- | --- | --- |
| Users, groups, access | `GET/POST /users`, `PATCH /users/{userId}`, `GET/POST /resource-groups`, `PUT /resource-groups/{groupId}`. `PUT/DELETE /grants/{grantId}` grant or revoke an action of a subject on a point, a group or an interval, including the export of the original. `POST /audit/search` limits the results to the scope of the actor | create-user, grant-point, revoke-point, grant-export, revoke-export use the same C++ operations |
| Provider and external identity | `GET/PUT /identity/provider` set the issuer, the client ID and the trusted MFA level. ## Client contract

A compatible client keeps the `site_id`, the point identifier and the UTC interval. For a frame or a command it also records the binding revision, the actual device and the channel. Replacing a camera keeps the point. For an investigation the identifiers of the event, the rule revision, the case, the hold and the copy are kept. Names, coordinates and view URLs can change. A new resource gets the site scope and a stable identifier. The client gets a media link after the current permissions are checked.

The server reports the operations available for a resource to the current subject, model, firmware and delivery profile. The client shows the reason for limitations and requests the state again after a change of permissions, device or topology. Mutations with retries get an idempotency key, changes of versioned resources a precondition revision. A batch operation returns separate results per device. An asynchronous command has an ID, a term, an owner and the states "sent", "acknowledged", "result observed", "rejected" or "outcome unknown".

Within a compatible API the existing fields, values and semantics are kept. A new optional field accepts the previous request and client. An incompatible change gets a parallel major version and contract examples for both sides. With an unknown capability the client keeps the other operations available. An error returns the HTTP status, a stable code and the request identifier. The client distinguishes a missing session (401), a refused permission (403, taking the resource hiding rules into account), a replay conflict (409), a revision conflict (412), a missing precondition (428) and an unavailable dependency (503). On WSS the client applies an event by ID, continues after the last applied cursor and gets a fresh snapshot on `resync_required`. Removing a resource from the permission scope closes its views and the active delivery. [ADR-001](adr/001-api-contracts.md) · [REST examples](../tests/contracts/rest.yaml) · [WSS examples](../tests/contracts/alerts.yaml)

### Sign-in through the site

The site publishes the available sign-in methods. In an autonomous installation local accounts apply, and an administrator needs a password and WebAuthn with user verification. With OIDC enabled, the site acts as a Keycloak client, starts the Authorization Code Flow with PKCE S256 and one-time `state` and `nonce`, and checks the result against the exact trusted issuer, the signature, the audience and the term. The client secret and the provider tokens are available only to the server. The site administrator explicitly binds a unique `(iss, sub)` pair to a Bacuri user. Changing or removing the binding revokes the related sessions and is recorded in the audit. A matching e-mail, login or group name grants no permissions. [OpenID Connect Core](https://openid.net/specs/openid-connect-core-1_0.html)

For an administrator session the server requires a verified `acr` level that the trusted realm configuration maps to a mandatory second factor. With an insufficient level, a repeat with MFA or a local sign-in with WebAuthn is needed. The site issues its own session, applies its own permissions and writes the sign-in method and the local actor to the audit. The web gets the regular protected cookie and the CSRF token. The desktop client opens the system browser on the site and gets a one-time Bacuri code with a 60 s term through a registered loopback redirect. The exchange is bound to the return URI, to the client instance through PKCE S256 and to the original state. Only the exchange opens a separate application session. [OAuth for native apps](https://www.rfc-editor.org/rfc/rfc8252)

Sign-out first closes the Bacuri session, its media sessions and subscriptions, and the client clears the local state of all windows of this session. The site can also end the IdP session. A failure of this request keeps the local sign-out result. A permission revocation in Bacuri applies to new operations at once, and the limit for stopping active delivery is 5 s. From blocking a user in Keycloak to the refusal of their active corporate Bacuri sessions and the end of their delivery it takes at most 60 s. The budget consists of 55 s of freshness of the confirmed subject state and 5 s to stop the transmission. The confirmation must take the actual block in the realm into account. Checking the signature of an already issued JWT does not by itself refresh the state. With the provider unavailable, a new corporate sign-in is closed, and the active access uses up the same budget from the last positive confirmation. The local administrator keeps sign-in and recovery. Record in the protocol the Keycloak version, the MFA settings, the status confirmation method and the measurements from the block to the last permitted action.
