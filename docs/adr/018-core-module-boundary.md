# ADR-018. Boundary between Core and pluggable modules

[Русская версия](../ru/adr/018-core-module-boundary.md)

**Status** - Accepted.

**Decision.** Core is the set of domain capabilities and guarantees that Bacuri is responsible for on an autonomous site. A pluggable module enriches these capabilities with data, an algorithm, an integration or a specialized workflow. Membership is defined by responsibility to the user. The placement of code, the number of processes and the inclusion of a component in the installation kit are chosen separately.

## Responsibility boundary

| Area | Owner in Core | What a pluggable module adds |
| --- | --- | --- |
| Devices and video | Point catalog, binding history, command permissions, the supported regular path for connection, recording, live video and playback | An adapter for a device family, additional commands and telemetry sources |
| Archive and investigations | Originals and catalog, time and breaks, storage and protection of an interval, manual search and selection, applying masks by the site policy, export and verification of material origin | Detections and search attributes, selection of related frames, automatic object tracking for masking, an industry report |
| Events and shift work | Intake of observations with their source, local rules, alarm state and history, assignment, confirmation and audit | Point-of-sale or access control events, specialized conditions, an external notification channel |
| Access and operation | Identity and permissions, their granting and revocation, the recording state and read verification, site diagnostics and recovery | Scene quality assessment, failure prediction, diagnostics of the module's own hardware or service |

The regular client provides a manual path from a camera or an alarm to a recording and to the release of material. A module can add an action or a view. The owner of the operation checks the right to read, change and release. For example, a point-of-sale module owns the mapping "receipt -> point and time". When a receipt is opened, Core checks the current access to the recording, and when an interval is protected, Core itself resolves the conflict with the cleanup. For an industry customer a module can be a mandatory part of the solution. [Data owners](../architecture.md#2-components-and-data-owners)

## Execution and the module contract

Today control is gathered in the `bacuri-vms-core` process. Recording and media delivery are moved to `bacuri-vms-recorder` and `bacuri-vms-media` to isolate failures. All three services implement Core responsibilities. [ADR-002. Process boundaries](002-processes.md)

**Rule inside the monolith.** Only the owning module reads and changes its internal tables and views. The rule covers both `SELECT` and `JOIN`, even when the domains share one PostgreSQL. Another module requests data or an action through the public interface of the owner or maintains its own projection from published events. In one process the interface can be an ordinary C++ call. Implementation headers and data repositories stay internal. For example, the camera registry needs the operation "find the last interval of the previous binding". The SQL for it belongs to the archive catalog.

Operations between owners take and return typed C++ values. HTTP, gRPC, PostgreSQL and the SQLite journal convert their wire or storage representation at the boundary. A conversion used by one adapter lives in its implementation file. Adapters that share a representation include a codec for that format. Input commands and stored records use separate types when the server assigns fields, such as the archive hold on an investigation material. The architecture check follows project includes from headers in `src/modules`, `src/application` and `src/archive`. Outside explicitly listed transport and serialization headers, it rejects JSON types and direct or transitive dependencies on the JSON library or a codec.

### Internal Core modules

The boundary of a domain (a bounded context in DDD) is defined by the meaning of the terms, the invariants and the owner of the change. An observation point keeps its identity after the camera is replaced. A recorded block keeps the binding revision at the time of recording. An alarm has its own revision and owner. One user operation can touch all three models. An application handler coordinates them through the operations of the owners.

| Owner | PostgreSQL schema | Data and operations |
| --- | --- | --- |
| [Equipment registry](../../src/modules/inventory/operations.hpp) | `bacuri_inventory` | Site, points, devices, configuration and binding history. Confirms the source revision when an observation is accepted. |
| [Identity and access](../../src/modules/access/operations.hpp) | `bacuri_access` | Accounts, browser sessions, roles, permissions for points and export intervals. Decides access at the time of the operation. |
| [Recording catalog](../../src/modules/recordings/operations.hpp) | `bacuri_archive` | Intervals, breaks, retention policy, recovery and the mapping of playback parts to specific blocks. Returns intervals and part descriptions. |
| [Media sessions](../../src/modules/media_sessions/operations.hpp) | `bacuri_media_sessions` | Opening, term, state and closing of a delivery session. On recovery the catalog closes the active archive sessions through the owner. |
| [Events and alarm handling](../../src/modules/events/operations.hpp) | `bacuri_events` | Observations, alarm state, the action log and the publication of changes. For the transition to a recording, returns the point, the time, the precision and the binding revision. |
| [Maps and plans](../../src/modules/maps/operations.hpp) | `bacuri_maps` | Regions, plans and point placement. Applies the visibility scope of the operator when a plan, its image and markers are delivered. |
| [Investigation cases](../../src/modules/investigations/cases.hpp) | `bacuri_investigations` | Case number, assignee, materials, bookmarks and revision. Changes material protection through the recording catalog within the same transaction. |

Export and backup coordinate several owners. When a package is released, export checks together the user's permission, the archive state and the retention of the selected blocks. These decisions are read in one PostgreSQL snapshot. On recovery each owner describes its configuration sections, and the whole set is applied in one transaction. When a service is extracted for such scenarios, the moment a revocation takes effect and the behavior on a partial failure must be defined explicitly.

The alarm handling model defines the available transitions by state, expected revision, owner and the presence of a result. The operator card and the command handler get the decision of one model. The transaction of the handler binds the revision change, the audit and the idempotent response. [Transition model](../../src/modules/events/workflow.hpp) · [Unit tests](../../tests/modules/events/alert_workflow.cpp)

The pattern is chosen for the specific task. Domain value objects check the bounds of time and intervals. For a composite read the catalog returns a typed result model. For reliable publication of observations the site uses a transactional outbox. A new internal module is justified when it has its own rules, data and a clear contract for the consumer. [Time types](../../src/domain/time.hpp) · [Observation registration](../../src/modules/events/observations.cpp)

### PostgreSQL data ownership

On an autonomous site Core uses one `bacuri_vms` database. The persistent objects of a module are placed in its schema. The technical `bacuri_meta` schema keeps the migration log of the whole database. An application query names the schema and the object. When a snapshot of accounts is restored, the maintenance tool chooses the owner's schema by the snapshot version. Historical keys of backup sections keep their meaning after tables are moved. [Schema migration](../../storage/postgresql/migrations/0016_module_schemas.sql)

In the current delivery, connections of the monolith to PostgreSQL use the common `bacuri-core` role. All domain schemas are closed to `PUBLIC`. Inside the process, calls to owners are controlled by architecture tests. When a separately running module with a direct PostgreSQL connection appears, it gets its own role with permissions on its schema and objects. To interact with Core it uses the published operations and events.

The existing foreign keys and the trigger of the feed permission revision keep the consistency of one transaction. When a service is extracted, the replacement of each such dependency is defined first, including the revocation deadline. A separate database is justified by independent recovery, an update cycle or a measured need for resource isolation. A module can introduce an outbox, projections or Event Sourcing while its data stays in the schema of the monolith.

### Pluggable components

A pluggable module can start as a component with an explicit interface. A trusted component may be delivered together with the platform. For third-party code and resource-intensive processing, isolated execution is provided. One module can over time become a standalone service or a subsystem with several services, its own storage and interface. For the site it still provides the declared capabilities through a versioned contract. Symmetrically, a Core domain can get a separate process and keep its obligations to the site.

The extension boundary defines the input data, the results with their origin, the permitted commands and the behavior when unavailable. A module owns its state. It requests changes in Core from the owner of the operation through the contract. For independently installed extensions the architecture provides a manifest of capabilities, versions, dependencies, permissions, quotas and migrations, a signature check and revocation of access on disconnection. The current implementation already has observation intake and limited delegations to a service. General installation of third-party modules belongs to the further development of the platform. [Extensions and SaaS](../architecture.md#9-extensions-and-pluggable-saas) · [Observation contract](../../contracts/v1/control.proto)

## Evolution of Core and events

**Extracting a service.** The reason is a specific limitation of the domain, for example the impact of its failure on recording, an independent release cycle or measured resource contention. Before the move, the data owner, the operations, the transactional guarantees and the client behavior on a lost connection are defined. The new service first reconciles its state with the current owner. The switch gives the write right to one owner and provides for processing the accumulated changes and a recovery path. In this way microservices can be extracted step by step from Core or from a pluggable subsystem.

**Event-driven interaction.** A command expresses an intention and is authorized by the owner. An event reports a committed fact. Today, when motion is registered, the site stores the observation, the alarm and the publication record in one PostgreSQL transaction. When a consumer is extracted, the event identity, the schema version, the order within the source or object and the idempotent processing of repeats are kept. A consumer recovers from an acknowledged position or from a snapshot when the delivery history has expired. A broker can be introduced when independent subscribers and load require it. [Registration implementation](../../src/modules/events/observations.cpp) · [Event delivery](../architecture.md#6-events-reactions-and-commands)

**Event Sourcing.** This is a separate decision about storing the state of a specific domain, applicable inside the monolith as well. In the current model the alarm state is stored in PostgreSQL, the audit records the actions, and the outbox provides delivery with a bounded history. With Event Sourcing, the ordered history of the domain events of an object becomes the source of its state. For example, for an investigation case the reason can be the requirement to reproduce the materials and decisions at any revision of the case. Before the move, the initial revision for the existing data, the rules of concurrent writes and the reading of old schemas are defined. The check of the move replays the events up to the selected revision and compares the state and the projections. When projections are rebuilt, sending notifications and executing hardware commands are disabled. [Event Sourcing](https://martinfowler.com/eaaDev/EventSourcing.html)

## Boundary verification

The root `CMakeLists.txt` includes seven domain modules and the export and configuration recovery modules with `add_subdirectory()`. Each module declares its static libraries, dependencies and GoogleTest sources in its own `CMakeLists.txt` under `src/modules/` or `src/application/`. CMake declares their dependencies and rejects cycles. Cross-module queries such as looking up a point on a plan can link to the owner’s operations independently of its HTTP handlers. The maintenance tool and Core link the same archive recovery implementation.

For one owner, `task module:check MODULE=maps` builds the module and its dependencies, checks the formatting of its sources and headers, runs its tests from `tests/modules/maps/` and analyzes its code and tests with clang-tidy. The project-wide checks use the same formatting and analysis rules. Each owner has a GoogleTest executable. Its link includes every object of that owner and only the declared dependency graph. Run `ctest --preset gcc-debug -L core-modules` in the builder to test the nine modules without PostgreSQL. Release builds perform the same nine link checks with an empty entry point. GoogleMock supplies point visibility in the monitor layout tests. The build target `core-undeclared-module-link` verifies that the access library alone cannot resolve the map placement lookup. For access, maps, investigations, inventory, events and recordings, GoogleMock supplies libpq result rows without a database connection. The tests check bound arguments and the decisions taken by the owner.

`task module:unit-coverage` runs only the owner tests without PostgreSQL and writes their line counts per module to `unit/modules.txt`. `task coverage:check` records the same baseline before the integration scenarios and applies the project line threshold to the combined result for every module in `cpp/modules.txt`. Source-directory totals include headers. Each production CMake target also has a separate threshold for its translation units.

- **Isolation of internal modules.** CTest runs `core-module-boundaries`. The check maps migration objects to owners, parses the SQL literals of C++, the catalog queries, the view and function definitions, and checks private headers and backup sections. Control examples include `SELECT`, `JOIN`, a write, a name without a schema and a private view. In `task schema:check` the same owner registry is compared with the actual schemas of tables, views and functions after the migrations are applied. The PostgreSQL dependency catalog is checked for views that read foreign tables and for new foreign keys and triggers between module schemas. Dynamically built SQL needs a separate check in review. [Source and catalog check](../../tests/architecture/core_boundaries.py) · [PostgreSQL dependency check](../../tests/schema/module-dependencies.sql)
- **Disabling an extension.** Stop the connected detector. For cameras with the regular recording path, recording, manual search and playback continue. The last processed position of the detections is visible. A module permission that was granted and then revoked is rejected at the next request.
- **Alarm ownership.** Deliver one observation again after a lost acknowledgement. Check that there is one alarm and that its history is available to the operator while the source is stopped.
- **Moving a domain.** On the same command sequence, compare before and after the move the permissions, the results, the state and the recovery after a failure. For a domain with Event Sourcing, additionally compare the result of a repeated replay and the absence of external actions.
