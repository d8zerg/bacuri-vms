# ADR-015. Choosing and maintaining platform technologies

[Русская версия](../ru/adr/015-technology-lifecycle.md)

**Status** - Accepted.

**Context.** A site works without external internet, keeps the archive longer than one update cycle and talks to cameras of different generations. Servers, browsers, libraries and build tools receive fixes independently. A pinned version lets the build be repeated. Admission to a release needs a separate confirmation that the version is maintained and that an update keeps the product properties.

**Options.** Automatically moving to every new release opens new capabilities sooner but can change the ABI, the data format and the client behavior at once. Freezing all versions makes test repetition simpler but leaves known defects. Choosing a stable supported branch with controlled promotion of fixes lets the changes be checked on the same scenarios as the product.

**Decision.** All Bacuri deliveries and all development loops use current supported technologies. The rule covers product code, the UI Kit, protocols and adapters, data, runtimes, third-party modules, build images, generators, CI, tests, diagnostics, and installation and recovery tools. It also applies to the cluster, federation and SaaS when they are implemented.

| Selection criterion | What to present when adopting |
| --- | --- |
| Support and security | A stable release, an official source, a channel for fixes from the project or the distribution. For a branch with a published end of support, a migration path before that date is needed. For a library without a formal LTS, name the maintained release line and how to obtain a fix. A new dependency with unknown or discontinued support blocks adoption |
| Benefit for the product | Name the task and compare with the solution already in use by a property important for this task. For example, for a new broker, measure latency and repeats while a subscriber recovers under recording load. Assess the impact on site resources and the maintenance cost. Record a significant choice in the relevant ADR |
| Compatibility and origin | Name the affected profiles and the compatibility with data, APIs, hardware and tools. Check the license for the planned use and delivery. Pin the versions, revisions or digests of the resolved graph in the source manifests. Take transitive dependencies into account in the actual content of the build or delivery |
| Verifiability | Prepare a reproducible example and an automatic check through the regular boundary of the component. For a new language or browser feature, check the whole supported matrix. Pre-releases and experimental APIs can be explored in isolation. Including them in the regular stack requires a stable release and passing the same checks |

**Updates.** The owner of a subsystem reviews the version when a dependency is added, a security fix is released, a deprecation is announced, and before every release candidate. The default candidate is the current corrective release of the supported branch. For Debian, the package revision and the fixes backported by the distribution are taken into account. For PostgreSQL, the branch support policy and the migration notes are checked. For Node.js in the build images, a supported LTS branch compatible with the tools is chosen. [Debian security fixes](https://www.debian.org/security/faq) · [PostgreSQL versioning policy](https://www.postgresql.org/support/versioning/) · [Node.js release lines](https://nodejs.org/en/about/previous-releases)

An update keeps the difference in versions and content, the applicability of security advisories and the result of the affected automatic tests. A storage format change requires checking that previous data is read, migrated and recovered. A protocol change requires checking the compatibility of the supported clients and devices. A toolchain change is subject to the clean build and reproducibility checks. External information for the checks is prepared in the build environment and is available to the automation from a local snapshot. [C++ build](010-build-dependencies.md) · [Offline delivery](011-offline-delivery.md)

**Deprecation and exceptions.** After an API is declared deprecated, new calls use its supported replacement. For the remaining calls or a temporary delay of an update, record the component and the profile, the reason, the risk, the mitigation, the person responsible for the replacement, the migration task and the version or event that ends the exception. Check the end condition at every candidate. In the delivery and the release tools, the end of support requires replacing the component or confirmed maintenance by the supplier. For an old external device, the compatibility scope is limited to an adapter and a specific model or firmware. For open RTSP, the conditions of [ADR-012](012-camera-capabilities.md) apply.

**Verification of the first release.** In the core regression, compare the installed npm trees and the resolved Conan graphs with the lock files. Check the content of the product, build and test images by their actual layers, the host tool versions and the separate runtime branches. Keep a snapshot of the supplier information and the results of the comparison with the advisory database. A critical match by version requires an applicability analysis. A temporary measure needs a specific component, version, advisory, scope, owner, review date and a successful automatic check of the measure. A missing result, an expired exception or an outdated snapshot blocks the check. [Regression and evidence](../test-profile.md#core-regression)

**Consequences and review.** A release needs an inventory of the actual dependencies and time for regular qualification of updates. Review the policy when a fix channel disappears, a new profile cannot be checked on the target stand, or the support term requirements of the delivery change. Check the dependencies at build and regression time. On the signed kit, repeat the update and offline recovery checks. [Acceptance requirements](../quality.md#acceptance-requirements)
