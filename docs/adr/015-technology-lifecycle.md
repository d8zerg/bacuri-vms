# ADR-015. Выбор и сопровождение технологий платформы

**Статус** - Принято.

**Контекст.** Площадка работает без внешнего интернета, хранит архив дольше одного цикла обновления и взаимодействует с камерами разных поколений. При этом серверы, браузеры, библиотеки и инструменты сборки получают исправления независимо. Закреплённая версия позволяет повторить сборку. Для допуска к выпуску нужно отдельно подтвердить, что её сопровождают и что обновление сохраняет свойства продукта.

**Варианты.** Автоматический переход на каждый новый выпуск быстрее открывает новые возможности, но может одновременно изменить ABI, формат данных и поведение клиента. Замораживание всех версий упрощает повторение испытаний, но оставляет известные дефекты. Выбор стабильной поддерживаемой ветки с контролируемым продвижением исправлений позволяет проверить изменения на тех же сценариях, что и продукт.

**Решение.** Во всех поставках Bacuri и во всех контурах разработки применяются современные поддерживаемые технологии. Правило распространяется на продуктовый код, UI Kit, протоколы и адаптеры, данные, среды исполнения, сторонние модули, образы сборки, генераторы, CI, тесты, диагностику и средства установки и восстановления. Оно действует и для кластера, федерации и SaaS при их реализации.

| Критерий выбора | Что предъявить при принятии |
| --- | --- |
| Поддержка и безопасность | Стабильный выпуск, официальный источник, канал получения исправлений от проекта или дистрибутива. Для ветки с опубликованным окончанием поддержки нужен путь перехода до этого рубежа. Для библиотеки без формального LTS указывают сопровождаемую линию выпусков и способ получить исправление. Новая зависимость с неизвестной или прекращённой поддержкой блокирует принятие |
| Польза для продукта | Назвать задачу и сравнить с уже используемым решением по свойству, важному для этой задачи. Например, для нового брокера измерить задержку и повторы при восстановлении подписчика под нагрузкой записи. Оценить влияние на ресурсы площадки и стоимость сопровождения. Существенный выбор фиксировать в профильном ADR |
| Совместимость и происхождение | Указать затронутые профили, совместимость с данными, API, оборудованием и инструментами. Проверить лицензию для планируемого использования и поставки. Версии, ревизии или digest разрешённого графа закрепить в исходных манифестах. Транзитивные зависимости учитывать в фактическом составе сборки или поставки |
| Проверяемость | Подготовить воспроизводимый пример и автоматическую проверку через штатную границу компонента. Для новой возможности языка или браузера проверить всю поддерживаемую матрицу. Предварительные выпуски и экспериментальные API можно исследовать изолированно. Их включение в штатный стек требует стабильного выпуска и прохождения тех же проверок |

**Обновление.** Владелец подсистемы пересматривает версию при добавлении зависимости, выпуске исправления безопасности, объявлении об устаревании и перед каждым релиз-кандидатом. Кандидат по умолчанию - актуальный корректирующий выпуск поддерживаемой ветки. Для Debian учитывается ревизия пакета и перенесённые дистрибутивом исправления. Для PostgreSQL проверяются политика поддержки ветки и указания по миграции. Для Node.js в сборочных образах выбирается поддерживаемая LTS-ветка, совместимая с инструментами. [Исправления безопасности Debian](https://www.debian.org/security/faq) · [Политика версий PostgreSQL](https://www.postgresql.org/support/versioning/) · [Линии выпусков Node.js](https://nodejs.org/en/about/previous-releases)

При обновлении сохраняют разницу версий и состава, применимость бюллетеней безопасности и результат затронутых автотестов. Изменение формата хранения требует проверки чтения прежних данных, миграции и восстановления. Изменение протокола требует проверки совместимости поддерживаемых клиентов и устройств. Для смены инструментария действуют проверки чистой сборки и воспроизводимости. Внешние сведения для проверки подготавливаются в среде сборки и доступны автоматике из локального снимка. [Сборка C++](010-build-dependencies.md) · [Автономная поставка](011-offline-delivery.md)

**Устаревание и исключения.** После объявления API устаревшим новые вызовы используют его поддерживаемую замену. Для оставшихся вызовов или временной задержки обновления фиксируют компонент и профиль, причину, риск, меру снижения, ответственного за замену, задачу миграции и версию либо событие окончания исключения. При каждом кандидате проверяют условие окончания. В поставке и инструментах выпуска прекращение поддержки требует замены компонента или подтверждённого сопровождения поставщиком. Для старого внешнего устройства область совместимости ограничивают адаптером и конкретной моделью или прошивкой. Для открытого RTSP сохраняются условия [ADR-012](012-camera-capabilities.md).

**Проверка в Basic.** В регрессии ядра сопоставить установленные деревья npm и разрешённые графы Conan с lock-файлами. Проверить состав образов продукта, сборки и тестов по фактическим слоям, версии инструментов хоста и отдельные ветки сред исполнения. Сохранять снимок сведений поставщиков и результаты сопоставления с базой бюллетеней. Критическое совпадение по версии требует разбора применимости. Для временной меры нужны конкретные компонент, версия, уведомление, область, владелец, срок пересмотра и успешная автоматическая проверка меры. Отсутствующий результат, истёкшее исключение или устаревший снимок блокируют проверку. [Регрессия и доказательства](../basic-test-profile.md#регрессия-ядра)

**Последствия и пересмотр.** Для выпуска нужен учёт фактических зависимостей и времени на регулярную квалификацию обновлений. Пересмотреть политику, если исчез канал исправлений, новый профиль нельзя проверить на целевом стенде или требования к сроку поддержки поставки изменились. В Basic исходный состав и автоматизацию проверяют в 0.3 и 5.3, обновление и автономное восстановление в 8.1-8.2, допуск конкретного комплекта в 8.3.
