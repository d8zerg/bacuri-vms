# План разработки настольного клиента Bacuri VMS

**Статус плана** - Готово к приёмке.

Цель выпуска - рабочее место администратора и оператора для заявленных профилей Bacuri VMS на Windows, Linux и macOS. На каждой системе доступны все рабочие сценарии веб-клиента, а также многомониторный пост, видеостена на выходах рабочей станции, синхронное расследование по нескольким камерам, физический пульт и автономный просмотр проверенных экспортов. Статус реализации каждого шага определяется отдельно по его результату и испытаниям.

Сверх паритета настольный клиент отличается свойствами профессионального инструмента оператора: показ видео без копирования кадра через системную память, синхронный архив по всем камерам раскладки без чёрных кадров, PTZ прямым действием в кадре, управление с клавиатуры и пульта без поиска кнопок, переход в соседнюю камеру по топологии площадки и мягкая деградация при перегрузке и потере связи. Каждое свойство задаётся измеримым бюджетом из 6.1 и проверяется в выпускном прогоне. Без них соответствующие наложения, полоса активности, проверка правила, предложенные маски и предложения пути скрыты, остальные сценарии работают без изменений. До готовности серверных шагов клиент развивается на эталонном наборе метаданных той же схемы. Функцию принимают только после совместного прогона с сервером, где соответствующий шаг плана аналитики готов к приёмке. [ADR-021](adr/021-video-analytics.md)

Клиент управляет VMS через публичные операции. Первичная установка узла, выдача кода доверенной привязки, аварийное восстановление администратора, резервное копирование и обновление сервера проходят по процедурам на узле. На посту должны быть видны результат переключения и необходимость повторного входа. Для внешнего события или перехода от интеграционного потребителя используется контракт из шага 1.3 Manager с повторной проверкой доступа к видео. СКУД, PSIM и другие внешние системы подключаются по необходимости. Все штатные задания VMS проходят при отключённых внешних системах. ## Принципы рабочего места оператора

| Принцип | Правило |
| --- | --- |
| Правдивость изображения | Видео показывается целиком, в исходном цвете и без декоративных эффектов: без обрезки кадра для заполнения ячейки, обесцвечивания, размытия, шума и наложенных линий. Плотная укладка ячеек с разным соотношением сторон допускается только без потери площади кадра. Маски и права на изображение применяются одинаково во всех окнах и миниатюрах |
| Стабильность раскладки | Ячейка камеры не меняет позицию без действия оператора. Тревога и разворот камеры используют выделенный слот или отдельный экран и не сдвигают остальные ячейки под курсором. Возврат восстанавливает прежнюю раскладку и фокус |
| Приоритет ввода | Отклик на ввод, перемещение по шкале и анимации интерфейса не ждут сети и декодирования. При перегрузке сначала снижается частота кадров и профиль неактивных миниатюр, затем камеры в фокусе. Каждое снижение видно в ячейке и в диагностике |
| Цвет как сигнал | Оформление интерфейса монохромное, цвет закреплён за состояниями: тревога, выделение, запись, отказ. Состояние дублируется формой или текстом и проверяется на различимость при нарушениях цветового зрения. Цифры таймкодов, координат и телеметрии имеют одинаковую ширину |
| Движение по делу | Переходы короткие, не задерживают показ кадра и отключаются системной настройкой уменьшения движения или параметром клиента. Звуковые отклики интерфейса по умолчанию выключены |
| Действие без поиска | Каждое частое действие доступно с клавиатуры, из командной строки, контекстного меню в кадре и с пульта. Видимые кнопки остаются для обнаружения функций и для доступности |
| Измеримость | Свойство поставки подтверждается числом из 6.1 на конфигурации из паспорта 0.2. Свойство без замера не заявляется |

## Этап 0. Зафиксировать объём и конфигурации испытаний

### Шаг 0.1. Реестр сценариев и контрактов

Сопоставить маршруты мониторинга, камер, карт и журнала, отдельные страницы эфира, архива и тревог, действия API и административной консоли со строками матрицы. Для каждого сценария записать роль, предусловие, действие, наблюдаемый результат, отказ, шаг реализации и тест. Сверить каждую применимую функцию реестра полного выпуска платформы с таблицей выше. Для сценария указать версию публичного контракта, тип установки, проверяемые ОС и материал приёмки. Возможность, которую обязательный серверный контракт ещё не предоставляет, остаётся открытой до совместного прогона. Клиент использует опубликованные серверные операции. Дополнительные требования к контрактам передаются владельцу соответствующего шага платформы. [Реестр платформы](release-register.md) · [Общий контракт входа](release-register.md#вход-через-площадку)

**Приёмка**

У каждой функции есть владелец и критерий паритета, у каждого расширения - версия API, проверка доступности возможности и ожидаемое поведение при подключении к прежнему серверу.

**Результат** - Готово к приёмке.

Реестр паритета [desktop/parity.yaml](../desktop/parity.yaml) сопоставляет 17 функций реестра выпуска с 65 сценариями настольного клиента. Каждый сценарий содержит роль, предусловие, действие, результат, отказ, шаги клиента и платформы, операции API, раздел веб-клиента, типы установки, ОС, тест и материал приёмки. Отдельные страницы эфира, архива и тревог удалены из веб-клиента, их функции входят в раздел «Мониторинг». Тринадцать расширений сверх веб-клиента указывают требуемый контракт, признак доступности и поведение с прежним сервером. Одиннадцать требований к контрактам переданы шагам платформы и аналитики: вход настольного клиента по одноразовому коду, записи передачи смены, модель этажей с калиброванными камерами, предсказание следующей камеры, синопсис, список возможностей площадки в сеансе, непрерывное движение PTZ, опорные кадры, метаданные анализа, ручные связи камер и операции Manager. Команды консоли сопоставлены с операциями API либо отнесены к процедурам узла.

`task desktop:parity` проверяет, что каждая из 95 операций OpenAPI, каждый раздел веб-клиента и каждое действие консоли покрыты, и сравнивает отпечатки OpenAPI, схемы WSS и каталога ошибок с ревизией сверки (API 1.6.0). После изменения контракта проверка требует повторной сверки, `task desktop:parity:accept` фиксирует новую ревизию. Все сценарии открыты до реализации соответствующих шагов.

### Шаг 0.2. Паспорт рабочего места

Зафиксировать редакции и архитектуры трёх ОС, GPU и драйверы, число и разрешение мониторов, масштаб интерфейса, модели пульта и WebAuthn-ключа. Для Linux указать оконную систему. ## Этап 3. Реализовать камеры, архив и администрирование

Работы начинаются после действующего рабочего места из этапа 2.

### Шаг 3.1. Ввод и замена камеры

Реализовать обнаружение через сервер, выбор ONVIF-профилей, ручной ввод, проверку адресов и сертификата камеры, диагностику ошибок потока, создание и изменение с ключом идемпотентности и версией ETag по контракту. Различать желаемую и применённую конфигурацию. При замене сохранять точку, доступ к прежнему интервалу и возможность открыть новую запись.

**Приёмка**

Выполнить обнаружение, ручной ввод, ошибку и повтор, конфликт двух администраторов и замену. Подтверждение доступно только после первого кадра нового полного блока нужной точки. После повторного входа в десктоп и из веб-клиента открыть ту же точку, сверить применённую конфигурацию и кадры до и после замены. [Мастер и совместимость](rtsp-compatibility.md#мастер-подключения)

### Шаг 3.2. Эфир, PTZ и поиск архива

Реализовать выбор точки, состояние связи и записи, команды по возможностям камеры, поиск с курсором, шкалу времени, выбор интервала, воспроизведение и паузу. Интервалы считать в UTC с исключённой правой границей, показывать локальное время с поясом, раздельно отображать пропуск, ожидание каталога, неопределённое время и недоступный носитель. Через API платформы 9.3 подключить фокус, предустановки, патрули, подсветку, чтение тревожных входов и управление выходами камеры.

PTZ управляется прямым действием в кадре. Перетаскивание из любой точки кадра поворачивает камеру со скоростью, пропорциональной смещению, отпускание кнопки останавливает движение. Выделение прямоугольника с Shift наводит и приближает камеру на выбранную область, колесо мыши управляет зумом. Действующий контракт PTZ передаёт только дискретные направления. Для непрерывного движения с вектором скорости, ограниченного по времени, и наведения на область кадра передать требования к контракту в шаг 9.3 платформы. До расширения контракта перетаскивание отображается на ближайшее направление, а наведение на область скрыто. Возможности камеры определяют доступные режимы.

**Мягкая деградация**

Профиль выбирается по размеру ячейки в физических пикселях: миниатюры получают дополнительный поток, развёрнутая камера - основной. При потере пакетов, росте очереди декодера или нехватке квоты клиент без участия оператора переходит на дополнительный поток, снижает частоту кадров неактивных ячеек и возвращает профиль после стабилизации с задержкой против колебаний. При потере связи ячейка оставляет последний правильный кадр в приглушённом виде с отметкой «нет связи» и временем с момента потери, без искажения изображения. По метке времени последнего кадра оператор отличает устаревшее изображение от живого. Переход между эфиром и архивом той же точки выполняется без чёрного кадра: прежний кадр остаётся на экране до первого правильного кадра нового источника.

**Приёмка мягкой деградации**

Ограничить канал рабочей станции, сбросить пакеты и отключить камеру во время просмотра. Переходы профиля видны в ячейке и в диагностике, не вызывают чёрного кадра и не изменяют раскладку. Отметка «нет связи» появляется в пределах заданного в 6.1 времени и снимается при первом новом кадре. Переход эфир -> архив -> эфир не показывает пустой ячейки.

Для вызова предустановок и поддержки зума использовать возможности камеры из контракта шага 9.3 основного плана. При соединении с более ранним сервером показывать заявленные им направления и остановку. Ось джойстика передаёт непрерывную скорость, если контракт 9.3 её поддерживает. На программируемой клавишной панели изображения кнопок меняются по выбранной камере и её возможностям. Назначения хранятся в реестре команд 2.4 и переносятся между постами вместе с профилем пользователя.

**Приёмка**

Проверить реальный джойстик, колесо и камеру каждого заявленного профиля. Отпускание оси, потеря фокуса, смена камеры и отключение пульта завершают движение в пределах ограничения команды. Для недоступной предустановки видна причина. Эквивалентные команды доступны с клавиатуры. [Контракт PTZ](../contracts/v1/openapi.yaml)

### Шаг 5.6. Дело расследования, защита и выдача материалов

После 5.3 и 5.4 реализовать рабочий сценарий платформы 10.3-10.5. Оператор сохраняет закладки и интервалы разных камер в дело, указывает примечание, ответственного и основание защиты. При повторном открытии видны фактический источник, статус удержания и доступность копии. Для передачи материала выбирает разрешённый вариант экспорта и видит применяемые маски и звуковые дорожки.

**Приёмка**

Сохранить дело на одном посту и открыть на другом с правами получателя. При действующем удержании запустить очистку и сверить кадры. На машине без сети проверить подпись, точку, интервал, маски и звук готового комплекта. Попытки выдать оригинал или снять удержание без нужного права отражены в аудите. Снятие защиты одного дела учитывает другие действующие удержания. [Платформа, расследование и экспорт](devplan.md#шаг-105-материалы-расследования-и-экспорт)

### Шаг 5.7. Пространственная навигация между камерами

После 4.2, 5.2 и 5.3 использовать размещение, ориентацию и секторы обзора камер из модуля карт. Для каждой камеры клиент вычисляет соседей по направлениям кадра. При наведении на край кадра появляется указатель соседней камеры, клик или клавиша направления переводят ячейку на неё, в эфире или в архиве на том же моменте UTC. Администратор может уточнить соседей вручную, если геометрия плана не отражает реальные проходы. Хранение ручных связей передаётся требованием к контракту карт шага 7.1 платформы. Клик по камере на карте открывает её в ячейке с переходом от сектора к кадру. При наведении на точку карты рядом с курсором показывается предпросмотр эфира с учётом прав и квоты. Если площадка вычисляет треки на плане и кандидатов продолжения пути (этап 4 плана аналитики), клиент показывает путь объекта на плане и упорядочивает соседние камеры по оценке кандидата. Решение о переходе принимает оператор.

**Приёмка**

На плане из четырёх камер проследить проход человека по эталонной записи только переходами по краям кадра, без дерева и поиска. Переход сохраняет момент архива и раскладку. Камера без размещения не предлагает соседей и не ломает переход. Ручная правка соседей видна на другом посту. Предпросмотр на карте освобождает сеанс после ухода курсора.

### Шаг 5.8. Восстановление поста и передача смены

После 4.1, 5.2 и 5.3 сохранять состояние поста: раскладки на экранах, развёрнутую камеру, открытые тревоги, позицию и масштаб архива, открытое дело и фокус. После перезапуска клиента, сбоя графического устройства или повторного входа пост возвращается в то же состояние с повторной проверкой прав. При смене оператора клиент формирует сводку смены по журналу тревог и действий: принятые, закрытые и открытые тревоги, поручения, закладки, начатые экспорты и камеры без связи. Сдающий оператор добавляет примечание, принимающий подтверждает приём. Сводка, примечание и подтверждение хранятся на площадке и видны в журнале. Хранение записей передачи смены передаётся требованием к контракту шага 7.2 платформы. Каждый оператор входит под своей учётной записью, состояние поста восстанавливается в пределах его прав.

**Приёмка**

Принудительно завершить клиент во время просмотра архива и обработки тревоги, перезапустить. Пост возвращает раскладки на свои экраны, позицию архива и карточку тревоги без повторного поиска. Проверить смену оператора: принимающий видит открытые тревоги, примечание и камеры без связи, подтверждение отражено в журнале. Объект, недоступный принимающему оператору, не попадает в его сводку и не восстанавливается. Измерить время от запуска до восстановленного поста.

### Шаг 5.9. Сводка пропущенного

После 5.3 и 5.8 отслеживать, какие камеры и интервалы оператор фактически видел: камера на экране, не перекрыта и не свёрнута. Когда оператор возвращается после отсутствия, обработки тревоги или работы в архиве, клиент показывает сводку непросмотренного интервала по камерам раскладки: тревоги, всплески активности и события камер в виде ленты ключевых кадров с переходом к точному моменту архива. Ключевые кадры берутся из индекса активности и сводки интервала сервиса аналитики (шаги 2.1 и 5.2 плана аналитики). Без аналитики сводка содержит тревоги и события камер. Учёт просмотренного хранится на посту и не используется для оценки работы оператора.

**Приёмка**

На эталонной записи с известными эпизодами переключить оператора на тревогу на заданное время. Сводка содержит все эпизоды непросмотренных камер и не содержит интервалов, которые были на экране. Переход из сводки открывает точный кадр. На площадке без аналитики сводка строится из тревог и событий камер. Измерить время построения сводки за час отсутствия по 16 камерам.

### Шаг 5.10. Режим одной задачи

После 4.1, 5.2 и 5.7 при принятии тревоги переключать рабочий экран в режим задачи: камера тревоги с повтором момента, соседние камеры по топологии, карточка с действиями и регламентом площадки. Видеостена на других мониторах продолжает работу, новые тревоги поступают в очередь со счётчиком и не перехватывают фокус. Критическая тревога более высокого приоритета показывается отдельным уведомлением с выбором оператора. Закрытие, передача или отложение тревоги возвращает прежнюю раскладку и фокус. Режим включается настройкой поста и отключается оператором.

**Приёмка**

Во время обработки тревоги создать ещё три тревоги, одну с более высоким приоритетом. Фокус ввода остаётся в текущей задаче, счётчик очереди растёт, уведомление о высоком приоритете требует решения оператора. После закрытия тревоги раскладка и фокус совпадают с исходными. Сравнить время обработки тревоги и число ошибок с режимом и без него на одном наборе заданий.

### Шаг 5.11. Пространственная видеостена

После 4.2, 5.2 и 5.7 добавить вид здания: этажи из модуля карт в 2.5D с камерами по калибровке (шаг 4.5 плана аналитики). Живое видео и архив проецируются на плоскость пола в зоне обзора каждой камеры, перекрывающиеся камеры показываются вместе. Оператор перемещается по зданию колесом, клавишами и джойстиком, клик по проекции открывает камеру в ячейке с переходом от сцены к кадру. Проекция - вид для ориентации: кадр камеры остаётся доступен без искажений одним действием. Видеопоток проекции выбирается по видимому размеру, невидимые камеры не получают поток. Отрисовка идёт через Qt Quick 3D или собственный узел RHI с текстурами кадров без копирования. Модель этажей передаётся требованием к контракту карт шага 7.1 платформы.

**Приёмка**

На плане из четырёх калиброванных камер проецированный кадр совпадает с планом на контрольных точках. Проход человека виден непрерывно на стыке двух камер. Переход из сцены к кадру и обратно сохраняет момент архива. Время кадра интерфейса и число потоков при облёте этажа укладываются в бюджет 6.1. Без калибровки камера показывается маркером с сектором, без проекции.

### Шаг 5.12. Синопсис интервала

После 5.3 открывать синопсис выбранной камеры и интервала: объекты интервала на одном фоновом кадре с временными метками, фильтр по классу, зоне и направлению, клик по объекту открывает точный кадр архива. Вид всегда помечен как синопсис и не используется как доказательство. Данные синопсиса строит сервис аналитики (шаг 5.3 плана аналитики).

**Приёмка**

На эталонном часе записи оператор находит все известные эпизоды через синопсис. Измерить время поиска эпизода по синопсису и по обычной перемотке на одном наборе заданий. Площадка без аналитики не показывает синопсис.

### Шаг 5.13. Заранее открытая следующая камера

После 5.7 и 5.10 при сопровождении объекта показывать предсказанные следующие камеры (шаг 4.4 плана аналитики) в ленте рядом с текущей до выхода объекта из кадра. Камеры с высокой оценкой заранее получают поток в пределах квоты, переход на них не требует ожидания первого кадра. Предсказание не меняет раскладку стены и не перехватывает фокус. Без аналитики лента показывает соседей по топологии.

**Приёмка**

На эталонных переходах измерить время от выхода объекта из кадра до кадра на следующей камере с предсказанием и без него. Квота сеансов поста не превышается, отменённое предсказание освобождает поток.

После завершения функциональных шагов прервать сеть, перезапустить ядро и медиавыдачу, усыпить и разбудить рабочую станцию, отключить монитор и пульт, отозвать права при эфире, паузе архива и экспорте. Повторить при полной загрузке. Сбросить графический драйвер и вызвать потерю графического устройства: клиент восстанавливает отрисовку без перезапуска, сеансов и потери раскладки. Потерять связь с камерой во время события, восстановить её и прервать догрузку. Проверить на шкале границы исходной записи, догруженного участка и оставшегося пропуска по серверному каталогу и эталонным кадрам. При переключении рекордера сверить показанный разрыв и время восстановления с пределами паспорта выбранной топологии.

**Приёмка**

Получение активного медиа прекращается в пределах серверного бюджета 5 с после отзыва, чувствительный кадр и данные отозванной точки убираются во всех окнах. Восстановление связи заново проверяет права. Подтверждённые команды не дублируются, частичная выгрузка не открывается как проверенная. В списках, миниатюрах, активных окнах и при смене профиля соблюдаются действующие маски и права на звук. Сохранить журнал событий и показатели клиентской и серверной стороны.

## Этап 7. Поставить и принять релиз-кандидат

### Шаг 7.1. Автономные пакеты

Собрать устанавливаемый пакет для каждой целевой системы. Предлагаемые форматы - MSI для Windows, DEB для базовой конфигурации Linux и подписанное приложение в DMG для macOS. Закрепить версии, лицензии и состав поставки, подпись и проверку целостности, штатный способ установки, обновления, отката и удаления. Проверить миграцию настроек и совместимость выпусков клиента и сервера.

**Приёмка**

На чистой целевой ОС без SDK и внешней сети установить подписанный комплект, подключиться к локальному серверу, открыть карту, эфир и архив. На чистой установке, после обновления и отката сверить версию справки с версией клиента и найти статью без подключения к серверу. Прервать обновление, восстановить рабочую версию, проверить раскладки и сохранённые экспорты. Пакет с нарушенной подписью отклоняется. [Автономная поставка платформы](adr/011-offline-delivery.md)

### Шаг 7.2. Выпускной прогон

На одних и тех же пакетах 7.1 и идентифицированной сборке сервера выполнить реестр 0.1 по обязательным профилям из 8.3 основного плана. Перед приёмкой полного выпуска сверить хеш сервера с отчётом квалификации платформы 12.1. Проверить сквозную работу изолированной площадки без внешних интеграций. На установленных пакетах повторить проверки помощи из 2.3, включая переход из ошибки к одной и той же статье на русском и английском, поиск по симптому на каждом языке и по коду при потере связи с сервером. На Windows, Linux и macOS проверить обе локали после чистой установки и сохранение выбранного языка после перезапуска и обновления. Для поставки с Manager повторить переходы между постами при потере узла и центра по [профилям Manager](devplan-manager.md#установки). На каждой целевой ОС пройти все строки паритета и настольные сценарии, испытания 6.1 и 6.2, включая физические мониторы, камеру, пульт и ключ. Собрать матрицу «версия клиента и сервера / ОС / GPU и драйвер / устройства / сценарий / результат», хеши, снимки, журналы и измерения. Обязательная конфигурация с пропуском или отклонением остаётся открытой. Исправленный комплект получает новый прогон затронутых сценариев и полную выпускную проверку.

На каждой целевой ОС пройти локальный вход на площадке без провайдера. В профиле с Keycloak войти в веб-клиент и открыть настольный клиент через тот же системный браузер. При действующей сессии провайдера и политике единого входа обе сессии Bacuri должны открыться с одной корпоративной учётной записью без повторного ввода пароля. Сверить доступ к камерам, PTZ, архиву и экспорту. Отозвать право просмотра в Bacuri и проверить прекращение активной выдачи в обоих клиентах в пределах 5 с. При недоступности Keycloak повторить локальный вход администратора с WebAuthn.

### Шаг 7.3. Приёмка администратора и оператора

После 7.2 на тех же пакетах выполнить самостоятельные задания. Администратор подключает камеру и подтверждает первую запись за 5 минут, проверяет прежний архив после замены и выдаёт ограниченный доступ. Оператор оценивает тревогу и возвращается к исходной карточке за 2 минуты, затем ведёт наблюдение на одном мониторе и расследование на другом, выбирает нужные эпизоды и проверяет экспорт без сети. Основу замеров дают действующие задания первого использования. Для многокамерного расследования фиксировать время от выдачи задания до первого правильного кадра, затем до открытия и автономной проверки разрешённой копии. Использовать эталон с известным пропуском и двумя похожими эпизодами. До испытания закрепить пределы в паспорте с учётом шага 8.3 платформы.

**Приёмка**

В заданиях смены оператор принимает пост с открытыми тревогами по сводке и примечанию, возвращается после перерыва и находит по сводке пропущенный эпизод, обрабатывает тревогу в режиме одной задачи при поступлении новых. Фиксировать время возврата к работе, долю найденных эпизодов, время и ошибки обработки.

В отдельном задании оператор по сообщению о занятой PTZ-камере открывает статью, объясняет причину и возвращается к наблюдению на том же посту. Зафиксировать, нашёл ли он решение без подсказки наблюдателя.

Фиксировать время, правильность точки и интервала, подсказки и критические ошибки для каждого задания. Для количественного сравнения с другим VMS-клиентом использовать одинаковые камеры, архив, цель, права и оборудование, чередовать порядок клиентов для участников. Публиковать долю самостоятельных завершений, время и ошибки вместе с числом попыток и версиями клиентов. Принять релиз можно после прохождения всех обязательных конфигураций, самостоятельного выполнения заданий и устранения критических ошибок. [Протокол первого использования](ui.md#проверка-первого-использования)

## Порядок выполнения и учёт результатов

Начать с шага 0.1 и паспорта поста 0.2. Опубликованный контракт позволяет вести клиентский сценарий независимо от остальных функций платформы. Прототипы графики и входа можно вести параллельно. После общего клиента работа над камерами, администрированием, картами и медиа может идти независимо в пределах указанных зависимостей. Ранний сквозной результат - вход -> выбор разрешённой точки -> эфир -> архив -> отзыв доступа. Прототип 1.1 с замерами копирования кадров и изоляции ввода определяет архитектуру отрисовки до начала этапа 2. Требования к расширению контрактов PTZ, опорных кадров, метаданных активности и связей камер передаются в шаги платформы в начале соответствующих шагов клиента, чтобы прямое управление и синхронный архив не ждали серверных изменений в конце. Далее проверить результаты этапов 3 и 4, пройти многомониторное дежурство, синхронный архив, пространственную навигацию, сохранение дела, восстановление поста и передачу смены, сводку пропущенного и режим одной задачи в этапе 5. Фирменные функции 5.11-5.13 - пространственная видеостена, синопсис и заранее открытая следующая камера - начинаются после готовности калибровки, предсказания и синопсиса в плане аналитики и сравниваются с обычной работой на одних заданиях. Шаги 5.8-5.10 проверяются и на людях в 7.3: время возврата к работе после перерыва, доля найденных пропущенных эпизодов, время и ошибки обработки тревоги. Полный паритет и настольные функции подтверждает 7.2 на трёх ОС, самостоятельную работу людей на тех же пакетах - 7.3.

Для каждого шага сохранять версию компонентов, условия, команду или протокол выполнения, фактический результат и ссылку на материалы. Статус шага `Готово к приёмке` ставится после его проверок, `Принято` - после сверки материалов с критериями. До появления материалов шаг остаётся задачей плана. Доказательства программного стенда и результаты целевых машин фиксируются раздельно.
