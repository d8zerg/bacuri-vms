# План разработки Bacuri VMS Client для Linux

**Статус плана** - Готово к приёмке.

Этот план охватывает разработку, сборку и приёмку рабочего места администратора и оператора только на Linux. Поддержка Windows и macOS вынесена в [отдельный план дополнительных платформ](ru/devplan-desktop-platforms.md).

Для заявленных профилей Bacuri VMS в состав Linux-клиента входят все рабочие сценарии веб-клиента, а также многомониторный пост, видеостена на выходах рабочей станции, синхронное расследование по нескольким камерам, физический пульт и автономный просмотр проверенных экспортов. Статус реализации каждого шага определяется отдельно по его результату и испытаниям.

Сверх паритета настольный клиент отличается свойствами профессионального инструмента оператора: показ видео без копирования кадра через системную память, синхронный архив по всем камерам раскладки без чёрных кадров, PTZ прямым действием в кадре, управление с клавиатуры и пульта без поиска кнопок, переход в соседнюю камеру по топологии площадки и мягкая деградация при перегрузке и потере связи. Каждое свойство задаётся измеримым бюджетом из 6.1 и проверяется в выпускном прогоне. Без них соответствующие наложения, полоса активности, проверка правила, предложенные маски и предложения пути скрыты, остальные сценарии работают без изменений. До готовности серверных шагов клиент развивается на эталонном наборе метаданных той же схемы. Функцию принимают только после совместного прогона с сервером, где соответствующий шаг плана аналитики готов к приёмке. [ADR-021](adr/021-video-analytics.md)

Клиент управляет VMS через публичные операции. Первичная установка узла, выдача кода доверенной привязки, аварийное восстановление администратора, резервное копирование и обновление сервера проходят по процедурам на узле. На посту должны быть видны результат переключения и необходимость повторного входа. Для внешнего события или перехода от интеграционного потребителя используется контракт из шага 1.3 Manager с повторной проверкой доступа к видео. СКУД, PSIM и другие внешние системы подключаются по необходимости. Все штатные задания VMS проходят при отключённых внешних системах. ## Принципы рабочего места оператора

| Принцип | Правило |
| --- | --- |
| Правдивость изображения | Видео показывается целиком, в исходном цвете и без декоративных эффектов: без обрезки кадра для заполнения ячейки, обесцвечивания, размытия, шума и наложенных линий. Плотная укладка ячеек с разным соотношением сторон допускается только без потери площади кадра. Маски и права на изображение применяются одинаково во всех окнах и миниатюрах |
| Стабильность раскладки | Ячейка камеры не меняет позицию без действия оператора. Тревога и разворот камеры используют выделенный слот или отдельный экран и не сдвигают остальные ячейки под курсором. Возврат восстанавливает прежнюю раскладку и фокус |
| Приоритет ввода | Отклик на ввод, перемещение по шкале и анимации интерфейса не ждут сети и декодирования. При перегрузке сначала снижается частота кадров и профиль неактивных миниатюр, затем камеры в фокусе. Каждое снижение видно в ячейке и в диагностике |
| Цвет как сигнал | Оформление интерфейса монохромное, цвет закреплён за состояниями: тревога, выделение, запись, отказ. Состояние дублируется формой или текстом и проверяется на различимость при нарушениях цветового зрения. Цифры таймкодов, координат и телеметрии имеют одинаковую ширину |
| Движение по делу | Переходы короткие, не задерживают показ кадра и отключаются системной настройкой уменьшения движения или параметром клиента. Звуковые отклики интерфейса по умолчанию выключены |
| Действие без поиска | Каждое частое действие доступно с клавиатуры, из командной строки, контекстного меню в кадре и с пульта. Видимые кнопки остаются для обнаружения функций и для доступности |
| Измеримость | Свойство поставки подтверждается числом из 6.1 на конфигурации из паспорта 0.2. Свойство без замера не заявляется |

## Этап 0. Зафиксировать объём и конфигурации испытаний

### Шаг 0.1. Реестр сценариев и контрактов

Сопоставить маршруты мониторинга, камер, карт и журнала, отдельные страницы эфира, архива и тревог, действия API и административной консоли со строками матрицы. Для каждого сценария записать роль, предусловие, действие, наблюдаемый результат, отказ, шаг реализации и тест. Сверить каждую применимую функцию реестра полного выпуска платформы с таблицей выше. Для сценария указать версию публичного контракта, тип установки, целевую ОС Linux и материал приёмки. Возможность, которую обязательный серверный контракт ещё не предоставляет, остаётся открытой до совместного прогона. Клиент использует опубликованные серверные операции. Дополнительные требования к контрактам передаются владельцу соответствующего шага платформы. [Реестр платформы](release-register.md) · [Общий контракт входа](release-register.md#вход-через-площадку)

**Приёмка**

У каждой функции есть владелец и критерий паритета, у каждого расширения - версия API, проверка доступности возможности и ожидаемое поведение при подключении к прежнему серверу.

**Результат** - Готово к приёмке.

Реестр паритета [desktop/parity.yaml](../desktop/parity.yaml) сопоставляет 17 функций реестра выпуска с 67 сценариями Linux-клиента. Каждый сценарий содержит роль, предусловие, действие, результат, отказ, шаги клиента и платформы, операции API, раздел веб-клиента, типы установки, целевую ОС Linux, тест и материал приёмки. Отдельные страницы эфира, архива и тревог удалены из веб-клиента, их функции входят в раздел «Мониторинг». Пятнадцать расширений сверх веб-клиента указывают требуемый контракт, признак доступности и поведение с прежним сервером. Реестр включает 13 требований к контрактам платформы, аналитики и Manager: вход настольного клиента по одноразовому коду, записи передачи смены, модель этажей с калиброванными камерами, предсказание следующей камеры, синопсис, список возможностей площадки в сеансе, непрерывное движение PTZ, опорные кадры, метаданные анализа, ручные связи камер, операции Manager, адреса узлов площадки и допуск к аварийному эфиру. Команды консоли сопоставлены с операциями API либо отнесены к процедурам узла.

`task desktop:parity` проверяет, что каждая из 97 операций OpenAPI, каждый раздел веб-клиента и каждое действие консоли покрыты, и сравнивает отпечатки OpenAPI, схемы WSS и каталога ошибок с ревизией сверки (API 1.7.0). После изменения контракта проверка требует повторной сверки, `task desktop:parity:accept` фиксирует новую ревизию. Все сценарии открыты до реализации соответствующих шагов.

### Шаг 1.2. Доверенный вход

На Linux-посту проверить вход оператора и полный цикл регистрации и входа администратора с WebAuthn на локальной площадке без внешнего интернета. **Приёмка**

### Шаг 5.1. Основной поток для выбранной камеры

После 2.2 и 3.2 подключить согласование профиля через публичный API шага 9.4 основного плана. Сейчас основной поток идёт в архив, дополнительный - в эфир. При выборе качества показывать фактический профиль, кодек камеры и кодек выдачи. Учитывать серверные квоты и права на изображение с маской и звук.

**Приёмка**

На камере с основным H.265 Main и дополнительным H.264 развернуть ячейку и подтвердить смену профиля по декодированному кадру, кодеку и разрешению. Сменить кодек камеры во время записи, открыть интервалы по обе стороны границы и проверить первый правильный кадр после перемотки. Повторить с доступным аппаратным ускорением и в заявленном программном режиме. При недоступном основном потоке показать фактически выбранный профиль. Сверить контрольную запись при переключениях и перегрузке зрителя. [Действующее разделение потоков](adr/005-media.md)

**Мягкая деградация**

Профиль выбирается по размеру ячейки в физических пикселях: миниатюры получают дополнительный поток, развёрнутая камера - основной. При потере пакетов, росте очереди декодера или нехватке квоты клиент без участия оператора переходит на дополнительный поток, снижает частоту кадров неактивных ячеек и возвращает профиль после стабилизации с задержкой против колебаний. При потере связи ячейка оставляет последний правильный кадр в приглушённом виде с отметкой «нет связи» и временем с момента потери, без искажения изображения. По метке времени последнего кадра оператор отличает устаревшее изображение от живого. Переход между эфиром и архивом той же точки выполняется без чёрного кадра: прежний кадр остаётся на экране до первого правильного кадра нового источника.

**Приёмка мягкой деградации**

Ограничить канал рабочей станции, сбросить пакеты и отключить камеру во время просмотра. Переходы профиля видны в ячейке и в диагностике, не вызывают чёрного кадра и не изменяют раскладку. Отметка «нет связи» появляется в пределах заданного в 6.1 времени и снимается при первом новом кадре. Переход эфир -> архив -> эфир не показывает пустой ячейки.

### Шаг 5.2. Раскладки, несколько мониторов и видеостена

После 5.1 реализовать сетки, перенос камеры и окна, разворот на выбранный экран, полноэкранную стену, сохранение и восстановление именованных раскладок. Личные и общие раскладки хранить через API площадки с проверкой владельца и права редактирования. Привязки окон к физическим дисплеям хранить на посту. Разделять подписку одной камеры между окнами при совпадающем профиле. Учитывать DPI, перестановку и отключение дисплея. Раскладку восстанавливать после входа с актуальными правами.

Кроме фиксированных сеток доступна укладка ячеек по соотношению сторон камер: 16:9, вертикальный коридорный кадр и панорама размещаются без обрезки и с минимальными полями. Укладка вычисляется при изменении раскладки и сохраняется вместе с ней, а не пересчитывается при каждом событии. Разворот камеры по клику увеличивает её в выделенной области экрана, остальные камеры остаются видимыми лентой миниатюр в постоянном порядке. Тревожный слот раскладки показывает камеру сработавшего события и не сдвигает остальные ячейки. Одна подписка на камеру обслуживает все ячейки и окна с совместимым профилем.

Сетки приложения строятся на общей шкале времени модуля `media` из шага 1.1. Измерения измерительного стенда переходят в модуль `diagnostics` приложения: запуск и перемотка сетки, расхождение показанных кадров между ячейками, самый долгий кадр интерфейса, копирование кадра через системную память и откат на программный декодер. Проверки первого кадра и перемотки по эталонным записям становятся тестами сеток приложения. Здесь же сетка получает общий приёмник или узел графа сцены с одним контекстом GL вместо отдельного контекста в каждой ячейке.

**Приёмка**

Сравнить площадь показанного кадра с исходной для каждой укладки: обрезка не допускается. Три тревоги подряд в тревожном слоте не меняют позиции остальных ячеек. Разворот и возврат восстанавливают прежнюю раскладку и фокус.

При отключении экрана органы управления доступны на оставшемся, после перезапуска окна возвращаются на доступные экраны. Открыть общую раскладку веб-клиента на посту другого оператора и проверить видимость камер и ограничения редактирования. Проверить перемещение между экранами, заполнение квоты, возврат из полного экрана и отзыв права на одном из каналов при работающей стене.

Сетка 16 ячеек в приложении не хуже измерительного стенда на том же стенде паспорта: время запуска и перемотки, самый долгий кадр интерфейса и расхождение ячеек сравниваются с последней серией `task desktop:video`.

### Шаг 5.3. Синхронное расследование

После 3.2 и 4.1 подключить поиск платформы 10.4 по площадке, зоне, камере и метаданным, включая выделение области движения в кадре. Реализовать общую шкалу UTC, выбор нескольких точек, совместный поиск, паузу, смену скорости и шаг на предыдущий и следующий кадр. Для каждой камеры сопоставлять PTS и UTC по данным записи. Показывать собственные пропуски и неопределённость времени. При медленном канале остальные продолжают работу, отставание обозначено.

Синхронный архив работает для всей раскладки, а не только для выбранных точек: перемещение по общей шкале ведёт все камеры к одному моменту UTC. Клиент держит в видеопамяти ограниченный кольцевой кэш опорных кадров для камер раскладки и заранее запрашивает соседние группы кадров по направлению и скорости перемещения по шкале. Размер кэша задаётся бюджетом видеопамяти из паспорта 0.2 и уменьшается при нехватке без отказа воспроизведения. **Приёмка**

Камера без размещения не предлагает соседей и не ломает переход. Ручная правка соседей видна на другом посту. Предпросмотр на карте освобождает сеанс после ухода курсора.

### Шаг 5.8. Восстановление поста и передача смены

При смене оператора клиент формирует сводку смены по журналу тревог и действий: принятые, закрытые и открытые тревоги, поручения, закладки, начатые экспорты и камеры без связи. Сдающий оператор добавляет примечание, принимающий подтверждает приём. Сводка, примечание и подтверждение хранятся на площадке и видны в журнале. Хранение записей передачи смены передаётся требованием к контракту шага 7.2 платформы. Каждый оператор входит под своей учётной записью, состояние поста восстанавливается в пределах его прав.

### Шаг 5.9. Сводка пропущенного

Переход из сводки открывает точный кадр. На площадке без аналитики сводка строится из тревог и событий камер. Измерить время построения сводки за час отсутствия по 16 камерам.

### Шаг 5.10. Режим одной задачи

После 4.1, 5.2 и 5.7 при принятии тревоги переключать рабочий экран в режим задачи: камера тревоги с повтором момента, соседние камеры по топологии, карточка с действиями и регламентом площадки. Видеостена на других мониторах продолжает работу, новые тревоги поступают в очередь со счётчиком и не перехватывают фокус. Критическая тревога более высокого приоритета показывается отдельным уведомлением с выбором оператора. Закрытие, передача или отложение тревоги возвращает прежнюю раскладку и фокус. Режим включается настройкой поста и отключается оператором.

**Приёмка**

Во время обработки тревоги создать ещё три тревоги, одну с более высоким приоритетом. Фокус ввода остаётся в текущей задаче, счётчик очереди растёт, уведомление о высоком приоритете требует решения оператора. После закрытия тревоги раскладка и фокус совпадают с исходными. Сравнить время обработки тревоги и число ошибок с режимом и без него на одном наборе заданий.

### Шаг 5.12. Синопсис интервала

После 5.3 открывать синопсис выбранной камеры и интервала: объекты интервала на одном фоновом кадре с временными метками, фильтр по классу, зоне и направлению, клик по объекту открывает точный кадр архива. Вид всегда помечен как синопсис и не используется как доказательство. Данные синопсиса строит сервис аналитики (шаг 5.3 плана аналитики).

**Приёмка**

На эталонном часе записи оператор находит все известные эпизоды через синопсис. Измерить время поиска эпизода по синопсису и по обычной перемотке на одном наборе заданий. Площадка без аналитики не показывает синопсис.

### Шаг 5.13. Заранее открытая следующая камера

После 5.7 и 5.10 при сопровождении объекта показывать предсказанные следующие камеры (шаг 4.4 плана аналитики) в ленте рядом с текущей до выхода объекта из кадра. Камеры с высокой оценкой заранее получают поток в пределах квоты, переход на них не требует ожидания первого кадра. Предсказание не меняет раскладку стены и не перехватывает фокус. Без аналитики лента показывает соседей по топологии.

**Приёмка**

На эталонных переходах измерить время от выхода объекта из кадра до кадра на следующей камере с предсказанием и без него. Квота сеансов поста не превышается, отменённое предсказание освобождает поток.

### Шаг 5.14. Пост при недоступной площадке

После 5.8 и шага Manager 1.1 хранить адреса всех узлов установки из ответа сеанса. При потере связи пробовать текущий узел, затем остальные и восстанавливать пост с повторной проверкой прав тем же путём, что после перезапуска. Показывать отказ и используемый узел.

Аварийный эфир напрямую с камер реализовать как опцию, выключенную по умолчанию. Администратор включает её для площадки, постов и групп камер по ролям. Пока связь есть, клиент получает и продлевает подписанный площадкой допуск, привязанный к ключу поста в хранилище ключей ОС: камеры и профили эфира, маски, право на звук и зашифрованные данные учётной записи камеры только для просмотра. Через 30 с недоступности площадки и всех узлов клиент предлагает режим, после подтверждения показывает только эфир камер из допуска с масками и постоянной плашкой об отсутствии записи. Просмотры пишутся в локальный журнал с цепочкой хешей и после возврата передаются в аудит площадки. [ADR-024](adr/024-post-without-site.md)

**Приёмка**

Остановка активного узла переводит пост на другой узел в пределах бюджета переключения установки плюс 5 с, раскладки, тревоги и позиция архива восстанавливаются, права проверяются заново. При выключенном режиме остановка всех узлов показывает только отказ. При включённом режиме камеры из допуска показывают эфир с масками, архив, запись, PTZ, экспорт и тревоги недоступны, площадка после возврата принимает журнал и проверяет цепочку. Истёкший допуск, отозванный пост, камера без учётной записи для просмотра и маска, которую клиент не может наложить, оставляют камеру скрытой. Ключ поста и данные камер не читаются другим пользователем ОС.

## Этап 6. Квалифицировать рабочее место

Базовый паспорт площадки предусматривает 8 камер и одного зрителя эфира. Для сеток 9 и 16 задать расширенный профиль источников и отдельно проверить нагрузку на сервер записи и выдачи. На полной сетке проверить смену профиля, отказ при нехватке квоты и её освобождение. Для большей конфигурации сначала квалифицировать серверное расширение. ### Шаг 6.2. Отказы и права

После завершения функциональных шагов прервать сеть, перезапустить ядро и медиавыдачу, усыпить и разбудить рабочую станцию, отключить монитор и пульт, отозвать права при эфире, паузе архива и экспорте. Повторить при полной загрузке. Сбросить графический драйвер и вызвать потерю графического устройства: клиент восстанавливает отрисовку без перезапуска, сеансов и потери раскладки. Потерять связь с камерой во время события, восстановить её и прервать догрузку. Проверить на шкале границы исходной записи, догруженного участка и оставшегося пропуска по серверному каталогу и эталонным кадрам. При переключении рекордера сверить показанный разрыв и время восстановления с пределами паспорта выбранной топологии.

**Приёмка**

Получение активного медиа прекращается в пределах серверного бюджета 5 с после отзыва, чувствительный кадр и данные отозванной точки убираются во всех окнах. Восстановление связи заново проверяет права. Подтверждённые команды не дублируются, частичная выгрузка не открывается как проверенная. В списках, миниатюрах, активных окнах и при смене профиля соблюдаются действующие маски и права на звук. Сохранить журнал событий и показатели клиентской и серверной стороны.

## Этап 7. Поставить и принять релиз-кандидат

### Шаг 7.1. Автономные пакеты

Собрать DEB-пакет для базовой конфигурации Linux из паспорта 0.2. Включить необходимые библиотеки Qt, QML-модули, плагины GStreamer, MapLibre, ресурсы интерфейса и локальный комплект помощи с иллюстрациями и поисковым индексом. Закрепить версии, лицензии и состав поставки, подпись и проверку целостности, штатный способ установки, обновления, отката и удаления. **Приёмка**

На чистой установке Linux из паспорта 0.2 без SDK и внешней сети установить подписанный комплект, подключиться к локальному серверу, открыть карту, эфир и архив. Прервать обновление, восстановить рабочую версию, проверить раскладки и сохранённые экспорты. Пакет с нарушенной подписью отклоняется. [Автономная поставка платформы](adr/011-offline-delivery.md)

### Шаг 7.2. Выпускной прогон

На одних и тех же пакетах 7.1 и идентифицированной сборке сервера выполнить реестр 0.1 по обязательным профилям из 8.3 основного плана. Перед приёмкой полного выпуска сверить хеш сервера с отчётом квалификации платформы 12.1. Проверить сквозную работу изолированной площадки без внешних интеграций. На установленных пакетах повторить проверки помощи из 2.3, включая переход из ошибки к одной и той же статье на русском и английском, поиск по симптому на каждом языке и по коду при потере связи с сервером. На Linux проверить обе локали после чистой установки и сохранение выбранного языка после перезапуска и обновления. Для поставки с Manager повторить переходы между постами при потере узла и центра по [профилям Manager](devplan-manager.md#установки). На каждой обязательной конфигурации Linux пройти все строки паритета и настольные сценарии, испытания 6.1 и 6.2, включая физические мониторы, камеру, пульт и ключ. Собрать матрицу «версия клиента и сервера / дистрибутив и версия Linux / GPU и драйвер / устройства / сценарий / результат», хеши, снимки, журналы и измерения. Обязательная конфигурация с пропуском или отклонением остаётся открытой. Исправленный комплект получает новый прогон затронутых сценариев и полную выпускную проверку.

На Linux-посту пройти локальный вход на площадке без провайдера. В профиле с Keycloak войти в веб-клиент и открыть настольный клиент через тот же системный браузер. При действующей сессии провайдера и политике единого входа обе сессии Bacuri должны открыться с одной корпоративной учётной записью без повторного ввода пароля. Сверить доступ к камерам, PTZ, архиву и экспорту. Отозвать право просмотра в Bacuri и проверить прекращение активной выдачи в обоих клиентах в пределах 5 с. При недоступности Keycloak повторить локальный вход администратора с WebAuthn.

### Шаг 7.3. Приёмка администратора и оператора

После 7.2 на тех же пакетах выполнить самостоятельные задания. Администратор подключает камеру и подтверждает первую запись за 5 минут, проверяет прежний архив после замены и выдаёт ограниченный доступ. Оператор оценивает тревогу и возвращается к исходной карточке за 2 минуты, затем ведёт наблюдение на одном мониторе и расследование на другом, выбирает нужные эпизоды и проверяет экспорт без сети. Основу замеров дают действующие задания первого использования. Для многокамерного расследования фиксировать время от выдачи задания до первого правильного кадра, затем до открытия и автономной проверки разрешённой копии. **Приёмка**

В заданиях смены оператор принимает пост с открытыми тревогами по сводке и примечанию, возвращается после перерыва и находит по сводке пропущенный эпизод, обрабатывает тревогу в режиме одной задачи при поступлении новых. Фиксировать время возврата к работе, долю найденных эпизодов, время и ошибки обработки.

В отдельном задании оператор по сообщению о занятой PTZ-камере открывает статью, объясняет причину и возвращается к наблюдению на том же посту. Зафиксировать, нашёл ли он решение без подсказки наблюдателя.

Фиксировать время, правильность точки и интервала, подсказки и критические ошибки для каждого задания. Для количественного сравнения с другим VMS-клиентом использовать одинаковые камеры, архив, цель, права и оборудование, чередовать порядок клиентов для участников. Публиковать долю самостоятельных завершений, время и ошибки вместе с числом попыток и версиями клиентов. Принять релиз можно после прохождения всех обязательных конфигураций, самостоятельного выполнения заданий и устранения критических ошибок. ## Порядок выполнения и учёт результатов

Начать с шага 0.1 и паспорта поста 0.2. Опубликованный контракт позволяет вести клиентский сценарий независимо от остальных функций платформы. Шаги 1.1 и 1.2 можно вести параллельно. После общего клиента работа над камерами, администрированием, картами и медиа может идти независимо в пределах указанных зависимостей. Ранний сквозной результат - вход -> выбор разрешённой точки -> эфир -> архив -> отзыв доступа. Замеры 1.1 копирования кадров и изоляции ввода определяют архитектуру отрисовки до начала этапа 2. Требования к расширению контрактов PTZ, опорных кадров, метаданных активности и связей камер передаются в шаги платформы в начале соответствующих шагов клиента, чтобы прямое управление и синхронный архив не ждали серверных изменений в конце. Далее проверить результаты этапов 3 и 4, пройти многомониторное дежурство, синхронный архив, пространственную навигацию, сохранение дела, восстановление поста и передачу смены, сводку пропущенного и режим одной задачи в этапе 5. Фирменные функции 5.11-5.13 - пространственная видеостена, синопсис и заранее открытая следующая камера - начинаются после готовности калибровки, предсказания и синопсиса в плане аналитики и сравниваются с обычной работой на одних заданиях. Шаг 5.14 начинается после 5.8 и шага Manager 1.1, его аварийный режим остаётся выключенным по умолчанию. Шаги 5.8-5.10 проверяются и на людях в 7.3: время возврата к работе после перерыва, доля найденных пропущенных эпизодов, время и ошибки обработки тревоги. Полный паритет и настольные функции подтверждает 7.2 на заявленных конфигурациях Linux, самостоятельную работу людей на тех же пакетах - 7.3.

Для каждого шага сохранять версию компонентов, условия, команду или протокол выполнения, фактический результат и ссылку на материалы. Статус шага `Готово к приёмке` ставится после его проверок, `Принято` - после сверки материалов с критериями. До появления материалов шаг остаётся задачей плана. Доказательства программного стенда и результаты целевых машин фиксируются раздельно.
