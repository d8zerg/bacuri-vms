## Результаты проверки инфраструктуры

Ниже зафиксированы выполненные проверки существующего ядра и среды сборки. Выпускной отчёт 8.3 и протокол финальной серии 9.1 формируются на релиз-кандидате.

В полном прогоне с Gitleaks и clang-format покрыты 2827 из 3171 строк продуктового C++ (89,15%) и 577 из 627 строк рабочего JavaScript (92,02%). Gitleaks завершил три проверки без находок. CTest прошёл на GCC, Clang, под ASan/UBSan и TSan, а также в сборке покрытия. Повторный прогон измеряет обе доли заново. [Критерии приёмки](basic-quality.md#автоматические-проверки-кода)

Для шкалы архива и формы подключения камеры `task ui-kit:check` прошёл 44 браузерные проверки в Chromium и Firefox в светлой и тёмной темах. На форму приходятся 24 проверки. Подтверждены фокус первого ошибочного поля, состояние каждого потока, сохранение ввода и однократная отправка при повторе, обработка запоздалого ответа после изменения адреса. Для шкалы проверены границы пропуска, выбор времени и обновление каталога с сохранением позиции. Оба компонента проверены при ширине 320 CSS-пикселей и размере текста 200%. По исходным TS и TSX покрыты 510 из 538 строк (94,80%). Контрольный незагруженный модуль учтён с нулевым покрытием при проверке механизма подсчёта. Для полных экранов действует отдельный сквозной протокол. [Шкала архива](basic-ui.md#шкала-архива-в-ui-kit) · [Форма подключения камеры](basic-ui.md#форма-подключения-камеры-в-ui-kit)

С Conan 2.34.0 два независимых разрешения профилей GCC и Clang дали одинаковый lockfile. После перехода с прежних каталогов CMake во всех четырёх тестовых пресетах прошёл 31 тест, включая прогоны с ASan/UBSan и TSan. Полный прогон `task check:report` завершился с кодом 0. На Release отдельная проверка тревоги в Chrome и Firefox открыла эталонный кадр 16. Команда `task build:repro` повторно собрала проект без сети в чистом каталоге того же образа. Все четыре исполняемых файла совпали побайтно. [Границы проверки воспроизводимости](adr/010-build-dependencies.md)

С чистой копии источников `task check:report` завершился с кодом 0. Прошли сборки GCC 14.2 и Clang 19.1, стартовый CTest в обычных и инструментированных сборках с ASan/UBSan и TSan, а также статический анализ. PostgreSQL 17.11 ответил на запрос по сети Compose. Оба H.264-профиля синтетической камеры декодировались в ожидаемом разрешении.

`task stand:check-storage` подтвердил сохранность тестовых данных PostgreSQL и архива после остановки и повторного запуска Compose. Заполнение tmpfs вернуло `ENOSPC` на границе 64 МиБ. При повторном запуске контейнера временный том был пуст.

## Протокол измерений

Базовый функциональный профиль включает управляемый источник и физическую IP-камеру. Для выпуска 8.3 обязательны все физические конфигурации, зафиксированные в 6.1. Для каждого теста указываются идентификатор комплекта, ожидаемый и фактический результат и код завершения. Ошибка, пропуск обязательной строки или отсутствие устройства блокируют переход к 9.1.

В обязательной автоматической серии 8.3 контрольную запись и смешанную нагрузку сравнивают на одном релиз-кандидате. Стенд использует восемь двухпоточных источников. При номинальном битрейте основного потока 2 Мбит/с выполняют контрольный и смешанный прогоны, затем повторяют оба при 4 Мбит/с. Каждый прогон включает 5 минут прогрева и 30 минут измерений. Во время смешанного прогона одновременно работают запись, один клиент эфира, один клиент архива, поиск и тестовые наблюдения с частотой 1 событие/с. Для первого кадра, окна поиска и задержки тревоги собирается не менее 200 проб каждого вида на каждый битрейт в смешанном прогоне. Холодный поиск прогоняется отдельно с описанием начального состояния кэша.

Основные условия приёмки приведены в матрице. Ориентир для планирования Basic - до 2 с по p95 для первого кадра эфира, отображения тревоги и первой страницы поиска. В каждом прогоне фиксируются p50, p95, p99, число проб, доля ошибок, потребление ресурсов, глубина очередей, разрывы и объём записи на диске. Стоимость хранения рассчитывается из фактического объёма за единицу времени и ёмкости выбранного носителя. Для каждого сценария отказа фиксируются начало отказа, первый обнаруженный пропуск, момент возвращения проверенной операции и объём невосстановимых данных.

| Поле результата | Что записать |
| --- | --- |
| Воспроизводимость | Ревизия проекта, версии образов и пакетов, оборудование, тип файловой системы, конфигурация сети и источник |
| Нагрузка | Число потоков и клиентов, измеренный битрейт, GOP, частота событий, длительность, объём выборки и условия запуска |
| Наблюдение | Ожидаемый результат, фактический результат, метрики и ссылки на артефакты |
| Сбои | Причина, диапазон пропуска, проверенные копии, потеря данных, длительность восстановления записи, архива и конфигурации |

## Регрессия ядра

Контрольный прогон на Linux x86_64 с ext4 и Docker Engine 29.10.0 прошёл все автоматические гейты. SHA-256 перечня проверенных исходников в `files.json` - `50b7f457334907838aa59e99eea5bb03416f2a6120d0d0e1b14a01bec090a8be`. Команда `task regression:check` формирует новый отчёт со своим хешем.

| Проверка | Результат на синтетической RTSP-камере и локальном стенде |
| --- | --- |
| Компиляторы, анализ и браузеры | 31 тест CTest в каждом из четырёх профилей, 8 проверок прототипа и 60 проверок UI Kit и экранов. Gitleaks, clang-format и clang-tidy прошли. Chrome и Firefox декодировали кадр, связанный с тревогой |
| Покрытие строк | C++ 3066/3409 (89,93%), JavaScript 570/627 (90,90%), TypeScript 1985/2204 (90,06%). Порог 75% выполнен отдельно для каждой области |
| Хранилище и восстановление | Шесть точек прерывания фиксации прошли в трёх профилях. При недоступной PostgreSQL подтверждённые блоки сохранились. После перезапуска Compose сохранились база и архив. Две независимые Release-сборки дали побайтовое совпадение четырёх исполняемых файлов |
| Обновление PostgreSQL | В копии данных перестроены 48 индексов. До обновления, после него и после восстановления полной копии совпали три архивные записи и ожидающая тревога |
| Сопровождение | В 12 образах, графах Conan, npm и инструментах стенда проверены 7754 записи о компонентах. Открытых блокирующих находок и временных исключений нет. В автономном прогоне получены те же решения |

В `postgres-upgrade/result.json` сохраняются образы исходной и обновлённой PostgreSQL, перечень перестроенных индексов, ключи найденных архивных блоков и ожидающей тревоги. Они должны совпасть на исходной базе, на обновлённой копии и после запуска сервера из новой полной резервной копии.

`task regression:check` проверяет функциональный профиль с синтетической RTSP-камерой. Для повтора сохраняются исходники с эталонами, ревизия Git, SHA-256 состава и признак локальных изменений. Новый каталог сборки, отдельная сеть и новые тома исключают использование данных предыдущего прогона. Результаты независимой Release-сборки и сохранности томов учитываются отдельно.

В `core/check.log` находятся результаты CTest, контрактов, ввода по RTSP, записи, эфира, тревог и поиска. В `core/workspace` сохраняются снимки Chrome и Firefox и измерения штатного клиента, в `core/recovery` - прерывания, потери и восстановление. В `core/dependencies` сохраняются фактические компоненты, роли, источники и ревизии сведений, применимые уведомления, исправленные версии и исключения. Критическое уведомление блокирует результат до обновления или успешной автоматической проверки адресной меры защиты. Пропуск сведений о сопровождении и истёкшее исключение также блокируют результат.

При автономном повторе проверяются хеши снимка и применяется момент исходной оценки. Для регрессии ядра срок актуальности снимка ограничен 30 сутками. Перед 8.3 сведения обновляются для конкретного кандидата. Для npm источником сведений служат карточка точной версии в реестре и канал исправлений проекта, для веток Node.js и PostgreSQL - сведения поставщиков. Системные пакеты проверяются по данным дистрибутива. Для компонентов внутри сторонних образов сохраняются также образ и отчёт сканера. [Политика сопровождения](adr/015-technology-lifecycle.md)

Протокол собственной RTSP-реализации физической камеры заполняется на выделенном стенде шага 2.2. Испытание смешанной нагрузки проводится на релиз-кандидате в 8.3. [Границы аппаратного подтверждения](rtsp-compatibility.md)

Стенд измеряет задержку интерфейса отдельно от времени пользователя и появления первого видеокадра.

Сквозной сценарий администратора подтвердил применённую версию 1 и кадр основного потока 1280×720. У оператора эфир имел ширину 640 пикселей. Оба браузера прошли ожидание каталогизации, возврат после перезапуска HTTPS-сервиса, обновление прямой ссылки и истечение сессии при фоновом опросе.

## Испытания отказов и восстановления

`task recovery:check` создаёт отдельный Compose-проект с PostgreSQL и синтетической RTSP-камерой. Регистратор, ядро и медиаслужба используют рабочие бинарные файлы. Два пользователя, две точки, основной поток 1280×720 и tmpfs на 64 МиБ входят в профиль. Отчёт содержит JSON по отказам и JUnit XML по границам фиксации. В общем прогоне это файлы `recovery/<preset>.json` и `recovery/<preset>.boundaries.xml`. [Процедура восстановления](basic-recovery.md)

| Прерывание | Проверяемый результат | Измерение на GCC Debug |
| --- | --- | --- |
| Процесс завершён после синхронизации медиа, манифеста или временного каталога | После открытия тома незавершённый каталог не попадает в выдачу | Три точки прерывания, ноль опубликованных блоков |
| Завершение после переименования, синхронизации родителя или фиксации журнала | Перезапуск восстанавливает завершённый блок. Повторная регистрация идемпотентна | По одному блоку в каждом из трёх случаев |
| Остановка процесса PostgreSQL | Во время отказа увеличивается локальный журнал, после запуска БД все подтверждения возвращаются | Все 3 автономно записанных блока дошли до каталога за 5,216 с от начала отказа |
| Остановка RTSP-камеры | После подключения возобновляется запись. Сохраняются точка и границы `source_offline` | 3,602 с пропуска |
| Остановка медиаслужбы | Запрос части получает HTTP 503, продолжается запись, прежний сеанс снова читает часть | 1,119 с до чтения |
| Заполнение тома до нуля свободных блоков | После освобождения места есть новый блок и интервал `storage_failure` | 1,000 с пропуска, 2,025 с до подтверждения восстановления |
| Запуск сверки без подключения тома | Отдельный контейнер видит ту же БД без архива. Прежний сеанс и новое чтение закрыты. С возвратом носителя выполняется повторная сверка | 0 утраченных блоков, 6,166 с до декодирования |

Повтор проверяет файлы, снимает запрет и сохраняет уникальность блоков | Проверены повтор восстановления конфигурации, прерывание сверки, восстановление без SQLite и отказ в доступе к чужой точке |
| Уничтожено всё содержимое единственного тома | Все известные старые блоки недоступны. На новом томе проверяется чтение новой записи | Утрачены все 23 доступных блока общим объёмом 1 513 063 байта. Новая запись прочитана через 1,997 с |

Для трёх измерений ниже начало RTO общее - потеря БД. Конец фиксируется отдельно для каждой операции. Указаны результаты одного автоматического прогона на малом томе. Скорость восстановления на архиве проектной ёмкости измеряют на целевом носителе.

| Объект | Фактическая потеря и измерение RPO | Результат, по которому остановлен таймер RTO |
| --- | --- | --- |
| Конфигурация и права | Возраст снимка 0,446 с. Потеряно одно изменение после снимка | 0,938 с до нового входа и проверки камеры, разрешённой и чужой точек |
| Исторический архив | Доступны все 16 исправных завершённых блоков. Потеря по повреждённому блоку - 1,000 с | 1,884 с до декодирования старого блока через HTTPS. Отдельно прочитан каждый исправный блок |
| Новая запись | Между концом последнего блока до отказа и началом первой новой записи прошло 3,558 с | 4,704 с до получения и декодирования нового блока после восстановления назначения регистратора |

В повторном прогоне GCC Debug конфигурация и права восстановились за 0,999 с, прежний фрагмент декодирован за 1,986 с, новый за 5,276 с. Возраст снимка составил 0,642 с, перерыв новой записи - 4,324 с. Проверены все 14 исправных исторических блоков. Единственный испорченный блок дал 1,000 с потери.

Прерывания фиксации моделируют остановку процесса при работающем ядре Linux. Отключение проверяет отсутствие подключения тома у процесса восстановления. Испытание физического выключения питания и производительность диска на полном архиве требуют отдельного аппаратного стенда.
