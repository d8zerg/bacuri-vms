# Восстановление конфигурации и архива Bacuri VMS

Процедура рассчитана на одну площадку и один узел записи. Её выполняют локальными командами C++ в окружении соответствующей службы. Требуются идентификаторы исходных площадки и узла, доступ ядра к PostgreSQL, ключ конфигурации ядра и сохранившийся архивный том. До начала работ определите, где находятся исходные данные и куда будет восстановлена площадка. Проверить процедуру на отдельном окружении можно командой `task recovery:check`. [Протокол испытаний](test-profile.md#испытания-отказов-и-восстановления)

Для установленного Debian-пакета полная копия включает также историю, каталог и ключи площадки. [Обслуживание установленного узла](maintenance.md)

## Резервная копия

Создайте снимок на носителе, независимом от PostgreSQL и тома записи. Пример для каталога резервных копий с доступом только администратору. Переменная `backup_dir` должна содержать путь к этому каталогу.

```sh
set -eu
umask 077
partial=$(mktemp "$backup_dir/.config-XXXXXXXX")
name=${partial##*/}
backup="$backup_dir/${name#.}.backup"
if docker compose exec -T core /opt/bacuri/bacuri-vms-core backup-config > "$partial"; then
    sync "$partial"
    ln "$partial" "$backup"
    rm "$partial"
    sync -f "$backup_dir"
    echo "$backup"
else
    rm -f "$partial"
    exit 1
fi
```

Снимок читается в одной транзакции PostgreSQL и шифруется с аутентификацией ключом ядра. Он содержит учётные записи с хешами паролей, аудит привязок WebAuthn, роли, области доступа, реестр, привязки, версии настроек, зашифрованные реквизиты камер, аудит конфигурации и ключи повтора регистрации. Восстановление завершает браузерные сессии и сбрасывает привязки WebAuthn, включая ключи из старых копий. Администратор повторно регистрирует ключ по одноразовому коду локальной консоли. Восстановление привязано к той же площадке и узлу. Предел шифротекста - 128 МиБ. Храните защищённую копию ключа ядра отдельно. Для продолжения подписи экспортов от имени площадки сохраните также `export.key` из тома `core-identity`. Архив доверенных открытых ключей позволяет проверять ранее выданные комплекты после смены ключа. Для восстановления существующих TLS-идентичностей и локального журнала назначений регистратора также сохраните соответствующие ключи. Частота снимков определяет возможный откат конфигурации и прав.

Архив, события и тревоги требуют отдельных резервных копий. Для видео сохраняют блоки с манифестами и журнал тома на независимом носителе. SHA-256 служит проверкой целостности сохранившихся байтов.

## Восстановление площадки

1. Остановите `core`, `recorder` и `media` на восстанавливаемой площадке. Сохраните исходные базы и тома для диагностики. Подготовьте отдельную чистую БД PostgreSQL, ключ ядра и том в исходной точке подключения. Все дальнейшие команды должны обращаться к целевой БД. Для восстановления старой конфигурации используйте свежий том `recorder-data`: регистратор получит назначение заново. Том `archive-data` содержит отдельный журнал архива.
2. Примените миграции, загрузите копию и проверьте состояние. Для повтора с тем же снимком допустима база с тождественной конфигурацией. Несовпадение содержимого, ключа или назначения прерывает восстановление. Операция отзывает браузерные сеансы и требует повторного применения настроек регистратором.

   ```sh
   docker compose run --rm --no-deps -T core /opt/bacuri/bacuri-vms-core migrate
   docker compose run --rm --no-deps -T core /opt/bacuri/bacuri-vms-core restore-config < "$backup"
   docker compose run --rm --no-deps -T core /opt/bacuri/bacuri-vms-core recovery-status
   ```

3. Сверьте роли, привязки и выданные права с действующими на момент возврата в эксплуатацию. Изменения после снимка, включая отзывы прав, требуют повторного применения. На этом этапе архив имеет состояние `awaiting_verification`. Если сохранена рабочая БД и требуется только сверка носителя, переходите сразу к следующей операции. При остановленном ядре в целевой БД список ролей и явных назначений точек доступен таким запросом. Для администратора область охватывает всю площадку.

   ```sql
   SELECT u.username, r.site_id, r.role, g.point_id
   FROM bacuri_inventory.site_roles r
   JOIN bacuri_inventory.local_users u USING (user_id)
   LEFT JOIN bacuri_inventory.point_grants g USING (user_id, site_id)
   ORDER BY u.username, r.site_id, g.point_id;
   ```

4. При остановленном регистраторе выполните `docker compose run --rm --no-deps -T archive-recovery`. Команда сама закрывает выдачу до проверки, удерживает исключительное владение томом и единолично обновляет каталог площадки. В журнале проверки указываются UUID повреждённых файлов. В итоговом JSON `verified` - число проверенных блоков, `corrupt` - повреждённых, `journal_missing` и `catalog_missing` - число отсутствующих блоков, известных соответственно журналу и каталогу. Эти два счётчика могут учитывать один и тот же блок.
5. Команда `recovery-status` показывает состояние допуска к архиву в ядре. Значение `available` означает, что административный запрет снят. Состояние `volume_unavailable` требует проверить подключение и путь. Состояние `verifying` после завершения процесса с ошибкой означает незавершённую сверку. Проверьте причину в stderr, владельца тома, права файлов и наличие исторических привязок в восстановленной конфигурации. При необходимости восстановите подходящий снимок в чистую БД. Повторите ту же команду. При отсутствии SQLite исправные манифесты и файлы позволяют восстановить журнал и каталог. Сведения о прежних пропусках требуют сохранённого журнала или каталога. При переходе с SQLite версии 3 сохраняются ожидающие передачи интервалы. Сведения об уже подтверждённых до перехода пропусках остаются в исходной PostgreSQL.
6. После успешной сверки запустите `docker compose up -d --wait core recorder media`. Проверьте `task archive:status`, состояние применения камеры и появление нового завершённого блока. Автоматическая приёмка дополнительно входит под оператором, декодирует через HTTPS старый и новый материал и проверяет отказ на соседней точке. [Матрица и измерения](test-profile.md#испытания-отказов-и-восстановления)

## Отказы во время работы

| Наблюдение | Действие и ожидаемый результат |
| --- | --- |
| PostgreSQL временно недоступен, том исправен | Запись продолжается. После возврата БД регистратор передаёт накопленные манифесты до подтверждения. Повторная регистрация совпадающего блока сохраняет одну строку каталога. |
| Камера недоступна | Вернуть связь с обоими RTSP-профилями. После нового ключевого кадра проверить продолжение записи и интервал `source_offline`. |
| Отказала медиавыдача | Перезапустить `media`. Регистратор продолжает писать. Повторное чтение проверяет права и контрольную сумму. |
| Том заполнен | Освободить место по принятой политике хранения. Регистратор повторяет фиксацию сведений об отказе после появления места. Диагностика содержит точку и границы `storage_failure`; при одновременной потере журнала и процесса сохраняются лишь внешние журналы диагностики. |
| Том отключён | Остановить регистратор и медиавыдачу. Вернуть исходный носитель, выполнить сверку и запустить службы. При несовпадении назначения выдача остаётся закрытой. |
| Повреждение известного блока | Сохранить повреждённый материал для диагностики. Сверка исключает его из выдачи и отмечает известный интервал как `storage_failure`. Для каталога без читаемого манифеста и без прежних метаданных доступны UUID каталога блока и сообщение о повреждении. |
| Утрачен единственный том | Если независимой копии нет, прежний материал утрачен. Сохранить исходный каталог с известными интервалами. На новом исправном носителе инициализировать каталоги штатным `control-init`, запустить регистратор для создания журнала нового тома и остановить его. Выполнить сверку и вернуть службы. Известные прежние интервалы получают `storage_failure`, новая запись доступна отдельно. |
