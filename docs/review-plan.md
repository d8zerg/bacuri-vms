# План исправлений по результатам ревью

Ревью сверяет код, контракты, сборку и интерфейс с [принципами продукта](ru/product-principles.md): открытость, скорость оператора, достоверность архива, а также с [ADR-018](adr/018-core-module-boundary.md) и [критериями качества](quality.md). Находки получены чтением кода и эталонных снимков и подтверждены при исправлении сборкой и тестами. Расхождения интерфейса с принципами перечислены отдельно в [ревью экранов](ui.md#ревью-по-принципам-продукта).

## Приоритеты

| Приоритет | Значение |
| --- | --- |
| P0 | Нарушает приоритетное свойство, грозит потерей записи или недоступностью площадки |
| P1 | Мешает достичь целевых порогов или эталонного уровня архитектуры |
| P2 | Качество кода и сопровождение |

## Сильные стороны

Эти решения сохраняются и служат образцом для остального кода.

- Фиксация блока архива: промежуточный каталог, `fsync` медиа, манифеста и каталога, `renameat2(RENAME_NOREPLACE)`, журнал после синхронизации родителя, сверка при запуске. [volume.cpp](../src/archive/volume.cpp)
- Удаление по сроку хранения через устойчивое переименование `.expired-*` с завершением после сбоя. [retention.cpp](../src/archive/retention.cpp)
- Пропуски источника и перегрузки очереди записываются в журнал пропусков с причиной. [sources.cpp](../src/services/recorder/sources.cpp#L175-L193)
- Веб-безопасность: cookie `HttpOnly; Secure; SameSite=Strict`, CSRF-токен с проверкой Origin, CSP, Argon2 для паролей, зашифрованные учётные данные камер, разбор XML без сети и подстановки сущностей. [session.cpp](../src/modules/access/session.cpp#L12) · [onvif.cpp](../src/modules/inventory/onvif/adapter.cpp#L57-L58)
- Подпись экспорта отдельным ключом Ed25519 и автономная проверка. [evidence.cpp](../src/archive/evidence.cpp)
- Транзакционные миграции PostgreSQL с блокировкой. [migrations.cpp](../src/storage/postgresql/migrations.cpp)
- Инструменты проверки: санитайзеры, покрытие, воспроизводимая сборка, проверка секретов, зафиксированные зависимости, скриншот-тесты в двух браузерах и темах. [CMakePresets.json](../CMakePresets.json) · [Taskfile.yml](../Taskfile.yml)
- Веб-клиент: строгий TypeScript, типы из OpenAPI, доступность с клавиатуры, проверка контраста.

## P0. Достоверность и доступность

### R1. Статусы связи и записи всегда неизвестны

- **Где.** Список точек возвращает фиксированные `'connection','unknown','recording','unknown'`. [registry.cpp](../src/modules/inventory/registry.cpp) Контракт объявляет `recording: [unknown, current, delayed, stopped]`, но сервер не формирует `current`, `delayed` и `stopped`. [openapi.yaml](../contracts/v1/openapi.yaml#L4355) Состояние «Запись ведётся» на эталонных снимках задаёт только фикстура Storybook. [workspaceFixture.ts](../web/client/stories/workspaceFixture.ts)
- **Последствие.** На реальной площадке оператор всегда видит «Связь с камерой неизвестна» и «Состояние записи неизвестно». Главное требование достоверности архива не выполняется, а скриншот-тесты проверяют недостижимое состояние.
- **Исправление.** `recording` выводить из возраста последнего зафиксированного блока точки в каталоге: `current` - не старше порога, `delayed` - старше порога, `stopped` - запись остановлена политикой, нехваткой места или отказом носителя. `connection` выводить из состояния потока рекордера. Изменения публиковать в ленте обновлений. Состояние рекордера `point_states` уже есть в `GetStorageStatus`. [main.cpp](../src/services/recorder/main.cpp#L184)
- **Проверка.** Сценарий на стенде: остановить камеру, заполнить носитель до резерва, отключить политику. Для каждого случая состояние меняется в пределах порога и возвращается после восстановления. Отдельный контрактный тест проверяет, что сервер формирует каждое значение перечисления.

### R2. Запуск рекордера читает весь архив

- **Где.** Конструктор `Volume` вызывает `reconcile`, который для каждого каталога блока пересчитывает SHA-256 медиа и звука. При настроенной копии сверяются и копии. [volume.cpp](../src/archive/volume.cpp) · [block_verification.cpp](../src/archive/block_verification.cpp) `Volume` создаётся членом `Recorder` до запуска gRPC-сервера и источников. [main.cpp](../src/services/recorder/main.cpp#L338)
- **Последствие.** После перезапуска или отключения питания запись не возобновляется, пока не прочитан весь архив. Для 8 ТБ при 500 МБ/с это около 4,5 часа без записи.
- **Исправление.** При запуске проверять только блоки, которые отсутствуют в журнале или зафиксированы после последней устойчивой отметки. Полную проверку целостности выполнять фоновой задачей с ограничением скорости чтения, по аналогии с `scrub_copy`. Запуск записи не зависит от фоновой проверки.
- **Проверка.** Тест с синтетическим архивом заданного объёма: время от запуска процесса до первого нового блока ограничено и не зависит от объёма архива. Повреждённый блок обнаруживается фоновой проверкой.

### R3. Блокирующий пул ядра и соединение с PostgreSQL на каждый запрос

- **Где.** Все обработчики HTTP выполняются синхронно в пуле из четырёх потоков. [https.cpp](../src/services/control/transport/https.cpp#L191) Каждый обработчик открывает новое соединение PostgreSQL. В коде 60 таких мест. [database.cpp](../src/storage/postgresql/database.cpp) Догрузка архива с камеры держит поток пула до 35 с. [edge_archive.cpp](../src/modules/inventory/edge_archive.cpp) Хеширование паролей Argon2 выполняется в том же пуле.
- **Последствие.** Четыре одновременных долгих операции (догрузка, экспорт, загрузка карт, вход) останавливают весь API: открытие эфира, снимок ленты тревог, обработку тревоги. Новое соединение PostgreSQL на каждый запрос добавляет задержку к каждому действию оператора.
- **Исправление.** Пул соединений PostgreSQL. Долгие операции вынести в фоновые задания с ресурсом состояния (`202 Accepted` и опрос или публикация в ленте). Отдельный ограниченный пул для хеширования паролей. Действия оператора обслуживаются пулом, который фоновые задания не занимают.
- **Проверка.** Нагрузочный сценарий: параллельные догрузки и экспорт во время работы оператора. p95 открытия эфира и доставки тревоги остаются в пределах порогов.

## P1. Достоверность архива

### R4. Потеря кадров при пределе группы кадров не попадает в журнал пропусков

- **Где.** При превышении 900 кадров, 32 МБ или 15 с без ключевого кадра писатель завершает блок и отбрасывает кадры до следующего ключевого. В журнал пропусков это не попадает, только в `stderr`. [writer.cpp](../src/archive/writer.cpp#L384-L397)
- **Исправление.** Записывать пропуск с причиной `gop_limit` от первого отброшенного кадра до следующего ключевого.
- **Проверка.** Синтетическая камера с группой кадров длиннее 15 с. На шкале виден пропуск с причиной.

### R5. Обрезанная догрузка помечается как полная

- **Где.** Остановка по лимиту 30 с не задаёт `outcome`, поэтому результат с любым числом блоков получает `copied`. Курсор продолжения ставится на конец запрошенного окна. [writer.cpp](../src/archive/writer.cpp#L162-L165) · [writer.cpp](../src/archive/writer.cpp#L217-L218) · [edge_archive.cpp](../src/modules/inventory/edge_archive.cpp)
- **Исправление.** Возвращать `partial` и фактически покрытый интервал. Продолжение начинается с конца покрытия.
- **Проверка.** Медленный источник воспроизведения: ответ содержит `partial`, повторный запрос дозаполняет остаток.

## P1. Скорость оператора

### R6. Первый кадр эфира ждёт ключевого кадра камеры

- **Где.** Новая очередь подписчика начинается с `need_keyframe_ = true` и ждёт следующего ключевого кадра. [ingest.hpp](../src/ingest/ingest.hpp#L84) · [ingest.cpp](../src/ingest/ingest.cpp#L25-L32) Процесс выдачи подписывается на поток только после установления WebRTC-соединения. - **Исправление.** Хранить в `Stream` последнюю группу кадров от ключевого кадра с ограничением по объёму и отдавать её новому подписчику сразу. Подписку открывать параллельно согласованию WebRTC.

### R7. Опрос вместо ожидания и конвейер GStreamer на каждый блок

[writer.cpp](../src/archive/writer.cpp#L371-L381) Для каждого блока создаётся и разбирается новый конвейер GStreamer. [writer.cpp](../src/archive/writer.cpp#L62-L125) Процесс выдачи опрашивает состояние WebRTC каждые 40 мс. [live.cpp](../src/services/media/live.cpp#L84-L85)
- **Последствие.** 100 пробуждений в секунду на камеру и создание конвейера каждые 1-2 с на камеру ограничивают число камер на узел и повышают задержку.
- **Исправление.** Ожидание по условной переменной с `stop_token`. Запись фрагментированного MP4 напрямую или постоянный муксер на поток. Подписка на сигналы состояния WebRTC вместо опроса.
- **Проверка.** Замер числа камер на ядро и загрузки CPU до и после на одном стенде.

### R8. Наблюдаемость не позволяет измерить пороги на площадке

- **Где.** Архитектура объявляет структурированные журналы, метрики Prometheus и трассировку OpenTelemetry. [architecture.md](ru/architecture.md#3-топологии-и-базовый-стек) В коде 35 вызовов `fprintf(stderr)`/`fputs`, 18 блоков `catch`, которые возвращают ошибку без записи причины, ошибки PostgreSQL теряют `PQerrorMessage`. [database.cpp](../src/storage/postgresql/database.cpp) Метрики - шесть показателей, которые периодически собирает отдельный процесс. [maintenance_diagnostics.cpp](../src/admin/maintenance_diagnostics.cpp)
- **Исправление.** Общий модуль структурированного журнала с событием, точкой, кодом и причиной. Запись причины в каждом `catch`, который преобразует исключение в ответ. Гистограммы задержек для целевых порогов: первый кадр, доставка тревоги, ответ API, фиксация блока. Публикация через существующий сокет метрик.
- **Проверка.** На стенде пороги из принципов продукта читаются из метрик без отдельного стенда замеров.

### R9. Канал gRPC создаётся на каждый вызов

- **Где.** 13 вызовов `local_channel(...)` создают канал при каждом запросе, например [edge_archive.cpp](../src/modules/inventory/edge_archive.cpp).
- **Исправление.** Один долгоживущий канал на сокет в процессе.

### R25. Интерфейс на двух языках

### R26. Разные способы сообщать об ошибках

- **Где.** HTTP API возвращает код Problem, а HTTP-статус выбирается в каждом месте сервера, поэтому один код встречается с разными статусами. Служебный gRPC описывает сбои английским текстом. Веб-клиент сопоставляет коды с сообщениями отдельно на каждом экране. Страница неудачного корпоративного входа и описания изменений политики записи в журнале событий формируются сервером на русском языке. Непредвиденный сбой обработчика возвращается как `authorization_unavailable`.
- **Исправление.** Один каталог ошибок с категорией, HTTP-статусом, кодом gRPC, классом повтора и адресатом причины. Сервер, контракт, клиент и справочник получают коды из каталога. Сервер передаёт коды и параметры, тексты для людей выводит клиент на языке интерфейса. [ADR-020](adr/020-error-catalog.md)
- **Проверка.** `task api:check` сверяет каталог с контрактом, исходниками сервера, сообщениями обоих языков клиента и справочником. Проверка типов клиента отклоняет код без сообщения.

## P2. Качество кода и инструменты

### R22. Предупреждения компилятора и clang-tidy

- **Где.** Пресеты превращают предупреждения в ошибки (`CMAKE_COMPILE_WARNING_AS_ERROR`), но `-Wall -Wextra -Wpedantic` включены только для части целей. [CMakeLists.txt](../CMakeLists.txt#L10) clang-tidy включает только `clang-analyzer-*` и `bugprone-*`. [.clang-tidy](../.clang-tidy)
- **Исправление.** Предупреждения для всего проекта, затем поэтапно `-Wconversion` и `-Wshadow`. Добавить группы `performance-*`, `modernize-*` и выбранные `cppcoreguidelines-*`.

### R23. Числовые константы без имени

- **Где.** Параметры звука `125` и `2` при обрезке PCM. [writer.cpp](../src/archive/writer.cpp#L309-L318) Границы времени в запросе догрузки. [main.cpp](../src/services/recorder/main.cpp#L74-L76) Длины путей в маршрутизации (R18).
- **Исправление.** Именованные константы и доменные типы времени из [time.hpp](../src/domain/time.hpp).
