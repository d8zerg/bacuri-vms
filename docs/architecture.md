# Архитектура Bacuri VMS Platform

- **Техническое имя** - `bacuri-vms`.
- **Статус документа** - проект архитектуры.
- **Основание** - [концепт Bacuri VMS Platform](concept.md).
- **Принято** - C++23 для серверного кода, Debian 13 и новее на x86-64, автономная on-premises установка, федерация независимых инсталляций и опциональные SaaS-модули.

## 1. Архитектурная модель

Площадка - единица владения устройствами, данными, политиками и восстановления. В простом профиле на одном узле работают модульное ядро управления и отдельные процессы записи и выдачи видео. В кластере те же компоненты распределяются по узлам. Их исходный код, модели данных и контракты общие. Внешний центр федерации обслуживает независимые площадки через поток метаданных и ограниченные операции.

Контуры имеют разные требования к работе при отказе. Запись опирается на локальное хранилище и последнюю применённую конфигурацию. Просмотр использует отдельные лимиты декодирования и исходящего трафика. Управление хранит желаемую конфигурацию и фактическое состояние применения. Поиск и аналитика допускают отставание с указанием актуальности. Отзыв доступа и исполнение команд проверяются в контуре, который выдаёт данные или управляет устройством.

```text
Камеры -> приём потоков -> архив площадки -> выдача записи -> рабочее место
Приём потоков -> выдача прямого эфира -> рабочее место
Детекторы и адаптеры -> журнал событий -> правила и тревоги -> рабочее место
Ядро управления -> конфигурация и назначение потоков -> процессы площадки
Площадка -> разрешённые метаданные -> центр федерации / PSIM / SaaS
Внешний запрос -> вход площадки -> проверка прав и срока -> локальное исполнение
```

## 2. Компоненты и владельцы данных

| Компонент | Ответственность | Устойчивое состояние |
| --- | --- | --- |
| Ядро управления | Каталог ресурсов, привязка устройств, карты и планы объекта, политики, роли, конфигурация, размещение потоков, REST API | PostgreSQL. Транзакции ограничены областью площадки |
| Приём и запись | Сеансы с камерами, основной и дополнительный потоки, сохранение сегментов, догрузка с камер | Файлы архива и локальный журнал фиксации. Прикладной каталог записей в PostgreSQL |
| Выдача медиа | Сеансы прямого эфира и воспроизведения, выбор копии, маскирование и трансформация по запросу | Краткоживущие сеансы. Архив и результаты экспорта живут в хранилище |
| События, правила и тревоги | Нормализация, корреляция, очередь смены, эскалация, симуляция и уведомления | Журнал наблюдений и бизнес-состояние тревог и реакций |
| Исполнение команд и адаптеры | Проверка возможности устройства, арбитраж, отправка и наблюдение результата | Журнал команд в ядре. Внешнее устройство остаётся источником наблюдаемого физического состояния |
| Поиск и расследования | Временная шкала, географические фильтры, индекс детекций, закладки, защита и экспорт | Материалы и ограничения хранения в PostgreSQL. Перестроение индекса ограничено сроком хранения исходных детекций и манифестов. Превью восстанавливается из доступного видео |
| Центр управления федерацией | Реестр и доверие площадок, распространение политик, сводка, федеративный поиск и диагностика | Собственное хранилище центра с разрешёнными проекциями данных площадок |
| Выполнение фоновых задач | Репликация, проверка целостности, экспорт, аналитика, интеграции | Состояние заданий, прогресс и контроль повторов у владельца задания |

Модель различает площадку, точку наблюдения, физическое устройство, канал и профиль потока. Точка сохраняет идентификатор при замене камеры. История связывает каждый интервал с конкретным каналом и версией его привязки. География, зона детекции и версия правила разрешаются на момент события. Наблюдение, тревога, команда и материал расследования имеют собственные идентификаторы и связи. Изменения конфигурации хранятся версиями с результатами применения по ресурсам.

Массовая настройка хранит ожидаемую версию и результат по каждому ресурсу. Конфликт двух редакторов возвращает текущую версию. Повтор после обрыва продолжает незавершённые операции с тем же идентификатором. Монтажник видит, где камера уже применила шаблон, где нужна сверка фактических настроек и какие изменения можно откатить.

В базовой поставке ядро объединяет управление, правила, тревоги и API поиска. Запись и выдача работают в отдельных процессах. Внутри ядра каждый модуль владеет своим состоянием и предоставляет операции другим модулям через интерфейс. Процессы и сторонние расширения используют авторизованные API. Бинарные записи, детекторные метаданные и пользовательские права имеют раздельные правила доступа и хранения.

### Контракты сценариев PoC

Монтажник регистрирует камеру через ядро. Только узел записи подтверждает применённую версию, только чтение опубликованного блока позволяет показать первый архивный кадр. Оператор получает тревогу из состояния ядра. Право и ссылка на архив проверяются при открытии, а факт выдачи и прекращение потока наблюдаются на стороне медиавыдачи. Браузер владеет выбором точки, позицией и фокусом. [Критерии архитектуры и данных](poc-quality.md#требования-к-приёмке)

| Граница и контракт | Обязательство и результат при отказе | Проверка на стенде |
| --- | --- | --- |
| Браузер -> ядро -> запись. HTTPS, версия и `ApplyConfiguration` | Ядро хранит желаемую версию и права. Повтор создания с тем же ключом даёт исходный результат. Узел подтверждает применение и продолжает запись по последней применённой конфигурации при недоступности ядра | Потерять ответ, повторить создание, прервать применение и перезапустить узел. Сопоставить версии в API и фактический поток. [ADR-001](adr/001-api-contracts.md) · [ADR-002](adr/002-processes.md) |
| Запись -> том -> каталог. Манифест, SQLite, `RegisterBlock` и `RegisterGap` | Узел публикует завершённый блок, ядро подтверждает регистрацию после транзакции. До регистрации покрытие может ожидать каталогизации. Повреждение после сверки имеет наблюдаемую причину | Прервать фиксацию и потерять подтверждение, повторить регистрацию и сверить каталог с томом. [ADR-003](adr/003-archive.md) |
| Запись -> выдача -> браузер. `Subscribe`, WebRTC, `ReadPart` и HTTPS | Выдача читает архив с тома только для чтения, получает разрешение у ядра и ограничивает очереди. Медленный зритель и перезапуск выдачи сохраняют запись. Истечение разрешения прекращает передачу | Сравнить интервалы записи с контролем, измерить отзыв на выходе эфира и архива. [ADR-005](adr/005-media.md) · [Сроки доступа](adr/001-api-contracts.md#жизненный-цикл-медиасеанса) |
| Источник -> ядро -> браузер. `SubmitObservation`, снимок ленты, WSS и поиск по точке | Одна транзакция фиксирует наблюдение, тревогу и публикацию. Повтор не создаёт вторую тревогу. После обрыва клиент догоняет ленту по курсору или обновляет снимок. Учитываются версия привязки и неопределённость часов | Повторить событие, прервать подписку, проверить равенство снимка и ленты. Сверить кадр с известным временем, отдельно вызвать пропуск и потерю привязки. [ADR-004](adr/004-time.md) · [Контракт наблюдения](adr/001-api-contracts.md#приём-наблюдения-и-архив-тревоги) |

На архитектурном ревью изменение прослеживают от действия роли до владельца данных и обратно до наблюдаемого результата. Проверяют, какая зависимость может отказать, кто ограничивает память и время ожидания, как повтор влияет на данные и как установить причину по диагностике. Смена владельца состояния, гарантии доставки или допустимого поведения при отказе требует пересмотра соответствующего ADR и повторного испытания затронутых сценариев. [Реестр решений](poc-test-profile.md#реестр-проектных-решений)

## 3. Топологии и базовый стек

| Профиль | Обязательная топология | Дополнительные компоненты |
| --- | --- | --- |
| Компактный | Один узел, процессы управления, записи и выдачи, локальный PostgreSQL, локальный диск | Локальные детекторы в заданном бюджете, поддерживаемая внешняя копия |
| Одиночный сервер | Те же роли на сервере, отдельный том архива, отдельные лимиты записи, просмотра и фоновых задач | GPU, резервный пул, отдельный сервер интеграций или аналитики |
| Кластер | Управление и PostgreSQL с высокой доступностью, распределённые узлы записи и выдачи, хранилища в заданных доменах отказа | Выделенные узлы декодирования, индексирования, аналитики, копирования, Kafka и внешние модули |

Basic определяет стартовую поставку. Профиль определяет топологию и ресурсы. Каждая площадка может работать самостоятельно или войти в федерацию. Стоимость кластера и потеря пропускной способности в режиме N-1 проверяются по ролям и доменам отказа, включая питание, сеть и диски.

При размещении потоков учитываются доступность камеры из сети узла, пропускная способность, свободное место и бюджет декодирования. Запись обычно идёт на диск узла, который принимает поток. Для выдачи и аналитики добавляются отдельные узлы по мере исчерпания соответствующего бюджета. Операции переноса и ребалансировки учитывают лимиты входящих подключений на камере и текущий резерв на отказ.

В кластере клиенты и интеграции используют стабильный адрес площадки с резервированным входом API. Реплики ядра восстанавливают сессии и операции из общего устойчивого состояния. Задание планировщика получает один исполнитель по ограниченному назначению. После потери узла выдачи клиент открывает новый медиасеанс на доступном узле с повторной проверкой прав. Для архива клиент сохраняет позицию воспроизведения.

## 4. Устройства, приём и выдача медиа

1. Адаптер обнаруживает устройство в разрешённом сегменте или принимает адрес из инвентаря. Результат подключения включает доступность, прошивку, заявленные и испытанные возможности, часы, кодеки, профили потоков и результаты контрольной записи. ONVIF Profile T, G и M применяются к поддерживаемым функциям. Для камеры с одним RTSP-потоком доступен ручной ввод с проверкой фактических возможностей. Смена камеры проходит через проверку совместимости привязок и масок до переключения. [Профили ONVIF](https://www.onvif.org/profiles/)
2. Узел записи открывает один входной сеанс на используемый профиль в штатном режиме. Поток разветвляется внутри узла. Основной профиль обычно пишется в исходном кодировании. Дополнительный обслуживает раскладки и низкую пропускную способность. Очередь просмотра или аналитики имеет отдельный предел и может пропускать кадры при перегрузке. Ручная запись, расписание и триггеры сходятся в единой политике. Предзапись использует ограниченный буфер и доступные точки декодирования.
3. Сервер выдачи получает право на конкретный поток, интервал и представление. Для прямого эфира опорная совместимость браузеров - согласованный режим H.264 и Opus при наличии аудио. H.265 может сохраняться в архиве в исходном кодировании. В прямом эфире сервер выбирает совместимый профиль камеры. Для архива он выбирает совместимую запись того же интервала либо транскодирование по квоте. Клиент видит качество и доступность выбранного варианта. TURN при необходимости разворачивается в сети заказчика. Пути браузера и режимы аппаратного ускорения подтверждаются матрицей клиентов и оборудования.
4. Воспроизведение строится вокруг общего времени и карты доступных интервалов. Переход к произвольной позиции использует предыдущую точку декодирования. Для перемотки, многокамерного просмотра и экспорта действуют отдельные лимиты. Запись помечает изменение кодека, разрешения, конфигурации и разрывы. Для синхронизации RTP-потоков узел использует пары отметок RTP и NTP из отчётов RTCP при их наличии. Скачок часов или перезапуск камеры открывает новый интервал привязки времени. При отсутствии надёжной привязки шкала показывает оценку по времени приёма и её неопределённость. Расписания применяются в часовом поясе площадки. [Синхронизация RTP и RTCP](https://www.rfc-editor.org/rfc/rfc3550.html#section-6.4.1)

Узел приёма передаёт сжатые данные процессам выдачи и аналитики по локальному межпроцессному каналу, удалённому узлу - по аутентифицированному защищённому медиасоединению. Дальнейшую раздачу зрителям выполняет узел выдачи. У каждого потребителя своя ограниченная очередь. Медленный просмотрщик может потерять кадры до следующей точки декодирования. При исчерпании очереди самой записи система фиксирует утраченный интервал и поднимает тревогу. Бюджеты CPU, GPU, памяти, диска и сети проверяются до запуска затратных задач. [Разветвление потоков в GStreamer](https://gstreamer.freedesktop.org/documentation/coreelements/tee.html)

## 5. Архив, поиск и расследование

**Формат.** Проектная основа архива - фрагментированный MP4 для проверенных сочетаний кодеков. Каждый завершённый блок имеет необходимую инициализацию декодирования, индекс временных границ, описание дорожек и контрольную сумму. Размер блока и гранулярность фрагментов внутри него определяются замерами поиска, записи и восстановления. Метаданные сегментов содержат идентификаторы камеры и источника, версию привязки, отметки времени, разрывы и поколение назначения узла.

**Фиксация.** Запись идёт во временный каталог на томе архива. Узел завершает контейнер, синхронизирует файл, манифест и каталог блока с носителем, атомарно переименовывает каталог и синхронизирует родительский каталог. Локальный журнал фиксирует завершённый блок. Каталог площадки принимает его идемпотентно по идентификатору и поколению владельца. При перезапуске узел сверяет журнал с томом, повторно регистрирует завершённые блоки и изолирует повреждённые. Неполные интервалы имеют явный статус. Каталог восстанавливается из проверенных манифестов и резервной копии прав и политик.

**Копии и сроки.** Базовое хранилище - локальная файловая система Linux. Для дополнительной копии предусмотрен независимый файловый пул, объектный API рассматривается для внешних копий после испытаний загрузки, проверки целостности и восстановления. Каталог различает наличие локальной, проверенной дополнительной и внешней копии. Копия считается проверенной после чтения и сверки контрольной суммы на целевом хранилище. Индексы и превью имеют свои сроки хранения.

**Очистка и защита.** Защита интервала расследования блокирует обычную очистку. До физического удаления каталог в одной транзакции проверяет срок и отсутствие защиты, затем фиксирует назначение на удаление. Защита и назначение на удаление одного блока взаимоисключающи. Служба очистки удаляет только назначенные экземпляры и фиксирует исход по каждой копии. При запросе защиты во время удаления интерфейс показывает фактически сохранённое покрытие. Поздняя догрузка наследует защиту интервала. Статус защиты от очистки и число проверенных копий отображаются раздельно. При исчерпании места применяются правила переключения или остановки с тревогой и фиксацией пропуска. Операции очистки и диагностики используют выделенный резерв места.

**Поиск.** Сначала выбираются разрешённые ресурсы и временные диапазоны. PostgreSQL хранит интервальные индексы и группирует записи по времени и источнику. Детекторные события и траектории записываются пакетно с версией детектора и отметкой полноты индекса. Локальный просмотр по интервалу остаётся доступен при недоступности поиска по детекциям. Площадка отправляет по узкой сети события и разрешённые превью, запрашиваемое видео передаётся отдельно. Догрузка с камеры сопоставляет доступные интервалы, заполняет пропуски и сохраняет происхождение записи. Перекрытия различаются по источнику и качеству, а обработка повторной догрузки идемпотентна.

**Расследование.** Пакет экспорта содержит запись, манифест с источниками, периодами, пропусками, контрольными суммами и преобразованиями, а также цифровую подпись. Оригинал и версия с масками выдаются по разным полномочиям. Подпись подтверждает целостность и происхождение пакета от площадки. Получатель проверяет её автономно с доверенным ключом. Снятие защиты и выдача копии фиксируются в аудите.

## 6. События, реакции и команды

Наблюдение содержит устойчивый идентификатор, источник, тип и версию схемы, время источника и приёма, ссылку на ресурс, происхождение и атрибуты. Для источников с поддержкой подтверждений приём подтверждается после устойчивой записи наблюдения. Для остальных адаптер отмечает известные пропуски и периоды, за которые полноту установить невозможно. Транзакция изменения состояния приложения записывает связанное событие в outbox. Потребитель сохраняет идемпотентный результат и факт обработки одной транзакцией, затем подтверждает чтение транспорту. Для журналов периферии задаются квоты, курсоры и срок повторной доставки. Порядок обработки контролируется по ключу источника или агрегата. Корреляция между источниками учитывает поздние события и неопределённость времени.

Один и тот же контракт событий действует для локальной доставки и Kafka. PostgreSQL остаётся владельцем состояния тревог и команд. В кластере Kafka при её наличии обслуживает независимые группы потребителей. Повторы доставки обрабатываются на границе исполнения. При недоступности брокера локальный путь ведения тревог сохраняется. Внешние подписчики получают собственные курсоры и ограниченный объём истории. При превышении лимита отстающий подписчик получает признак разрыва и возобновляет работу со снимка состояния и соответствующего курсора. Невосстановимые события за пропущенный интервал отмечаются отдельно. Для записи локальных тревог зарезервированы место и пропускная способность.

Версионируемые правила коррелируют движение, дым, огонь, доступ, показания датчиков и выводы видеоаналитики. Симуляция и переобработка читают тот же формат событий в изолированном режиме без отправки команд и оповещений. Разделяются фактическое наблюдение, вывод модели и подтверждение оператора. Тревога имеет очередь, приоритет, назначение, сроки эскалации, историю и основание закрытия. [Концепт, видео и события](concept.md#32-видео-события-и-география)

Команда хранит идентификатор запроса, исполнителя, целевой ресурс, параметры, срок действия, результат авторизации и статус. Исполнитель повторно проверяет срок, право и назначение владельца перед отправкой. Платформа различает ожидание, отправку, подтверждение устройства, наблюдаемый эффект и неопределённый результат.

**Повтор команды.** В пределах площадки ключ состоит из идентификаторов инициатора и запроса. Вместе с ключом сохраняется отпечаток параметров. Авторизованный повтор с теми же параметрами возвращает сохранённый статус, с изменёнными параметрами отклоняется. До обращения к устройству фиксируется попытка отправки. После сбоя между отправкой и фиксацией ответа исход считается неизвестным. Для устройства с дедупликацией повтор возможен с тем же ключом в пределах подтверждённого срока его действия. Для неидемпотентного действия без такой поддержки исполнитель запрашивает доступное состояние. Если исход остаётся неизвестным, новое действие требует явного решения уполномоченного исполнителя и отдельной записи в журнале. PTZ использует приоритет и ограниченное по времени владение, а исходящая сессия управления проверяет право владельца на каждое действие. Доступ к исполнительным функциям СКУД, громкоговорителей и других устройств проходит через тот же контроль.

## 7. Отказоустойчивость и восстановление

**Владение.** Одиночный узел блокирует параллельный запуск экземпляра записи локальной блокировкой. Назначение в кластере содержит владельца, поколение и ограниченный срок. Каталог принимает новые блоки только по действующему назначению. Передача назначения требует подтверждённой изоляции прежнего узла либо истечения его срока с запасом на допустимую погрешность времени. Узел контролирует срок монотонным таймером, который учитывает приостановку системы. Блоки разных поколений имеют отдельные идентификаторы. Поздние блоки сверяются как догрузка с проверкой происхождения и перекрытий. После восстановления базы из копии новые назначения получают уникальный идентификатор эпохи восстановления. До их выдачи прежних владельцев изолируют или ждут истечения старых полномочий. Переключение исполнителя команд требует подтверждения изоляции прежнего пути управления. До подтверждения исполнение приостанавливается.

**Хранилище управления.** Опорная топология HA - PostgreSQL с Patroni, кворумом etcd в трёх независимых доменах и проверенным механизмом изоляции прежнего ведущего узла. Профиль, рассчитанный на сохранность подтверждённых транзакций при потере ведущего узла, подтверждает запись после фиксации WAL на синхронной реплике в отдельном домене. При потере этой реплики строгий синхронный режим блокирует подтверждение новых записей до восстановления резерва. Режим репликации и поведение при деградации определяются политикой отказоустойчивости. Резервные копии базы и WAL проверяются восстановлением на отдельно развёрнутом узле. [Режимы репликации Patroni](https://patroni.readthedocs.io/en/latest/replication_modes.html) · [Изоляция через watchdog](https://patroni.readthedocs.io/en/latest/watchdog.html)

Исполнитель начинает работу по новому назначению или отправляет команду после подтверждения записи соответствующего состояния. При неопределённом результате фиксации он сверяет состояние на действующем ведущем узле и получает подтверждение записи до внешнего действия. Автоматическая передача владения требует сохранности подтверждённых назначений и попыток отправки при смене ведущего узла. Если профиль допускает их потерю, переназначение и возобновление команд требуют изоляции прежнего исполнителя и сверки. Утраченный ответ устройства сохраняет статус неопределённого исхода.

| Отказ | Поведение | Проверка после восстановления |
| --- | --- | --- |
| Камера или сеть камеры | Записывается разрыв, контролируется возврат потока | Догрузка из доступного архива камеры. Проверка источника, времени и отсутствия дубликатов |
| Процесс записи или узел | Перезапуск либо смена владельца при наличии ресурсов и права записи | Новая запись и чтение старого архива проверяются отдельно. История доступна по проверенной копии |
| Диск, том или питание | Переключение на предусмотренный пул. При его отсутствии - тревога и видимый пропуск | Сверка манифестов, контрольных сумм и непрерывности. Уникальные утраченные блоки помечаются недоступными |
| PostgreSQL или кворум площадки | Изменения политик и команды, требующие подтверждения состояния, приостанавливаются. Одиночный узел продолжает запись по применённой конфигурации в пределах ресурсов тома и журнала. Кластер пишет в пределах подтверждённого срока владения | Сверка поколений, журналов и полноты каталога. Удаление продолжается после восстановления актуальной политики |
| Поиск, аналитика или кэш | Просмотр по камере и интервалу использует каталог архива. Отставание индекса и аналитики видно пользователю | Восстановление из архивных манифестов, сохранённых событий и данных модулей |
| Центр федерации, внешний IdP или SaaS | Локальная запись и локальные роли работают автономно. Внешние функции показывают недоступность или неполноту данных | Синхронизация по курсорам. Повторная проверка сроков, прав и намерения перед выполнением |
| Площадка | Восстановление на подготовленной площадке по резервным копиям и ключам. Объём видео определяется фактически защищёнными интервалами | Проверка доступа, воспроизведения и цепочки аудита до возврата к эксплуатации |

В проекте установки отдельно задаются RPO и RTO для новой записи, исторического архива, конфигурации, тревог и аудита. RTO возобновления записи включает обнаружение отказа, передачу права владения, подключение к камере и ожидание точки декодирования. RPO внешней копии зависит от времени устойчивой записи и отставания репликации. Для асинхронной защиты измеряется фактическое отставание. Сохранность от удаления и отказа площадки требует независимой копии с отдельными полномочиями и политикой хранения. Резервирование дисков покрывает определённые отказы массива. План восстановления задаёт проверяемый порядок восстановления доверия и ключей, базы и каталогов, томов, а затем сервисов.

После восстановления на прошлый момент времени площадка сверяет каталог из резервной копии и WAL с манифестами доступных блоков. Более поздние ограничения хранения и отзывы доступа восстанавливаются из независимого журнала, если он доступен в выбранном профиле. Пока полнота политик по ресурсу не подтверждена, очистка и выдача медиа приостановлены и для локальных, и для удалённых получателей. При пробеле в истории администратор заново задаёт доступ и подтверждает ограничения хранения. Курсоры и запросы на исполнение из прежней эпохи восстановления теряют силу. Возобновление команд требует сверки с журналом исполнения, при потере сведений о попытке применяется режим неизвестного исхода. [Восстановление PostgreSQL на момент времени](https://www.postgresql.org/docs/current/continuous-archiving.html)

## 8. Федерация и внешние интеграции

Центр управления федерацией ведёт членство, доверие, согласованную топологию и версии общих политик. Площадка объявляет доступные функции и область обмена. Установление доверия связывает идентичность площадки с её сертификатом и разрешёнными ресурсами. В опорной топологии коннектор устанавливает исходящее mTLS-соединение из сети площадки. Видео запрашивается у площадки через разрешённый медиапуть. Центр хранит минимально необходимые проекции и показывает полноту ответа, последнюю синхронизацию и источники результатов.

Обновление политики имеет версию, область и порядок разрешения локальных исключений. Площадка валидирует и применяет политику локально, сообщает результат по каждому ресурсу и сохраняет предыдущую применимую версию. Поток синхронизации возобновляется по курсору. После истечения доступного диапазона площадка передаёт новый снимок разрешённого состояния. Локальные полномочия действуют при разрыве связи. Делегированные полномочия ограничены сроком и отзываются локально при выходе площадки из федерации. Запрос на исполнение содержит отдельный срок и переоценивается на площадке.

В копии метаданных центра ключ ресурса включает идентификатор площадки. Выдача закэшированного результата требует действующих полномочий пользователя и актуального разрешения площадки на соответствующий ресурс и представление. После истечения автономного срока центр исключает ресурс из поиска, счётчиков и превью. Повторное подключение начинается со сверки отзывов и актуальной области обмена.

СКУД, пожарные системы, датчики, громкоговорители и PSIM подключаются через адаптеры. Матрица возможностей разделяет чтение состояния, подписку и разрешённые действия. PSIM получает нормализованные события, ссылки на разрешённый материал и результаты команд. Площадка ведёт запись, проверяет доступ и обслуживает запросы к устройствам. Обязательные пожарные реакции выполняет профильная система. Миграция использует инвентаризацию, тестовую группу, контролируемое переключение записи и доступ к историческим интервалам через исходную систему или проверенный импорт. [Интеграции в концепте](concept.md#5-федерация-и-интеграции)

## 9. Расширения и подключаемый SaaS

Встроенный компонент разделяет цикл выпуска ядра. Сторонний адаптер или ресурсоёмкий модуль запускается в изолированном процессе с собственным бюджетом ресурсов и ограничениями исходящей сети. Тот же межпроцессный контракт позволяет вынести модуль на отдельный узел с mTLS. Манифест описывает версию и совместимость, объявленные функции, разрешения, конфигурацию, хранилище, квоты и миграцию. Установка проверяет подпись. Активация выдаёт ограниченные полномочия. Остановка отзывает доступ и отражается в состоянии зависимых функций.

Модуль получает событие, метаданные либо ограниченный доступ к медиа через площадку. Расширение рабочего места проходит через контролируемые представления и действия. Для интегратора предусмотрены схемы, эталонный адаптер, имитатор и проверки совместимости. Совместимые изменения схем добавочны. Несовместимые изменения вводятся отдельной версией с явной договорённостью о переходе.

Результат детектора связывается с устройством, интервалом, версией модели или прошивки, конфигурацией и местом выполнения. Планировщик различает текущую обработку и повторный анализ архива, хранит прогресс и ограничивает нагрузку каждого задания. Повторный анализ создаёт результаты со своим происхождением. Публикация этих результатов в действующие правила требует отдельной политики. При переносе модуля на другой узел новый экземпляр возобновляет задание с устойчивой позиции после передачи владения.

SaaS подключается и из Basic. Локальный коннектор связывает одну установку, арендатора и назначение модуля. Передача требует разрешения на класс данных, регион, срок хранения и канал обмена согласно политике площадки. Сначала передаются метаданные, медиа - по отдельному разрешению на конкретный интервал. Задания ограничены квотой и сроком. При недоступности услуги интерфейс показывает состояние очереди. При возобновлении коннектор переоценивает доступ и актуальность. Выход из услуги предусматривает отзыв ключей, отмену ожидающих заданий, выгрузку нужных результатов и согласованное удаление удалённых данных.

## 10. Безопасность и исполнители

- **Идентичность.** TLS для клиентских соединений, mTLS для межузловых соединений и федерации. На одном узле доверие между процессами опирается на отдельные системные учётные записи и защищённые сокеты. Локальные администраторы и дежурные имеют автономный вход. Для паролей используется Argon2id через проверенную библиотеку, для MFA предусматриваются WebAuthn или локальный TOTP. Веб-клиент получает серверную сессию. Внешний IdP подключается по Authorization Code с PKCE и проверкой доверенного издателя. Аварийная учётная запись защищена, проверяется при учениях и оставляет аудит. [Argon2](https://www.rfc-editor.org/info/rfc9106/) · [WebAuthn](https://www.w3.org/TR/webauthn-2/)
- **Авторизация.** RBAC назначает действия, ABAC ограничивает их площадкой, зоной, ресурсом, временем и контекстом. Решение проверяется при фильтрации, подписке, выдаче медиа, экспорте и непосредственно перед исполнением команды. Доступ по умолчанию закрыт. Для активного видео и подписок задаются срок разрешения и максимальная задержка отзыва. Источники, счётчики, превью и уведомления фильтруются теми же правилами.
- **Маски и аудио.** Сервер применяет политику к эфиру, архиву, превью, экспорту и данным для модулей до передачи получателю. Разрешение определяет вариант изображения и право на аудиодорожку. При отказе маскирования доступно только уже подготовленное разрешённое представление, иначе выдача приостанавливается. Ключ кэша учитывает представление, версию маски и область доступа. Монтажник проверяет маски при изменении геометрии кадра и настройке PTZ.
- **Границы доверия.** Камерная сеть, управление, операторские интерфейсы и исходящие интеграции имеют раздельные политики. Протокольные парсеры камеры и адаптеры обрабатывают вход в изолированных процессах. Устройства с ограниченной поддержкой шифрования допускаются по политике в выделенном сегменте. Секреты устройств выдаются только их адаптерам, обновляются по управляемой процедуре и исключаются из журналов.
- **Данные и аудит.** Архив, индексы и копии шифруются по политике, ключи резервируются отдельно. Для копий допускаются отдельное хранилище ключей или KMS. Действия, решения авторизации и результаты коррелируются по идентификаторам. Аудит имеет отдельные полномочия на запись и чтение, контроль целостности и защищённый резерв для критичных операций. Политика отказа при недоступности аудита блокирует критичные действия и сохраняет запись в пределах ресурсов.
- **Восстановление доверия.** Сертификаты узлов и ключи подписи имеют версии и процедуру ротации с периодом перекрытия. Публичные ключи проверки исторических экспортов сохраняются с данными о сроке доверия и отзыве. Для площадок с защитой от потери узла или всей площадки изменения ограничений хранения и отзывов доступа сохраняются в журнале в соответствующем независимом домене отказа. В режиме сохранности подтверждённых ограничений успешный ответ требует фиксации в этом домене. При асинхронном копировании риск потери последних изменений учитывается в RPO.
- **ИИ и сервисные исполнители.** Агент имеет отдельную короткоживущую идентичность, роль, область ресурсов и лимиты. Модель получает только разрешённые данные. Вывод преобразуется в типизированный запрос и проверяется исполнителем. Подтверждение человека для критичного действия привязано к параметрам, ресурсу и сроку действия. Аудит фиксирует инициатора, агента, версию модели и политики, подтверждение и исход. Текст, метаданные устройств и медиа обрабатываются как входные данные.

## 11. Интерфейс, поставка и эксплуатация

Веб-клиент сохраняет контекст площадки, точки наблюдения, тревоги и интервала между экраном, картой и архивом. API отдаёт состояние применения конфигурации, доступные действия и причины ограничения. Начальная выборка тревог возвращается с курсором того же снимка. После переподключения клиент дочитывает изменения с курсора, применяет версии объектов и при истечении истории загружает новый снимок. Принятие тревоги в работу проверяет текущую версию, поэтому при одновременном действии двух дежурных оба увидят одного ответственного. Сеанс медиа получает собственное ограниченное разрешение. В мобильном браузере монтажник проверяет ракурс и тестовую запись, а дежурный принимает тревогу в сети заказчика. Необходимость отдельного клиента для плотной видеостены решается по замерам.

Мастер запуска проверяет сеть, синхронизацию времени, носитель, совместимость устройств и тестовый цикл запись -> чтение. Автономный комплект содержит подписанные пакеты, зависимости и локальные ресурсы интерфейса. Аппаратная поставка использует те же форматы конфигурации и резервной копии. Для платных локальных модулей предусматривается автономная проверка подписанного разрешения. Обновление включает проверку версий и места на диске, резервную копию, контрольную запись и проверку чтения. Кластер обновляется по узлам с резервом под перенос нагрузки. Миграции базы сначала сохраняют совместимость на период совместной работы версий. Процедура восстановления учитывает этап, после которого возврат требует восстановления копии.

Сигналы эксплуатации включают время до первого кадра, задержку тревоги, свежесть детекций, пропуски архива, возраст последней подтверждённой записи, фактическую глубину хранения, пиковый трафик, заполнение, задержку репликации и остаток бюджета. На каналах с ожидаемой записью фоновая проверка выбирает свежий завершённый блок через штатный каталог, читает его и проверяет декодирование контрольного кадра. Доступность камеры, факт записи и успешное воспроизведение имеют отдельные статусы. Сквозная диагностика связывает ресурс, запись, событие, правило, команду и результат. Технические журналы, метрики и трассировка исключают секреты и медиа. В изолированной сети достаточно локальной диагностики и выгрузки отчёта по разрешению администратора. Поставка включает SBOM и проверку подписей обновлений и модулей.

## 12. Проверка архитектуры

| Сценарий | Критерий проверки |
| --- | --- |
| Компактный узел | Смешанная нагрузка записи, просмотра, событий и чтения архива на минимальном оборудовании. Фиксируются CPU, память, I/O и пропуски |
| До 100 камер | Непрерывная запись при 2 и 4 Мбит/с на камеру, параллельный просмотр и поиск. Основной входной поток составляет 200 и 400 Мбит/с соответственно. Полезный объём за 30 суток составляет 64,8 и 129,6 ТБ до копий и накладных расходов |
| Смешанная нагрузка и N-1 | Нагрузку измеряют при выводе узла, перестроении индекса, массовом экспорте и догрузке. Защищённый режим проверяется при потере домена, заданного в проекте установки |
| Задержки и удобство | Для первого кадра, тревоги и первой страницы поиска ориентир пилота - до 2 с по p95 при заданной нагрузке. Измеряются p50, p95, p99, ошибки и время выполнения задач оператором и монтажником |
| Целостность и восстановление | Моделируются внезапное выключение на разных этапах фиксации, заполнение тома и повреждение сегмента. При восстановлении на чистой машине измеряются потери и время возобновления, проверяется чтение защищённых копий |
| Разделение сети и команды | Остановка исполнителя после отправки команды до записи ответа, повтор исходного запроса и смена владельца. Если устройство не поддерживает дедупликацию и установить исход нельзя, число автоматических повторных отправок равно нулю |
| Изоляция и обновление | Локальный вход и работа без WAN, отозванные разрешения на активном видео, закрытые результаты поиска, недоступность модулей, совместная работа соседних версий и откат по проверенной процедуре |
| Частичное восстановление архива | Защитить интервал и отозвать доступ после создания копии базы, затем восстановить базу из этой копии. До сверки очистка и выдача затронутого материала заблокированы. После сверки защищённый материал читается уполномоченным субъектом, отзыв действует |
| Приватность при отказе | При остановке маскирования эфир, превью и экспорт не выдают получателю кадры без обязательной маски. После отзыва права на аудио активный сеанс прекращает выдачу звука в заданный срок. После истечения делегированных прав ресурс исчезает из поиска центра и счётчиков |
| Медленный потребитель | Остановить чтение у медиаклиента и у внешнего подписчика событий. При штатном входном потоке и доступном диске архив сохраняет интервалы, локальная тревога проходит, память и очереди остаются в бюджете. После восстановления подписчик видит границу пропуска |
| Конкурентные операции | Совместить защиту интервала с очисткой, подключение дежурного с новой тревогой и принятие одной тревоги двумя дежурными. Проверить фактическое покрытие защиты, полноту очереди и единственного ответственного |

Порядок реализации - локальный сквозной контур -> эксплуатация и восстановление -> управление кластером и федерация -> отдельные подсистемы и SaaS. До фиксации профилей подтверждаются параметры сегментации, предельное число потоков и клиентов, задержки, резерв N-1, RPO и RTO. Для Kafka, Redis и отдельного поискового двигателя нужны замеры под смешанной нагрузкой и оценка стоимости сопровождения. Для политик владения и отзыва доступа нужны испытания при разделении сети. Решения, зависящие от этих результатов, фиксируются отдельно после проверки.
