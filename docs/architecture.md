# Bacuri VMS Platform architecture

[Русская версия](ru/architecture.md)

- **Technical name** - `bacuri-vms`.
- **Document status** - architecture draft.
- **Accepted** - C++23 for server code, supported Debian releases on x86-64, autonomous on-premises installation, federation of independent installations and optional SaaS modules.

## 1. Architecture model

The Core boundary follows the obligations of an autonomous site. A Core domain can be extracted from the modular monolith into a service. A pluggable component can grow into a separate subsystem. Data ownership, permissions and guarantees are kept when the placement changes. Event-based interaction and Event Sourcing are chosen for each domain independently. [ADR-018. Core and pluggable module boundary](adr/018-core-module-boundary.md)

A site is the unit that owns devices, data, policies and recovery. In the simple profile, one node runs the modular control core and separate processes for recording and video delivery. In a cluster the same components are distributed across nodes. They share source code, data models and contracts. An external federation center serves independent sites through a metadata stream and restricted operations.

The paths have different requirements under failure. Recording relies on local storage and the last applied configuration. Viewing has its own decoding and outbound traffic limits. Control stores the desired configuration and the actual state of its application. Search and analytics may lag and state how current they are. Revocation of access and execution of commands are checked in the path that delivers data or controls a device.

```text
Cameras -> stream ingest -> site archive -> recording delivery -> workplace
Stream ingest -> live delivery -> workplace
Detectors and adapters -> event journal -> rules and alarms -> workplace
Control core -> configuration and stream assignment -> site processes
Site -> permitted metadata -> federation center / PSIM / SaaS
External request -> site entry -> permission and validity check -> local execution
```

## 2. Components and data owners

| Component | Responsibility | Durable state |
| --- | --- | --- |
| Control core | Resource catalog, device binding, site maps and plans, policies, roles, configuration, stream placement, REST API | PostgreSQL. Transactions are limited to the site |
| Ingest and recording | Camera sessions, main and secondary streams, segment storage, backfill from cameras | Archive files and the local commit journal. The recording catalog in PostgreSQL |
| Media delivery | Live and playback sessions, copy selection, masking and on-demand transformation | Short-lived sessions. The archive and export results live in storage |
| Video events, rules and alarms | Normalization of video events, recording and notification rules, rule testing on the archive, the video alarm queue and operator history | Observation journal, video rule versions and video alarm state |
| Command execution and adapters | Device capability checks, arbitration, sending and observing the result | Command journal in the core. The external device remains the source of the observed physical state |
| Search and investigations | Timeline, geographic filters, detection index, bookmarks, protection and export | Materials and retention restrictions in PostgreSQL. Rebuilding the index is limited by the retention of the source detections and manifests. Previews are restored from available video |
| Federation control center | Site registry and trust, policy distribution, summary, federated search and diagnostics | The center's own storage with permitted projections of site data |
| Background jobs | Replication, integrity verification, export, analytics, integrations | Job state, progress and retry control at the job owner |

The model distinguishes the site, the observation point, the physical device, the channel and the stream profile. A point keeps its identifier when the camera is replaced. History binds every interval to a specific channel and the revision of its binding. Geography, detection zone and rule version are resolved at the time of the event. Observations, alarms, commands and investigation materials have their own identifiers and links. Configuration changes are stored as versions with results of application per resource.

Bulk configuration stores the expected version and the result for every resource. A conflict between two editors returns the current version. A retry after a broken connection continues unfinished operations with the same identifier. The administrator sees where a camera already applied a template, where actual settings need reconciliation and which changes can be rolled back.

On a single node the core combines control, rules, alarms and the search API. Recording and delivery run as separate processes. Inside the core each module owns its state and offers operations to other modules through an interface. Processes and third-party extensions use authorized APIs. Binary recordings, detector metadata and user permissions have separate access and retention rules.

### Site scenario contracts

The administrator registers a camera through the core. Only the recording node confirms the applied version, and only reading a published block allows the first archive frame to be shown. The operator receives an alarm from the core state. Permission and the archive link are checked when opened, and the fact of delivery and the end of the stream are observed on the media delivery side. The browser owns the point selection, the position and the focus. [Architecture and data criteria](quality.md#acceptance-requirements)

In an architecture review a change is traced from the action of a role to the data owner and back to the observable result. The review checks which dependency may fail, what bounds memory and waiting time, how a repetition affects data and how the cause can be found from diagnostics. Changing the state owner, the delivery guarantee or the permitted behavior on failure requires revising the corresponding ADR and testing the affected scenarios again. ## 3. Topologies and base stack

[ADR-015 on technology selection and maintenance](adr/015-technology-lifecycle.md) applies to the whole platform. Selecting an implementation checks the supported version, compatibility with the target profile, behavior on failure and the upgrade path. These requirements apply to development tools and to external integrations as well.

| Profile | Required topology | Optional components |
| --- | --- | --- |
| Compact | One node, control, recording and delivery processes, local PostgreSQL, local disk | Local detectors within a set budget, a supported external copy |
| Single server | The same roles on a server, a separate archive volume, separate limits for recording, viewing and background jobs | GPU, a standby pool, a separate integration or analytics server |
| Cluster | Highly available control and PostgreSQL, distributed recording and delivery nodes, storage in defined failure domains | Dedicated nodes for decoding, indexing, analytics, copying, Kafka and external modules |

The deployment profile determines topology and resources. The first release targets one node. Each site can work on its own or join a federation. The cost of a cluster and the loss of throughput in N-1 mode are checked by role and failure domain, including power, network and disks.

Stream placement considers camera reachability from the node network, bandwidth, free space and the decoding budget. Recording usually goes to the disk of the node that receives the stream. Separate nodes are added for delivery and analytics as the corresponding budget is exhausted. Moving and rebalancing take into account the inbound connection limits of a camera and the current failover reserve.

In a cluster, clients and integrations use a stable site address with a redundant API entry. Core replicas restore sessions and operations from the shared durable state. A scheduler job gets one executor through a bounded assignment. After losing a delivery node the client opens a new media session on an available node with a new permission check. For the archive the client keeps the playback position.

## 4. Devices, ingest and media delivery

1. The adapter discovers a device in a permitted segment or takes an address from the inventory. The connection result includes reachability, firmware, declared and tested capabilities, clock, codecs, stream profiles and the results of a test recording. ONVIF Profile T, G and M apply to the supported functions. A camera with one RTSP stream can be entered manually with a check of its actual capabilities. Replacing a camera goes through a compatibility check of bindings and masks before switching. [ONVIF profiles](https://www.onvif.org/profiles/)
2. The recording node opens one inbound session per used profile in normal operation. The stream is split inside the node. The main profile is usually recorded in its original encoding. The secondary profile serves layouts and low bandwidth. The viewing or analytics queue has its own limit and may drop frames under overload. Manual recording, schedules and triggers meet in one policy. Pre-event recording uses a bounded buffer and available decoding points.
3. The delivery server receives a permission for a specific stream, interval and representation. For live video the reference browser compatibility is negotiated H.264 and Opus when there is audio. H.265 may be kept in the archive in its original encoding. For live video the server selects a compatible camera profile. For the archive it selects a compatible recording of the same interval or transcoding within a quota. The client sees the quality and availability of the selected variant. TURN is deployed in the customer network when needed. Browser paths and hardware acceleration modes are confirmed by the client and hardware matrix. A new live viewer starts with the frames received since the last keyframe, so the first frame does not wait for the next keyframe of the camera.
4. Playback is built around a shared time and a map of available intervals. Seeking to an arbitrary position uses the previous decoding point. Fast seeking, multi-camera viewing and export have separate limits. Recording marks changes of codec, resolution and configuration and discontinuities. To synchronize RTP streams the node uses RTP and NTP time pairs from RTCP reports when available. A clock jump or a camera restart opens a new interval of time binding. Without a reliable binding the timeline shows an estimate based on reception time and its uncertainty. Schedules apply in the time zone of the site. [RTP and RTCP synchronization](https://www.rfc-editor.org/rfc/rfc3550.html#section-6.4.1)

The ingest node passes compressed data to the delivery and analytics processes over a local inter-process channel, and to a remote node over an authenticated encrypted media connection. The delivery node serves the viewers. Each consumer has its own bounded queue. A slow viewer may lose frames until the next decoding point. When the queue of the recording itself is exhausted the system records the lost interval and raises an alarm. A block that reaches its limits without a keyframe is closed and the frames until the next keyframe are recorded as a gap. CPU, GPU, memory, disk and network budgets are checked before starting expensive jobs. [Stream splitting in GStreamer](https://gstreamer.freedesktop.org/documentation/coreelements/tee.html)

## 5. Archive, search and investigation

**Format.** The design basis of the archive is fragmented MP4 for verified codec combinations. Every complete block has the required decoder initialization, an index of time boundaries, a track description and a checksum. Block size and fragment granularity inside it are determined by measurements of search, recording and recovery. Segment metadata contains the camera and source identifiers, the binding revision, time stamps, discontinuities and the owner generation of the node. [Archive and export format](archive-format.md)

**Commit.** Recording goes to a temporary directory on the archive volume. The node finalizes the container, synchronizes the file, the manifest and the block directory with the medium, renames the directory atomically and synchronizes the parent directory. The local journal records the complete block. The site catalog accepts it idempotently by identifier and owner generation. On restart the node reconciles the journal with the volume using metadata only, registers complete blocks again and starts recording at once. A background verifier reads the blocks at a bounded rate, isolates damaged ones and repairs them from the second copy. Incomplete intervals have an explicit status. The catalog is restored from verified manifests and the backup of permissions and policies.

**Copies and retention.** The base storage is a local Linux file system. An independent file pool is provided for an additional copy, an object API is considered for external copies after tests of upload, integrity verification and restore. The catalog distinguishes a local, a verified additional and an external copy. A copy is verified after reading and comparing the checksum on the target storage. Indexes and previews have their own retention.

**Cleanup and protection.** Protection of an investigation interval blocks regular cleanup. Before physical removal the catalog checks expiry and the absence of protection in one transaction and then records the assignment for removal. Protection and assignment for removal of one block are mutually exclusive. The cleanup service removes only assigned instances and records the outcome for each copy. When protection is requested during removal the interface shows the coverage actually kept. Late backfill inherits the protection of the interval. Protection from cleanup and the number of verified copies are shown separately. When space runs out, rules for switching or stopping with an alarm and a recorded gap apply. Cleanup and diagnostics use a dedicated space reserve.

**Search.** Permitted resources and time ranges are selected first. PostgreSQL stores interval indexes and groups recordings by time and source. Detector events and tracks are written in batches with the detector version and an index completeness mark. Local viewing by interval stays available when detection search is unavailable. Over a narrow network the site sends events and permitted previews, and requested video is transferred separately. Backfill from a camera matches available intervals, fills gaps and keeps the provenance of the recording. Overlaps are distinguished by source and quality, and repeated backfill is idempotent.

**Investigation.** An export package contains the recording, a manifest with sources, periods, gaps, checksums and transformations, and a digital signature. The original and the masked version are issued under different permissions. The signature confirms the integrity of the package and its origin from the site. The recipient verifies it offline with a trusted key, with Bacuri tools or with standard tools. Removal of protection and issue of a copy are recorded in the audit.

The archive retention policy applies to the site. PostgreSQL computes the boundary from UTC and the retention period, records the highest confirmed boundary and excludes blocks that ended before it from search, part delivery and navigation from alarms. A block that crosses the boundary is kept whole until its end expires. The recorder receives the boundary after the catalog transaction commits, stores it in SQLite, renames the directories of expired blocks and removes the files. Synchronizing the file system directory precedes removing journal rows. After a restart the operation continues from the stored boundary. [Configuration and diagnostics](ui.md#archive-retention)

## 6. Events, reactions and commands

An observation contains a durable identifier, the source, type and schema version, source and reception time, a reference to the resource, provenance and attributes. For sources that support acknowledgements, reception is acknowledged after the observation is durably written. For others the adapter marks known gaps and periods whose completeness cannot be established. A transaction that changes application state writes the related event to the outbox. A consumer stores its idempotent result and the fact of processing in one transaction and then acknowledges the read to the transport. Peripheral journals have quotas, cursors and a redelivery period. Processing order is controlled by source or aggregate key. Correlation across sources accounts for late events and time uncertainty.

The same event contract applies to local delivery and Kafka. PostgreSQL remains the owner of alarm and command state. In a cluster, Kafka, when present, serves independent consumer groups. Delivery repetitions are handled at the execution boundary. When the broker is unavailable, the local alarm path is kept. External subscribers get their own cursors and a bounded history. A subscriber that falls behind the limit receives a gap mark and resumes from a state snapshot and the matching cursor. Unrecoverable events of the missed interval are marked separately. Space and throughput are reserved for recording local alarms.

Versioned VMS rules process camera and video detector events and control recording and post notification. Through an adapter a permitted external event can be linked to a point and a video interval. Simulation tests a rule on the archive in isolation. A video alarm card shows the source, the owner, the time, the result and history. An external PSIM owns cross-system incidents, escalation and coordination of services.

A command stores the request identifier, the actor, the target resource, parameters, validity period, the authorization result and status. The executor checks validity, permission and the owner assignment again before sending. The platform distinguishes waiting, sending, device confirmation, observed effect and an unknown result.

**Command repetition.** Within a site the key consists of the initiator and request identifiers. A fingerprint of parameters is stored with the key. An authorized repetition with the same parameters returns the stored status, with changed parameters it is rejected. The attempt to send is recorded before contacting the device. After a failure between sending and recording the response, the outcome is unknown. For a device with deduplication, repetition is possible with the same key within its confirmed validity. For a non-idempotent action without such support the executor queries the available state. If the outcome remains unknown, a new action requires an explicit decision of an authorized actor and a separate journal record. PTZ uses priority and time-bounded ownership, and an outgoing control session checks the owner's permission for every action. Access to executive functions of access control systems, loudspeakers and other devices goes through the same control.

## 7. Fault tolerance and recovery

**Ownership.** A single node prevents a parallel start of a recording instance with a local lock. An assignment in a cluster contains the owner, the generation and a bounded validity. The catalog accepts new blocks only under a valid assignment. Transferring an assignment requires confirmed isolation of the previous node or expiry of its validity with a margin for clock error. The node tracks validity with a monotonic timer that accounts for system suspension. Blocks of different generations have separate identifiers. Late blocks are reconciled as backfill with checks of provenance and overlaps. After the database is restored from a copy, new assignments receive a unique recovery epoch identifier. Before they are issued, previous owners are isolated or their old authority is left to expire. Switching the command executor requires confirmed isolation of the previous control path. Until it is confirmed, execution is suspended.

**Control storage.** The reference HA topology is PostgreSQL with Patroni, an etcd quorum in three independent domains and a verified fencing of the previous leader. A profile that preserves confirmed transactions when the leader is lost confirms a write after the WAL is committed on a synchronous replica in a separate domain. When this replica is lost, strict synchronous mode blocks confirmation of new writes until the reserve is restored. The replication mode and degraded behavior are set by the fault tolerance policy. Database and WAL backups are verified by restoring them on a separately deployed node. [Patroni replication modes](https://patroni.readthedocs.io/en/latest/replication_modes.html) · [Fencing with watchdog](https://patroni.readthedocs.io/en/latest/watchdog.html)

An executor starts work under a new assignment or sends a command after the write of the corresponding state is confirmed. With an uncertain commit result it reconciles the state on the current leader and obtains confirmation of the write before the external action. Automatic transfer of ownership requires that confirmed assignments and send attempts survive a change of leader. If the profile allows their loss, reassignment and resumption of commands require isolation of the previous executor and reconciliation. A lost device response keeps the status of an unknown outcome.

| Failure | Behavior | Check after recovery |
| --- | --- | --- |
| Camera or camera network | A gap is recorded, the return of the stream is monitored | Backfill from the available camera archive. Check of source, time and absence of duplicates |
| Recording process or node | Restart, or a change of owner when resources and write permission are available. Recording resumes before the archive is verified | New recording and reading of the old archive are checked separately. History is available from the verified copy |
| Disk, volume or power | Switching to the provided pool. Without one, an alarm and a visible gap | Reconciliation of manifests, checksums and continuity. Unique lost blocks are marked unavailable |
| PostgreSQL or site quorum | Policy changes and commands that require confirmed state are suspended. A single node keeps recording with the applied configuration within the volume and journal resources. A cluster records within the confirmed ownership validity | Reconciliation of generations, journals and catalog completeness. Removal continues after the current policy is restored |
| Search, analytics or cache | Viewing by camera and interval uses the archive catalog. Lag of the index and analytics is visible to the user | Restore from archive manifests, stored events and module data |
| Federation center, external IdP or SaaS | Local recording and local roles work autonomously. External functions show unavailability or incomplete data | Synchronization by cursors. Validity, permissions and intent are checked again before execution |
| Site | Recovery on a prepared site from backups and keys. The amount of video is determined by the intervals actually protected | Check of access, playback and the audit chain before returning to operation |

The installation design sets RPO and RTO separately for new recording, the historical archive, configuration, alarms and the audit. The RTO of resuming recording includes failure detection, ownership transfer, connection to the camera and waiting for a decoding point. The RPO of an external copy depends on the time of durable recording and the replication lag. For asynchronous protection the actual lag is measured. Protection against deletion and site failure requires an independent copy with separate permissions and retention policy. Disk redundancy covers certain array failures. The recovery plan sets a verifiable order: trust and keys, database and catalogs, volumes, then services.

After a point-in-time recovery the site reconciles the catalog from the backup and WAL with the manifests of available blocks. Later retention restrictions and access revocations are restored from an independent journal if one is available in the chosen profile. Until the completeness of policies for a resource is confirmed, cleanup and media delivery are suspended for local and remote recipients. With a gap in history the administrator sets access again and confirms retention restrictions. Cursors and execution requests from the previous recovery epoch lose validity. Resuming commands requires reconciliation with the execution journal, and when information about an attempt is lost the unknown outcome mode applies. [PostgreSQL point-in-time recovery](https://www.postgresql.org/docs/current/continuous-archiving.html)

## 8. Federation and external integrations

The federation control center keeps membership, trust, the agreed topology and versions of shared policies. A site announces its available functions and the scope of exchange. Establishing trust binds the identity of the site to its certificate and permitted resources. In the reference topology a connector opens an outbound mTLS connection from the site network. Video is requested from the site through a permitted media path. The center stores the minimum necessary projections and shows the completeness of a response, the last synchronization and the sources of results.

A policy update has a version, a scope and an order for resolving local exceptions. The site validates and applies the policy locally, reports the result for each resource and keeps the previous applicable version. The synchronization stream resumes by cursor. When the available range has expired the site sends a new snapshot of the permitted state. Local authority works while the connection is broken. Delegated authority is time-bounded and revoked locally when the site leaves the federation. An execution request carries its own validity and is re-evaluated on the site.

In the metadata copy of the center the resource key includes the site identifier. Serving a cached result requires valid user authority and a current permission of the site for the resource and representation. After the autonomous validity expires the center excludes the resource from search, counters and previews. Reconnection starts with reconciliation of revocations and the current scope of exchange.

Access control systems, fire systems, sensors, loudspeakers and PSIM are connected through adapters. The capability matrix separates reading state, subscription and permitted actions. PSIM receives normalized events, links to permitted material and command results. The site records, checks access and serves requests to devices. Mandatory fire reactions are executed by the dedicated system. Migration uses an inventory, a test group, a controlled switch of recording and access to historical intervals through the source system or a verified import.

## 9. Extensions and pluggable SaaS

A built-in component shares the release cycle of the core. A third-party adapter or a resource-intensive module runs in an isolated process with its own resource budget and outbound network restrictions. The same inter-process contract allows moving the module to a separate node with mTLS. A manifest describes the version and compatibility, declared functions, permissions, configuration, storage, quotas and migration. Installation verifies the signature. Activation grants bounded authority. Stopping revokes access and is reflected in the state of dependent functions.

A module receives an event, metadata or bounded access to media through the site. Extensions of the workplace go through controlled views and actions. Integrators get schemas, a reference adapter, a simulator and compatibility checks. Compatible schema changes are additive. Incompatible changes are introduced as a separate version with an explicit migration agreement.

A detector result is linked to the device, the interval, the model or firmware version, the configuration and the place of execution. The scheduler distinguishes current processing from re-analysis of the archive, stores progress and bounds the load of each job. Re-analysis creates results with their own provenance. Publishing them into active rules requires a separate policy. When a module moves to another node the new instance resumes the job from a durable position after ownership transfer.

A local site can connect SaaS modules. A local connector binds one installation, a tenant and the purpose of the module. Transfer requires permission for the data class, region, retention and exchange channel according to the site policy. Metadata is transferred first, media by separate permission for a specific interval. Jobs are bounded by quota and validity. When the service is unavailable the interface shows the queue state. On resumption the connector re-evaluates access and relevance. Leaving the service includes revoking keys, cancelling pending jobs, exporting needed results and agreed deletion of remote data.

## 10. Security and actors

- **Identity.** TLS for client connections, mTLS for inter-node connections and federation. On a single node trust between processes relies on separate system accounts and protected sockets. Local administrators and operators on duty sign in autonomously. Passwords use Argon2id through a verified library, MFA uses WebAuthn or local TOTP. The web client receives a server session. An external IdP is connected with the Authorization Code flow with PKCE and a check of the trusted issuer. The emergency account is protected, checked during drills and leaves an audit trail. [Argon2](https://www.rfc-editor.org/info/rfc9106/) · [WebAuthn](https://www.w3.org/TR/webauthn-2/)
- **Authorization.** RBAC assigns actions, ABAC restricts them by site, zone, resource, time and context. The decision is checked during filtering, subscription, media delivery, export and immediately before a command is executed. Access is closed by default. Active video and subscriptions have a permission validity and a maximum revocation delay. Sources, counters, previews and notifications are filtered by the same rules.
- **Masks and audio.** The server applies the policy to live video, archive, previews, exports and data for modules before transmission. The permission determines the image variant and the right to the audio track. When masking fails, only an already prepared permitted representation is available, otherwise delivery is suspended. The cache key includes the representation, the mask version and the access scope. The administrator checks masks when the frame geometry changes and when PTZ is configured.
- **Trust boundaries.** The camera network, control, operator interfaces and outbound integrations have separate policies. Camera protocol parsers and adapters process input in isolated processes. Devices with limited encryption support are admitted by policy in a dedicated segment. Device secrets are issued only to their adapters, rotated by a managed procedure and excluded from logs.
- **Data and audit.** The archive, indexes and copies are encrypted per policy, and keys are backed up separately. Copies may use a separate key store or KMS. Actions, authorization decisions and results are correlated by identifiers. The audit has separate write and read permissions, integrity control and a protected reserve for critical operations. When the audit is unavailable the refusal policy blocks critical actions and keeps recording within resources.
- **Trust recovery.** Node certificates and signing keys have versions and a rotation procedure with an overlap period. Public keys for verifying historical exports are kept with data about trust validity and revocation. For sites protected against the loss of a node or the whole site, changes of retention restrictions and access revocations are stored in a journal in the corresponding independent failure domain. In the mode that preserves confirmed restrictions a successful response requires a commit in that domain. With asynchronous copying the risk of losing the latest changes is accounted for in the RPO.
- **AI and service actors.** An agent has a separate short-lived identity, role, resource scope and limits. The model receives only permitted data. Its output is converted into a typed request and checked by the executor. Human confirmation of a critical action is bound to the parameters, the resource and the validity period. The audit records the initiator, the agent, the model and policy versions, the confirmation and the outcome. Text, device metadata and media are treated as input data.

## 11. Interface, delivery and operation

The web client keeps the context of the site, the observation point, the alarm and the interval between the screen, the map and the archive. The API returns the state of configuration application, the available actions and the reasons for restrictions. The initial alarm selection is returned with a cursor of the same snapshot. After reconnecting the client reads changes from the cursor, applies object versions and loads a new snapshot when history has expired. Taking an alarm into work checks the current version, so when two operators act at once both see one owner. A media session gets its own bounded permission. In a mobile browser the administrator checks the view and a test recording, and the operator on duty accepts an alarm in the customer network. Whether a separate client is needed for a dense video wall is decided by measurements.

The setup wizard checks the network, time synchronization, the storage medium, device compatibility and a test cycle of recording -> reading. The offline bundle contains signed packages, dependencies and local interface resources. Hardware delivery uses the same configuration and backup formats. Paid local modules can be checked offline with a signed license. An update includes version and disk space checks, a backup, a test recording and a read check. A cluster is updated node by node with a reserve for moving the load. Database migrations first keep compatibility for the period when versions run together. The recovery procedure accounts for the stage after which going back requires restoring a backup.

Operational signals include time to the first frame, alarm delay, freshness of detections, archive gaps, the age of the last confirmed recording, the actual retention depth, peak traffic, fill level, replication lag and the remaining budget. The recording state of a point is derived from the archive catalog and the recorder report: "recording" is shown only when a recently received frame is already in an available block. Camera reachability, the fact of recording and successful playback have separate states. End-to-end diagnostics link the resource, recording, event, rule, command and result. Technical logs, metrics and traces exclude secrets and media. In an isolated network local diagnostics and export of a report by permission of the administrator are sufficient. The delivery includes an SBOM and verification of signatures of updates and modules.

## 12. Architecture verification

| Scenario | Verification criterion |
| --- | --- |
| Compact node | Mixed load of recording, viewing, events and archive reading on minimal hardware. CPU, memory, I/O and gaps are recorded |
| Up to 100 cameras | Continuous recording at 2 and 4 Mbit/s per camera, parallel viewing and search. The main inbound stream is 200 and 400 Mbit/s respectively. The useful volume for 30 days is 64.8 and 129.6 TB before copies and overhead |
| Mixed load and N-1 | The load is measured while a node is removed, during index rebuilding, bulk export and backfill. The protected mode is checked by losing the domain set in the installation design |
| Delays and usability | For the first frame, the alarm and the first page of search the initial target is up to 2 s at p95 under the set load. The target level of the product is stricter. [Product principles](product-principles.md#2-operator-speed) An automatic run measures p50, p95, p99 and errors. In the acceptance of the first release the time of independent task completion by operators and administrators is measured in manual acceptance |
| Integrity and recovery | Sudden power-off at different stages of the commit, a full volume and a damaged segment are simulated. On recovery on a clean machine, losses and time to resume are measured, and reading of protected copies is checked |
| Network partition and commands | Stopping the executor after sending a command and before recording the response, repeating the original request and changing the owner. If the device does not support deduplication and the outcome cannot be established, the number of automatic resends is zero |
| Isolation and update | Local sign-in and operation without WAN, revoked permissions on active video, closed search results, unavailable modules, adjacent versions working together and rollback by a verified procedure |
| Partial archive recovery | Protect an interval and revoke access after creating a database backup, then restore the database from this backup. Until reconciliation, cleanup and delivery of the affected material are blocked. After reconciliation the protected material is readable by an authorized subject and the revocation is in effect |
| Privacy under failure | When masking stops, live video, previews and exports do not deliver frames without a required mask. After the audio permission is revoked an active session stops delivering sound within the set time. After delegated permissions expire the resource disappears from the search and counters of the center |
| Slow consumer | Stop reading at a media client and at an external event subscriber. With the regular inbound stream and available disk the archive keeps its intervals, the local alarm goes through, and memory and queues stay within budget. After recovery the subscriber sees the gap boundary |
| Concurrent operations | Combine interval protection with cleanup, an operator connecting with a new alarm and two operators accepting one alarm. Check the actual protection coverage, the completeness of the queue and the single owner |

Implementation order: local end-to-end path -> operation and recovery -> cluster control and federation -> separate subsystems and SaaS. Before the profiles are fixed, segmentation parameters, the maximum number of streams and clients, delays, the N-1 reserve, RPO and RTO are confirmed. Kafka, Redis and a separate search engine require measurements under mixed load and an estimate of maintenance cost. Ownership and revocation policies require tests under network partition. Decisions that depend on these results are recorded separately after verification.
