# План разработки видеоаналитики Bacuri VMS

**Статус плана** - Готово к приёмке.

Цель - серверная видеоаналитика площадки на OpenCV 5, которая работает круглосуточно без открытых клиентов, даёт одинаковый результат тревогам, поиску, экспорту и аудиту и повторяется на архиве. Аналитика уменьшает число ложных тревог, сообщает о неисправности и саботаже камеры, ускоряет поиск в архиве и обезличивает выдаваемые копии. Распознавание личности по биометрическим признакам в план не входит. Размещение и границы компонентов определяет [ADR-021](adr/021-video-analytics.md). Статус реализации каждого шага определяется отдельно по его результату и испытаниям. [План платформы](devplan.md) · [План настольного клиента](devplan-desktop.md)

## Принципы

| Принцип | Правило |
| --- | --- |
| Запись важнее анализа | Сбой, перегрузка или обновление сервиса не задерживают запись и эфир. Сервис получает кадры по ограниченной подписке и пропускает их при отставании, а не накапливает |
| Повторяемость | Один и тот же архив с той же версией анализатора и правила даёт те же наблюдения и метаданные. Версии анализатора, модели и правила сохраняются в каждой записи |
| Честная точность | Каждое заявленное свойство подтверждается точностью, полнотой и долей ложных тревог на размеченном наборе с условиями съёмки. Неопределённость результата передаётся клиенту, а не скрывается |
| Объяснимость | Наблюдение содержит, что сработало: зона, линия, направление, класс, оценка и кадр. Оператор видит причину тревоги поверх кадра |
| Минимум персональных данных | Лица обнаруживаются только для маскирования. Метаданные следуют правам, маскам и сроку хранения видео точки. Чтение номеров и текста отключено по умолчанию и включается администратором площадки |
| Автономность | Модели, их лицензии и хеши входят в поставку. Сервис не обращается к внешним ресурсам |
| Ресурсы под контролем | Каждый анализатор объявляет стоимость. Узел распределяет бюджет CPU, GPU и памяти, при нехватке снижает частоту анализа неприоритетных точек и показывает это в состоянии точки |

## Технологии и границы компонентов

| Компонент | Технология и ответственность |
| --- | --- |
| Живой анализ | Процесс `bacuri-analytics-live` на C++23, один на узел. Подписка на поток рекордера по gRPC, одно декодирование потока через GStreamer с аппаратным ускорением узла для всех анализаторов, кадры в пуле заранее выделенных буферов `cv::Mat` и `cv::UMat`. Планировщик распределяет точки и анализаторы по рабочим потокам с бюджетом CPU и GPU узла |
| Исполнитель моделей | Процесс `bacuri-analytics-models` на C++23 с модулем DNN OpenCV. Принимает от живого анализа и заданий запросы вывода на выбранных кадрах по gRPC с ограниченной очередью и сроком ответа. Может работать на отдельном GPU-узле площадки. Функции с персональными данными включаются отдельно |
| Очередь заданий | Процесс `bacuri-analytics-jobs` на C++23: повторный анализ архива, проверка правила на записи, обезличивание экспорта, синопсис и сводка интервала. Задания хранятся в очереди с приоритетом, лимитом параллелизма и отменой, читают архив и не задерживают живой анализ |
| Анализаторы | Каждый анализатор - отдельная библиотека C++ за общим интерфейсом: описание и версия, схема настроек, стоимость ресурсов, обработка кадра, состояние между кадрами, сброс при разрыве и смене ревизии привязки. У библиотеки свои тесты на размеченном наборе и порог покрытия, как у модулей ядра. Один и тот же анализатор подключается к живому анализу и к заданиям, поэтому повторный анализ даёт тот же результат |
| Классический анализ | OpenCV `imgproc`, `video`, `features2d`, `calib3d`, `objdetect`: модели фона MOG2 и KNN, морфология и контуры, фильтр Калмана, оптический поток DIS, признаки ORB с гомографией, метрики резкости и яркости, детекторы QR-кодов и штрихкодов, модель камеры fisheye |
| Модели | Модуль DNN OpenCV 5 с моделями ONNX из открытого набора OpenCV Zoo или равноценных с совместимой лицензией: детектор объектов, детектор лиц YuNet. Бэкенд выбирается по паспорту узла: CPU, OpenVINO или CUDA. Модель закреплена по хешу, версия и лицензия записаны в составе поставки |
| Контракт метаданных | Схема Protobuf для треков, классов, сетки движения, активности и состояния камеры с версией схемы. Чтение через OpenAPI и подписку WSS для живых наложений. Коды причин отказа из каталога ошибок |
| Индекс анализа | Хранилище метаданных по точке, ревизии привязки и блоку архива с временем UTC и PTS кадра. Срок хранения и удаление следуют архиву точки. Пропуски анализа хранятся явно |
| Правила | Ядро хранит версии видеоправил. Сервис получает действующую версию правила точки, проверяет геометрические условия и передаёт наблюдение с версией. Проверка правила на записи выполняется тем же кодом на архиве |
| Проверка | GoogleTest и GoogleMock для анализаторов на кадрах и коротких записях, размеченный видеонабор для точности, сценарии стенда для потока, архива и отказов. Нативный Docker Engine на Linux, узлы с GPU подключаются как отдельные исполнители |

## Этап 0. Зафиксировать объём, эталоны и ресурсы

### Шаг 0.1. Реестр анализаторов и контрактов

Для каждого анализатора записать назначение, входной профиль, частоту анализа, настройки, формат наблюдения и метаданных, потребителей в ядре и клиентах, шаг платформы и тест. Указать, какие результаты создают тревогу, какие только пишутся в индекс. Сверить с действующими видеоправилами шага 10.2 платформы и поиском 10.4. Определить коды каталога ошибок для недоступного анализа, отсутствующей модели, превышения бюджета и несовместимой версии правила.

**Приёмка**

У каждого анализатора есть владелец, контракт, критерий точности и ресурсный ориентир. Изменения публичного API переданы в соответствующие шаги платформы.

### Шаг 0.2. Размеченный видеонабор и паспорт узла

Собрать записи с днём, ночью, инфракрасной подсветкой, дождём, снегом, туманом, бликами фар, тенями, листвой, насекомыми у объектива, сменой экспозиции и PTZ-движением. Для каждой записи разметить объекты, треки, пересечения линий, пребывание в зоне, оставленные предметы, лица для маскирования и события саботажа. Отделить набор настройки от контрольного набора. Зафиксировать профили узлов: CPU без ускорения, встроенная графика, дискретный GPU, и число потоков на каждом.

**Приёмка**

Контрольный набор не используется при настройке порогов и выборе моделей. Для каждой записи известны камера, профиль, условия и лицензия использования. Паспорт узла указывает декодер, бэкенд DNN и измеренную стоимость кадра каждого анализатора.

## Этап 1. Создать сервис и контракт метаданных

### Шаг 1.1. Живой анализ и интерфейс анализатора

Создать процесс живого анализа `bacuri-analytics-live` с подпиской на поток рекордера, аппаратным декодированием, пулом кадров и планировщиком анализаторов. Определить общий интерфейс анализатора C++ и сборку каждого анализатора отдельной библиотекой со своими тестами и порогом покрытия. Процесс сообщает состояние анализа точки ядру. Перенести детектор движения из рекордера в отдельную библиотеку анализатора и удалить декодирование для анализа из процесса записи.

**Приёмка**

Остановить сервис, перегрузить узел и уронить анализатор во время записи. Запись и эфир не прерываются, точка показывает причину недоступности анализа кодом каталога, после восстановления анализ возобновляется с нового опорного кадра. Рекордер не декодирует кадры для анализа. Ограниченная очередь сбрасывает устаревшие кадры при отставании и считает их в метриках.

### Шаг 1.2. Контракт метаданных и индекс анализа

Описать схему метаданных: сетка движения, уровень активности, треки с идентификатором, рамкой, классом и оценкой, пересечения линий и пребывание в зонах, состояние камеры. Хранить записи по точке, ревизии привязки и блоку архива с UTC и PTS кадра, версиями анализатора, модели и правила. Предоставить чтение интервала через OpenAPI и живую подписку WSS для наложений в клиентах. Применять права и маски точки к метаданным так же, как к кадрам.

**Приёмка**

Метаданные интервала совпадают с кадрами по PTS на границе блоков и после смены часовой привязки. Пользователь без права на точку не получает её метаданных. Удаление архива по сроку удаляет метаданные того же интервала. Пропуск анализа отображается отдельно от пропуска записи.

### Шаг 1.3. Очередь заданий: повторный анализ и проверка правила на архиве

Создать процесс очереди заданий `bacuri-analytics-jobs`. Задание запускает те же библиотеки анализаторов на записанном интервале с заданной версией правила, без отправки команд устройствам и без создания тревог. Задания имеют приоритет, лимит параллелизма на узел, отмену и состояние, видимое клиентам. Использовать повторный анализ для заполнения пропусков индекса и для пересчёта после обновления анализатора с сохранением прежних версий. Обезличивание экспорта 3.2 и синопсис 5.3 выполняются как задания этой очереди.

**Приёмка**

Два прогона одного интервала дают совпадающие наблюдения и метаданные. Проверка правила на архиве показывает те же срабатывания, что дал бы живой поток. Пересчёт не изменяет тревоги, созданные прежней версией. Тяжёлое задание на весь архив точки не увеличивает задержку живого анализа сверх бюджета 6.1, отмена задания освобождает его ресурсы.

### Шаг 1.4. Исполнитель моделей

Создать процесс `bacuri-analytics-models` с модулем DNN OpenCV и внутренним интерфейсом gRPC: запрос вывода с моделью, версией и кадрами, ограниченная очередь, срок ответа и отказ кодом каталога при перегрузке. Живой анализ и задания запрашивают вывод только на выбранных кадрах трека. Исполнитель загружает модели по хешу из поставки, сообщает доступные модели и бэкенд и может работать на отдельном GPU-узле площадки. Модели с персональными данными, такие как чтение номеров, загружаются только после включения функции администратором.

**Приёмка**

Остановить исполнитель, подменить файл модели и перегрузить его запросами во время работы. Живой анализ продолжает классические анализаторы, наблюдения без класса помечаются как непроверенные, точка показывает недоступность моделей. Подменённая модель отклоняется по хешу. Перенос исполнителя на другой узел меняет только адрес в настройках площадки.

## Этап 2. Классическая аналитика OpenCV

### Шаг 2.1. Движение с моделью фона

Заменить сравнение соседних кадров моделью фона MOG2 или KNN с подавлением теней, адаптацией к постепенной смене освещения и сбросом при резкой смене экспозиции или режима день-ночь. Добавить морфологическую очистку, минимальную площадь и длительность, зоны включения и исключения. Писать в индекс сетку движения и уровень активности по секундам для поиска и полосы активности на шкале.

**Приёмка**

На контрольном наборе сравнить с прежним детектором долю ложных тревог на камеро-час при листве, дожде, бликах фар и включении подсветки при не меньшей полноте. Полоса активности за сутки строится из индекса без декодирования архива. Поиск движения в области кадра использует ту же сетку.

### Шаг 2.2. Сопровождение объектов, линии и зоны

Сопоставлять области движения между кадрами фильтром Калмана и венгерским алгоритмом, сохранять идентификатор трека через кратковременное перекрытие. По трекам определять пересечение линии с направлением, вход и выход из зоны, время пребывания и подсчёт в обе стороны. Передавать в наблюдении трек, точку пересечения и кадр.

**Приёмка**

На размеченных эпизодах сверить число пересечений и направление, время пребывания и подсчёт с разметкой. Два объекта, прошедшие рядом, дают два пересечения. Объект, остановившийся на линии, не даёт повторных срабатываний. Оператор видит рамку и след трека на кадре события.

### Шаг 2.3. Состояние камеры и саботаж

Определять расфокус по дисперсии лапласиана относительно эталона точки, перекрытие объектива по яркости и энтропии, засветку и недоэкспонирование по гистограмме, смещение поля зрения по признакам ORB и гомографии относительно эталонного кадра, замёрзший кадр по совпадению содержимого при идущем потоке. Эталон точки обновляется администратором и при смене ревизии привязки. Результаты создают события обслуживания, а не охранные тревоги, если правило не задаёт иное.

**Приёмка**

Расфокусировать, закрыть, засветить и повернуть камеру на стенде, повторить с физической камерой из паспорта. Каждое воздействие обнаружено в пределах заданного времени с указанием вида. Включение ИК-подсветки и смена погоды не дают ложного события смещения. PTZ-движение по команде оператора не считается саботажем.

### Шаг 2.4. Оставленные и унесённые предметы

Использовать две модели фона с разной скоростью обновления. Область, которая стала частью медленной модели и отличается от быстрой, проверяется на постоянство в течение заданного времени. Различать появление предмета и исчезновение части сцены. Передавать кадр до изменения и кадр после.

**Приёмка**

На размеченных эпизодах проверить оставленную сумку, унесённый предмет, припаркованный автомобиль в зоне и человека, долго стоящего на месте. Человек не считается предметом, если правило использует фильтр классов из 3.1.

### Шаг 2.5. Поток и направление движения

Вычислять оптический поток DIS на уменьшенном кадре в заданной зоне. Определять встречное движение относительно заданного направления, скопление по доле занятой площади и времени, резкое изменение скорости потока.

**Приёмка**

Проверить встречное движение в коридоре и на въезде, скопление у турникетов, отсутствие срабатываний при раскачивании камеры ветром. Стоимость анализа укладывается в паспорт узла при заданной частоте.

## Этап 3. Модели через модуль DNN OpenCV

### Шаг 3.1. Классы объектов и фильтр ложных тревог

Подключить детектор объектов ONNX в исполнителе моделей 1.4. Классифицировать треки как человек, транспорт или прочее, проверять класс только на кадрах трека, а не на каждом кадре потока. Правило может требовать класс. Наблюдение содержит класс и оценку.

**Приёмка**

На контрольном наборе измерить точность и полноту по классам ночью и днём, снижение ложных тревог на камеро-час по сравнению с 2.2 без классов. Работа на CPU без ускорения укладывается в паспорт узла для заявленного числа точек. Отсутствие файла модели или несовпадение хеша отключает фильтр с кодом причины и не останавливает остальные анализаторы.

### Шаг 3.2. Обезличивание выдаваемых копий

Заданием очереди 1.3 обнаруживать лица детектором YuNet и людей детектором 3.1 исполнителя моделей на интервале экспорта, сопровождать области между кадрами и строить маски производной копии. Оператор просматривает предложенные маски, добавляет и снимает их до выдачи. Комплект экспорта описывает применённые автоматические и ручные маски. Оригинал не изменяется.

**Приёмка**

На контрольном наборе измерить долю кадров, где лицо осталось открытым, в том числе в профиль, при движении и при низком разрешении. Каждый пропуск показан оператору до выдачи. Подпись комплекта охватывает маски, автономная проверка показывает их состав.

### Шаг 3.3. Коды и метки

Читать QR-коды и штрихкоды детекторами OpenCV в зоне, заданной администратором, например на рампе погрузки. Писать значение и кадр в метаданные события, давать поиск по значению.

**Приёмка**

Проверить чтение на движущейся паллете, под углом и при бликах плёнки. Значение доступно только пользователям с правом на точку. Повтор кода в пределах заданного времени даёт одно событие.

### Шаг 3.4. Текст и номера транспортных средств

Подготовить модели обнаружения и распознавания текста через модуль DNN для номеров транспортных средств и надписей на контейнерах. Функция отключена по умолчанию, включается администратором площадки для выбранных точек, хранение значений следует сроку архива и отдельному праву поиска.

**Приёмка**

Измерить долю правильно прочитанных номеров по условиям съёмки и скорости. Без включения функции значения не вычисляются и не хранятся. Поиск по номеру требует отдельного права и фиксируется в аудите.

## Этап 4. Пространственная аналитика

### Шаг 4.1. Треки на плане

По ориентирам на кадре и плане вычислять гомографию плоскости пола для неподвижной камеры. Переводить точку опоры трека в координаты плана. Хранить калибровку как версию размещения камеры в модуле карт.

**Приёмка**

Сверить положение размеченных точек на плане с погрешностью, указанной в паспорте калибровки. Смена размещения камеры создаёт новую версию калибровки и не изменяет прежние треки. Клиент показывает трек на плане по метаданным.

### Шаг 4.2. Продолжение пути на соседних камерах

По топологии соседей из карт, направлению выхода трека, времени и скорости предлагать кандидатов продолжения пути на соседних камерах. Для сравнения внешнего вида использовать цветовые гистограммы области трека без биометрических признаков. Результат - упорядоченный список кандидатов с оценкой, решение принимает оператор.

**Приёмка**

На размеченных переходах между камерами измерить долю случаев, где верный кандидат первый и входит в первые три. Кандидаты учитывают права пользователя на точки. Отсутствие калибровки или соседей не ломает переход, а скрывает предложения.

### Шаг 4.3. Камеры fisheye

Хранить модель камеры fisheye точки и строить развёртки для анализа и показа. Анализаторы работают на развёрнутых видах, координаты метаданных переводятся в исходный кадр.

**Приёмка**

Трек и линия на развёрнутом виде совпадают с исходным кадром после обратного преобразования. Экспорт оригинала не изменяется, развёрнутая производная описывает преобразование.

### Шаг 4.4. Предсказание следующей камеры

На основе 4.1 и 4.2 вычислять для живого трека вероятные следующие камеры с ожидаемым временем появления по топологии соседей, направлению, скорости и истории переходов площадки. Публиковать предсказание в живой подписке метаданных до выхода объекта из кадра и уточнять его по мере движения. История переходов накапливается по трекам без признаков внешности и хранится со сроком архива. Предсказание - подсказка для клиента, оно не создаёт тревог.

**Приёмка**

На размеченных переходах измерить долю случаев, где фактическая следующая камера входит в первые две предсказанные, и запас времени между предсказанием и появлением объекта. Проверить объекты, которые остановились, развернулись и ушли в зону без камер: предсказание снимается, а не остаётся ложным.

### Шаг 4.5. Калибровка камер для пространственной сцены

Расширить калибровку 4.1 до положения камеры в здании: высота установки, наклон, поле зрения и привязка к этажу. Для камер с общей зоной обзора вычислять перекрытие на плоскости пола. Передавать калибровку клиентам вместе с моделью этажей из модуля карт для проекции видео на план.

**Приёмка**

Спроецированный кадр совпадает с планом на контрольных точках в пределах погрешности паспорта калибровки. Перекрытие двух камер на плане совпадает с размеченными точками в обоих кадрах.

## Этап 5. Поиск и расследование

### Шаг 5.1. Поиск по метаданным

Расширить поиск платформы условиями класса, направления, пересечённой линии, зоны, времени пребывания и преобладающего цвета области трека. Результат - эпизоды с миниатюрой, интервалом и треком. Показывать покрытие индекса анализа отдельно от покрытия записи.

**Приёмка**

На наборе с известными эпизодами измерить полноту и время холодного и прогретого поиска за сутки и за неделю по 16 точкам. Поиск учитывает права, маски и срок хранения.

### Шаг 5.2. Сводка интервала

По индексу активности и трекам выбирать ключевые кадры интервала и строить сводку: лента кадров с отметками событий и переход к точному моменту архива. Сводка строится без полного декодирования интервала.

**Приёмка**

Для суток записи с известными эпизодами все эпизоды представлены в сводке. Время построения сводки и число декодированных кадров укладываются в паспорт.

### Шаг 5.3. Синопсис: интервал на одном кадре

По модели фона, трекам и маскам строить синопсис интервала: объекты разных моментов накладываются на один фоновый кадр со своими временными метками без перекрытия друг друга. Каждый объект ссылается на исходный трек и точный кадр архива. Маски приватности применяются к каждому объекту. Синопсис - производное представление для поиска: клиент помечает его как синопсис, в экспорт он попадает только как производная копия с описанием преобразования.

**Приёмка**

Для часа записи с известными эпизодами все объекты присутствуют в синопсисе, клик по объекту открывает правильный кадр архива. Объекты в маске закрыты. Измерить время построения синопсиса часа и суток по одной точке на профиле узла.

## Этап 6. Квалифицировать аналитику

### Шаг 6.1. Точность, задержка и нагрузка

Прогнать контрольный набор и живые потоки на каждом профиле узла. Измерить точность, полноту и ложные тревоги по анализаторам и условиям, время от кадра до наблюдения и до тревоги на посту, стоимость кадра, число потоков на узел, память и стабильность за 72 часа.

| Измерение | Предлагаемый ориентир и проверка |
| --- | --- |
| Задержка | От кадра события до наблюдения в ядре до 1 с по p95, до тревоги на посту в пределах ориентира платформы 2 с |
| Ложные тревоги | Доля на камеро-час по каждому анализатору и условию съёмки, сравнение с прежним детектором на тех же записях |
| Полнота | По каждому анализатору и условию съёмки на контрольном наборе, без смешивания с набором настройки |
| Плотность | Число точек на профиль узла для каждой комбинации анализаторов при заданной частоте анализа |
| Стабильность | Рост памяти и времени кадра за 72 часа не превышает предела паспорта, пропуски кадров сервиса учтены |

**Приёмка**

Каждое заявленное свойство подтверждено числами на конкретном профиле узла. Неподтверждённая комбинация не заявляется.

### Шаг 6.2. Отказы и обновления

Перезапустить сервис, рекордер и ядро, удалить модель, подменить её файл, отключить GPU во время работы, обновить анализатор с сохранением правил. Проверить отсутствие влияния на запись, явное состояние точки, повторный анализ пропусков и неизменность тревог прежней версии.

**Приёмка**

Запись и эфир не прерываются ни в одном сценарии. Подменённая модель отклоняется по хешу. После обновления наблюдения содержат новую версию анализатора, прежние записи индекса сохраняют свою.

### Шаг 6.3. Поставка

Включить сервис, библиотеки OpenCV, модели, их лицензии и хеши в автономный комплект платформы. Описать включение анализаторов по точкам, бюджет узла и проверку после установки.

**Приёмка**

На чистом узле без сети установить комплект, включить анализаторы, получить тревогу и метаданные на эталонной записи. Состав поставки содержит версию OpenCV, бэкенды DNN, модели и лицензии. [Автономная поставка](adr/011-offline-delivery.md)

## Порядок выполнения и учёт результатов

Начать с реестра 0.1 и размеченного набора 0.2: без контрольного набора свойства аналитики не заявляются. Живой анализ, контракт метаданных и очередь заданий 1.1-1.3 открывают работу клиентов над наложениями и полосой активности. Исполнитель моделей 1.4 нужен до этапа 3. Классическая аналитика этапа 2 не требует GPU и даёт основной эффект: меньше ложных тревог, контроль камер, линии и зоны. Модели этапа 3 добавляются после измерения нагрузки на профилях узлов. Пространственная аналитика этапа 4 использует размещение камер из модуля карт и связывается с переходами между камерами в клиентах. Предсказание следующей камеры 4.4, калибровка 4.5 и синопсис 5.3 дают основу фирменных функций настольного клиента: пространственной видеостены, синопсиса и заранее открытой следующей камеры. Поиск этапа 5 опирается на индекс, накопленный этапами 2-4.

Для каждого шага сохранять версию сервиса, анализатора, модели и правила, набор данных, профиль узла, команду или протокол выполнения, фактический результат и ссылку на материалы. Статус шага `Готово к приёмке` ставится после его проверок, `Принято` - после сверки материалов с критериями.
