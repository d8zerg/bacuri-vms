# Интерфейс и проверка пользовательских сценариев Bacuri VMS Basic

**Статус визуальной системы** - Принято. Интерактивный макет служит оснасткой для ранних браузерных тестов. Приёмке продукта подлежит рабочий клиент с реальными сервисами. [План разработки](devplan-basic.md#6-контрольные-точки-и-последовательность)

Запуск - `task prototype:up`. Адрес по умолчанию - [http://127.0.0.1:8088](http://127.0.0.1:8088). Для остановки используется `task prototype:down`.

Адреса RTSP проверяются по тестовому набору. Эфир и архив воспроизводят локальные фрагменты WebM. Проверка связи, появление записи, тревоги и отказы моделируются в браузере. Перезагрузка возвращает начальные условия для следующего теста. Разделы «Мониторинг» и «Камеры» переключают роль оператора и монтажника.

## Визуальная система

| Компонент | Правило |
| --- | --- |
| Рабочее пространство | Системная цветовая схема выбирает кремовые поверхности с молочными панелями или нейтральные серые поверхности и текст VS Code Dark+. Видеокадр и непрозрачные подложки надписей сохраняют цвета в обеих темах. На широком экране видео и тревоги находятся рядом, на узком лента следует после шкалы |
| Цвет и типографика | Обе темы используют [общие цветовые токены](../design/bacuri/tokens.css). В светлой теме заголовки и основной текст почти чёрные, подписи нейтрально-серые. Главная кнопка имеет приглушённую песочно-жёлтую заливку. Боковая полоса и оттенок фона обозначают выбранный раздел или тревогу. Оливковый - исправную связь и подтверждение, терракотовый - предупреждение, карминовый - тревогу или отказ. Время и счётчики используют моноширинные цифры |
| Фирменный знак | В шапке изображён поперечный срез бакури. Три кремовые дольки с семенами образуют треугольный просвет диафрагмы внутри золотого кольца. Для вкладки браузера у знака отдельная геометрия на 16 пикселях. [Комплект знака](../design/bacuri/brand) |
| Форма камеры | Явные подписи, раздельные адреса и подсказки по их назначению. Исправимая ошибка фокусирует поле, значения открытой формы сохраняются |
| Результат проверки | Связь, основной поток, дополнительный поток, запись и воспроизведение имеют отдельные состояния. Доступность камеры и успешное чтение кадра проверяются как разные действия |
| Шкала архива | Сплошная заливка для записи, диагональная штриховка для пропуска, вертикальные терракотовые штрихи для оценочного времени, точечная для каталогизации. Легенда, текст состояния и выделенная позиция дополняют цвет |
| Тревога | Карточка показывает приоритет, время и точку. Открытие архива переводит фокус в область видео, возврат переводит фокус на выбранную карточку |
| Сбой | Сообщение показывает причину и доступное действие. Обрыв связи останавливает воспроизведение. После повторного подключения сохраняются выбранная тревога и интервал |
| Клавиатура | Tab и Shift+Tab перемещают фокус, Enter и Space активируют кнопки. На шкале клавиши со стрелками меняют позицию, Home и End выбирают границы. Видимый фокус обозначен обводкой |

После проверки потоков фокус переходит к созданию записи. По завершении записи он переходит к открытию фрагмента. После первого воспроизводимого кадра доступно подтверждение. Асинхронный шаг переводит фокус только если он оставался на исходной кнопке.

Например, для подтверждённого пропуска шкале нужны границы интервала, для оценочного времени - доступные сведения о погрешности. Оба экрана используют один контракт компонента. Для нового варианта взаимодействия зафиксировать ожидаемое улучшение относительно принятого макета и признак ухудшения. На одинаковых данных сравнить число необходимых действий, повторный ввод и сохранение контекста. Вариант с потерей точки, ложным подтверждением или недоступным действием возвращают на доработку. Самостоятельность, время человека и понимание результата оцениваются на финальной серии по [заданиям первого использования](#проверка-первого-использования).

#### Шкала архива в UI Kit

Компонент получает окно и непересекающиеся интервалы в миллисекундах UTC, выбранную позицию и обработчики выбора и обновления. Владелец сценария передаёт непустое окно и позицию внутри него. Начало интервала включается, конец исключается. Пока позиция между известными интервалами, отображается «Нет сведений». Компонент сообщает выбранный момент вызывающему коду. Получение кадра и подтверждение записи принадлежат сценарию и плееру.

Сплошная полоса означает запись, диагональ - подтверждённый пропуск, вертикальные штрихи - оценочное время, точки - каталогизацию, горизонтальные штрихи - недоступный носитель или другой отказ выдачи. Текст рядом с курсором указывает причину пропуска или недоступности и границы. Для оценочного времени видна погрешность либо сообщение, что она неизвестна. При переходе через полночь видны обе календарные границы. Загрузка, пустой результат и ошибка каталога имеют отдельные примеры. При обновлении после ошибки фокус остаётся на кнопке, а результат объявляется через область статуса.

Локальный каталог запускается командой `task ui-kit:up` и доступен по адресу [http://127.0.0.1:6010](http://127.0.0.1:6010). Остановка - `task ui-kit:down`. Команда `task ui-kit:check` изолированно собирает библиотеку и каталог, проходит примеры в Chromium и Firefox в обеих темах и сохраняет результаты в каталоге отчёта. #### Форма подключения камеры в UI Kit

Монтажник вводит название, адрес основного потока для архива и адрес дополнительного потока для эфира. Поля имеют постоянные подписи. Enter отправляет форму. При ошибке фокус получает первое ошибочное поле, а его доступное описание содержит назначение и текст исправления. Форма проверяет синтаксис RTSP и RTSPS. Адрес с реквизитами, строкой запроса или фрагментом отклоняется до отправки. Проверка доступности устройства, доверия сертификату и разрешений для открытого RTSP принадлежит серверу. [Контракт камеры](../contracts/v1/openapi.yaml) · [Политика транспорта](adr/012-camera-capabilities.md)

Форма получает текущие значения, состояние проверки и обработчики действий. Владелец сценария хранит черновик и допускает одну активную проверку. Редактирование сбрасывает прежний результат и отменяет запрос. Запоздалый ответ от отброшенной попытки игнорируется. При интеграции экран должен создавать отдельный экземпляр сценария по идентификатору выбранной точки. После обрыва оба адреса сохраняются для повтора. При частичном успехе каждый профиль показывает свой результат. Проверка записи и воспроизведения следует на экране монтажника после проверки потоков.

Примеры используют детерминированные ответы без подключения к камере. Автотесты проверяют ввод с клавиатуры, повторную отправку, исправление адреса во время запроса, независимые результаты профилей, доступность и компоновку при ширине 320 пикселей и тексте 200%. [Форма](../web/client/src/ui-kit/CameraConnectionForm.tsx) · [Сценарий проверки](../web/client/src/workflows/useCameraConnectionCheck.ts) · [Примеры в Storybook](../web/client/stories/CameraConnectionForm.stories.tsx) · [Браузерные тесты](../web/client/tests/camera-connection.spec.mjs)

## Дизайн-ревью целых экранов

Автотесты проверяют экран ввода камеры и рабочее место оператора в контексте задания, а с этапа 7 также карту, план, обработку тревоги, ёмкость архива и экспорт. Для каждого сохраняют полные снимки при ширине 1440, 768, 390 и 320 CSS-пикселей, а для асинхронных переходов - последовательность состояний до ответа, после ответа и после повтора. Серия включает реальные длинные имена точек, время с часовым поясом, непустую ленту и диагностическую ошибку. Макет задаёт ожидаемый вид, на шаге 4.2 рядом помещают снимок интегрированного клиента с теми же условиями.

Исходные параметры макета - основной текст 1 rem с межстрочным интервалом 1,45, заголовок экрана от 1,65 до 2,25 rem, метаданные панели 0,875 rem. Форма и плеер используют одну шкалу отступов. Для изменения этих значений рецензент сравнивает перенос подписей, видимость действия и читаемость состояния на тех же полных экранах. [Стили прототипа](../prototype/dist/styles.css)

Измерить контраст обычного текста не менее 4,5:1, крупного - 3:1. Проверить сохранение подписей и действий при ширине 320 CSS-пикселей. При обрыве видны состояние и действие для восстановления. При отзыве выдача прекращается, запрещённые сведения исчезают |

Браузерная автоматика фиксирует ревизию, полные снимки и различия с эталоном, контраст, дерево доступности и порядок фокуса при вводе с клавиатуры. Различие с эталоном требует исправления либо обоснованного обновления эталона с повторным прогоном. Рецензент оценивает визуальную иерархию по полученным экранам. Понятность сообщений, в том числе озвученных экранным диктором, проверяют в финальной серии 9.1. [Решение о дизайн-системе](adr/007-ui-states.md)

## Проверка первого использования

Пригласить практикующих монтажников видеонаблюдения и дежурных операторов, впервые работающих с Bacuri. Выдать адрес входа, учётные данные, данные объекта и цель обычными словами. Пример для монтажника - «Подключите камеру у ворот и покажите, как вы убедились, что запись можно посмотреть». Оператору - «Покажите, что произошло у ворот при сигнале, и вернитесь к наблюдению за тревогами». Наблюдатель сбрасывает данные и профиль браузера перед каждой попыткой, фиксирует действия, молчит и после завершения просит объяснить результат. Документация и показ порядка действий исключены из задания. Любая подсказка или вмешательство записываются как несамостоятельное завершение.

В 6.1 для каждой строки записать численный предел и его основание по условиям работы роли. Измерения задержек стенда помогают учесть ожидание. В 8.3 автоматика проверяет полноту профиля и технический результат. Человеческое время измеряется только в 9.1, включая вход и ожидание системы.

После успешного 8.3 на том же комплекте привлечь минимум пять новых монтажников и пять новых операторов. Обе группы охватывают оба целевых браузера. Первое задание выполняется при первом входе, затем участник проходит дополнительные задания своей роли и вариант отказа. Включить выполнение ключевого задания с клавиатурой и экранным диктором. Администратор отдельно проходит обслуживание по поставляемой инструкции. Для приёмки каждый участник самостоятельно достигает результата в закреплённое время и правильно объясняет его, критических ошибок нет. При дефекте сохранить исходный протокол, добавить автоматический регрессионный тест, повторить 8.3 на исправленном комплекте и затронутые финальные задания. Для повторной проверки первого использования привлечь новых участников. [ADR-008](adr/008-first-use.md)

## Проверка в браузерах

Команда `task prototype:check` сверяет файлы значка с исходными SVG, запускает оба маршрута и axe-core в светлой и тёмной темах Chromium и Firefox. Для экрана оператора и экрана монтажника сравниваются 32 эталона на ширине 1440, 768, 390 и 320 CSS-пикселей. Для сравнения эфир останавливается на фиксированном кадре. Снимки сохраняются в отчёте, при расхождении Playwright добавляет эталон, фактическое изображение, разницу и трассу. Запуск проверки читает эталоны из репозитория. [Браузерные тесты и эталоны](../tests/prototype)

После изменения дизайна получить новые эталоны в подготовленном тестовом образе и проверить изменившиеся PNG целиком. Затем повторить обычный `task prototype:check`.

```sh
docker compose build prototype-check
mkdir -p build/prototype-results
BACURI_PROTOTYPE_SCREEN_MODE=rw docker compose run --rm --no-deps -T --user "$(id -u):$(id -g)" prototype-check --grep 'full operator' --update-snapshots=all
```

На интерактивном макете в Chromium и Firefox пройдены ввод камеры, восстановление после ошибки связи, воспроизведение и подтверждение записи, переход из тревоги и возврат фокуса. Проверены пропуск, оценочное время, повторная проверка каталога и сохранение позиции после обрыва. При ширине 1440, 768, 390 и 320 пикселей проверено отсутствие горизонтального переполнения. Автоматические проверки axe-core для обоих экранов прошли. Для рабочего клиента результаты прикладываются отдельно к 8.3, а наблюдения за пользователями - к 9.1.
