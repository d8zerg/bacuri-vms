# Приём RTSP и матрица совместимости

Узел записи открывает отдельный сеанс RTSP/TCP для каждого профиля применённой конфигурации. После перезапуска он восстанавливает адреса и учётные данные из зашифрованного снимка SQLite. При изменении адреса или секрета пересоздаётся соответствующий сеанс. Состояние `receiving` означает, что узел получил пригодный для начала декодирования H.264-кадр.

## Матрица оборудования для выпуска

Для программного профиля закреплён bacuri.vms ONVIF emulator с прошивкой 1.1, HTTPS для управления и RTSPS для обоих потоков. Стенд доверяет временному сертификату, созданному для одного прогона. Исключений для открытого транспорта нет. Фактический инвентарь физических камер пуст. Для полного выпуска заданы эталонные пары, оснащение и обязательные функции. При подключении каждой пары сохранять наблюдаемую идентичность и результаты по отдельным функциям. [Эталонные устройства полного выпуска](release-profile.md#эталонные-устройства)

| Функция | Что проверяет автоматический сценарий на физическом устройстве |
| --- | --- |
| Защищённый транспорт | В строке модели указать режим управления и медиаканал, доверенный источник сертификата и результат записи. В защищённом режиме подтвердить шифрование фактического видеопотока. На управляемом источнике отдельно подставить недоверенный сертификат и неверное имя, сверить отказ без передачи секрета и без перехода на открытый RTSP. Для старой камеры проверить отказ до включения адресного исключения и после его отзыва |
| Обнаружение и ввод | Камера найдена в разрешённом сегменте, повторный поиск сохраняет идентичность, неверные реквизиты дают диагностируемый отказ |
| Потоки и замена | Выбраны H.264-профили, получены кадры эфира и новой записи. После замены старый и новый интервалы доступны по одной точке |
| PTZ | На модели с PTZ стенд подтверждает фактическое изменение положения и остановку по обратной связи или контрольному кадру. Для модели без функции интерфейс и API учитывают отсутствие возможности |
| Событие оборудования | Программно управляемый стимул вызывает событие камеры. Проверяются источник, время, одна тревога при повторной доставке и переход к кадру |

К каждой строке приложить идентификатор релиз-кандидата, модель, прошивку, заявленную возможность, условия опыта, фактический результат и отчёт. Обязательная функция без успешного прогона в 12.1 блокирует выпуск. Аппаратная квалификация открыта до появления обязательных физических моделей и результатов. ## Стенд ONVIF

Команда `task camera:check` запускает изолированный контейнер Docker Compose без внешней сети. RTSP-сервер создаёт два синтетических H.264-потока GStreamer. Имитатор принимает адресный UDP Probe, запросы SOAP по HTTPS с UsernameToken, возвращает медиапрофили, моделирует положение PTZ и подписку PullPoint. Стимул ставит в очередь событие движения для активной подписки. Веб-камера доступна в отдельном V4L2-прогоне через `task webcam:check`. [Сценарий оборудования](../tests/cameras/series.py) · [Спецификации ONVIF](https://www.onvif.org/profiles/specifications/)

Серия проверяет повтор обнаружения, точную идентичность, отказ при неверном пароле и два разных профиля. Для каждого профиля запрашивает URI и декодирует H.264 по TCP внутри TLS. Для PTZ сравнивает координату до и после ограниченного смещения и ожидает подтверждения остановки. Для движения сверяет источник, время и значение события после стимула. Подключение к точке и воспроизведение проверяет отдельный прогон мастера. Связь события с архивным кадром проверяет сквозной сценарий управления камерой.

Отчёт `emulator.json` в выведенном каталоге содержит наблюдаемые свойства устройства и результаты функций. Отрицательные прогоны проверяют отказ при ошибке доверия, несовпадении имени, прошивки и кодека, неполном профиле и пропущенном результате. В контрольном прогоне прошли 8 функций. Декодированы кадры 1280×720 и 640×360, координата поворота изменилась с 0 до 0,1, после Stop получено состояние IDLE. Получено событие движения от источника main. Пустой инвентарь физических камер дал код 1.

### Мастер подключения

В разделе «Камеры» администратор выбирает «Поиск ONVIF и замена камеры» и запускает поиск. Для замены нужно выбрать существующую точку. После ввода реквизитов мастер показывает изготовителя, модель, прошивку, серийный номер и объявленные службы PTZ и Events. Администратор выбирает разные профили записи и эфира, подключает камеру, создаёт тестовую запись и подтверждает декодированный кадр. После замены доступна предыдущая запись той же точки. Для известной пары адресов доступен ручной ввод.

- Обнаружение использует IPv4 WS-Discovery multicast `239.255.255.250:3702`. У процесса управления должен быть интерфейс в разрешённом сегменте камер с доступным multicast. Для физического стенда подключите контейнер к сети камеры, например через выделенную сеть macvlan. Укажите соответствующие CIDR в `BACURI_CAMERA_NETWORKS` у ядра и узла записи.
- Управление использует Device и Media ver10 по HTTPS с WS-Security UsernameToken PasswordDigest. Мастер читает адрес службы Media и токены из ответа камеры, выбирает H.264 и запрашивает GetStreamUri. Поддерживаются адреса служб и потоков с тем же именем узла, два разных URI без параметров запроса и фрагмента, RTP поверх RTSP/TCP. Для защищённого видео нужен RTSPS.
- По умолчанию оба процесса используют системные доверенные сертификаты. Для частного центра сертификации смонтируйте PEM-файл только для чтения в оба контейнера и задайте его абсолютный путь внутри контейнера в `BACURI_CAMERA_CA_FILE`. Имя в адресе должно соответствовать сертификату. Параметры реквизитов передаются отдельно от URI.
- Для открытого RTSP в выделенном сегменте задайте `BACURI_LEGACY_RTSP_ADDRESSES` списком конкретных IP через запятую у обоих процессов и пересоздайте контейнеры. Адрес должен входить и в разрешённый CIDR. Пустой список закрывает открытый транспорт. Изменения действующего списка фиксируются в `bacuri_inventory.camera_transport_audit`. Смена адреса и удаление исключения требуют пересмотра настройки. Для локального RTSP-стенда IP можно получить командой `docker compose exec -T rtsp-camera hostname -i`.

`task camera:commissioning` запускает проверку на синтетическом видео. В `commissioning.json` и снимках Chrome сохраняются результаты открытия записи до и после замены, в том числе после восстановления узла записи. В аппаратном протоколе проверяется конкретная пара модели и прошивки. [Сквозной сценарий](../tests/cameras/commissioning.py)

### Управление PTZ и приём движения

В эфире оператору доступны направления основного профиля, для которых камера объявляет стандартное пространство скорости PanTilt, скорость ±0,5 по соответствующей оси и длительность 1 с. Нажатие отправляет один ContinuousMove, кнопка «Остановить» отправляет Stop. Интерфейс показывает подтверждение устройства или причину отказа. Проверяются сеанс, CSRF, право на точку и идентификатор текущей камеры. Во время движения управление закреплено за оператором, администратор может перехватить его. Повтор запроса с тем же ключом возвращает исход предыдущей попытки в течение 24 часов. При потере связи длительность движения ограничивает сама камера. [Служба ONVIF PTZ](https://www.onvif.org/ver20/ptz/wsdl/ptz.wsdl)

Для ранее подключённой камеры или после смены прошивки запустите поиск ONVIF, прочитайте профили и выберите «Обновить подключённую камеру». Мастер сверяет идентичность и сохраняет новую конфигурацию у прежней привязки. При ручном вводе RTSP доступен только медиаканал.

Ядро читает уведомления PullPoint через HTTPS, продлевает подписку и создаёт новую после потери связи. Из темы `RuleEngine/CellMotionDetector/Motion` принимается изменение `IsMotion` на `true` для `VideoSourceConfigurationToken` выбранного профиля. Идентификатор наблюдения зависит от устройства, привязки, источника события и времени камеры. Правило `motion` публикует одну тревогу при повторной доставке. Для сопоставления с архивом учитываются точность отметки и расхождение часов по ответу PullMessages. При погрешности свыше 5 с применяется время приёма, переход к точному кадру получает статус неопределённого времени. [Служба ONVIF Events](https://www.onvif.org/ver10/events/wsdl/event.wsdl)

| Модель и прошивка | Проверенные функции |
| --- | --- |
| bacuri.vms ONVIF emulator 1.1 | Выбор команд по профилю, горизонтальное движение, Stop, остановка по тайм-ауту при обрыве связи, повтор команды, приоритет управления, продление и восстановление PullPoint, повтор движения до одного архивного кадра |
| Физические IP-камеры | Модели и прошивки для аппаратной проверки пока отсутствуют |

`task camera:commissioning` сохраняет `camera-operations.json` и снимок Chrome. Отчёт содержит идентификаторы наблюдения, тревоги, привязки и блока, позицию UTC и индекс кадра. Стенд сравнивает изображение в браузере с независимым декодированием исходного блока и соседними кадрами. [Сквозной тест](../tests/cameras/operations.py)

### Прогон на выделенном оборудовании

В массив `hardware` добавить обязательные строки того же формата, что и `emulator`, с изготовителем, точной моделью и прошивкой, функциями и источником доверия. Для текущего профиля обязательны HTTPS, RTSPS и отсутствие исключения. Функции `ptz` и `motion` включать только для соответствующих моделей. Весь комплект должен покрывать обе функции. [Инвентарь](../tests/cameras/qualification.json)

Команда `task camera:hardware STAND=/absolute/path/to/stand` монтирует каталог стенда только для чтения. В каталоге разместить файл поставки `bundle`, доверенный PEM, файл пароля и массив `connections.json`. На каждую строку инвентаря нужна одна запись подключения со следующими полями.

| Поля | Значение |
| --- | --- |
| `manufacturer`, `model`, `firmware` | Те же точные значения, что в инвентаре. Идентичность сверяется с GetDeviceInformation |
| `device_service`, `discovery_port` | Полный адрес HTTPS с именем из сертификата камеры, доступный из сети Compose. Устройство принимает адресный Probe на UDP-порту, по умолчанию 3702 |
| `ca_file`, `username`, `password_file` | Путь к доверенному PEM относительно каталога стенда, учётное имя ONVIF и относительный путь к файлу пароля |
| `profile_tokens` | Объект с разными токенами `main` и `sub` из GetProfiles. Для серии PTZ основной профиль поддерживает GetConfigurationOptions, RelativeMove, ContinuousMove с тайм-аутом 1 с, Stop и GetStatus |
| `stimulus`, `motion_source` | Для проверки движения указать относительный путь к исполняемой программе физического стимула и объект с полями `name` и `value` из источника ONVIF-события. Часы камеры и стенда синхронизировать |

Код 0 означает успешный прогон каждой заявленной функции каждой обязательной прошивки. Отчёт `hardware.json` содержит хеш комплекта при его проверке, хеш профиля, идентичность, результат декодирования каждого потока и результаты команд. Пустая аппаратная матрица, пропуск, расхождение с прошивкой и недоступное оборудование завершают команду ошибкой.

## Нагрузка и восстановление

| Граница | Лимит | Поведение |
| --- | --- | --- |
| Очередь основного потребителя | 64 кадра или 8 МиБ | Сохраняет принятые кадры. При исчерпании места учитывает потерю входящих кадров и её начало. Приём в очередь возобновляется с ключевого кадра |
| Очередь потребителя просмотра | 8 кадров или 1 МиБ | При переполнении освобождает очередь и возобновляет выдачу с ключевого кадра, содержащего параметры декодирования |
| Вход каждого конвейера | Джиттер-буфер 250 мс, appsink до 4 буферов или 8 МиБ | Потоки имеют отдельные конвейеры и отдельные потоки исполнения. Слишком крупная единица H.264 или повреждённый буфер завершают текущий сеанс |

При ошибке, EOS или отсутствии данных узел завершает сеанс. Ожидание первого кадра ограничено 8 с, следующих кадров - 5 с. Повторные подключения выполняются через 1, 2, 4, 8, 16 и далее 30 с. После 5 с устойчивого приёма начальная задержка возвращается к 1 с. Остановка прерывает ожидание повторной попытки.

В журнале `rtsp_ingest` доступны счётчики кадров, байтов, ключевых кадров, попыток переподключения, пропусков и потерь конкретного потребителя. Пропуск источника открывается после последнего принятого кадра и закрывается при первом пригодном ключевом кадре. Границы приведены в микросекундах UTC по времени приёма. До первого успешного подключения журнал сообщает причину недоступности источника. Сброс кадров у потребителя просмотра учитывается в его очереди.

## Время и воспроизведение проверки

Для единицы H.264 сохраняются исходный 32-битный RTP timestamp со шкалой 90 кГц, PTS в наносекундах, время приёма и доступная исходная отметка NTP. Узел сопоставляет метаданные RTP с кадром по PTS в пределах одного сеанса. После получения опоры NTP с расхождением до 5 с от часов узла используется `source_clock`. Оценка неопределённости равна наблюдаемому расхождению. При отсутствии опоры или превышении порога используется `reception`. Переподключение или изменение разности NTP и PTS более чем на 500 мс создаёт новую эпоху привязки. [Метаданные GStreamer](https://gstreamer.freedesktop.org/documentation/gstreamer/gstbuffer.html#GstReferenceTimestampMeta) · [Синхронизация RTCP в jitterbuffer](https://gstreamer.freedesktop.org/documentation/rtpmanager/rtpjitterbuffer.html)

`task ingest:check` использует синтетическую камеру. `task webcam:check` дополнительно запускает эмулятор и одновременно декодирует по 25 кадров каждого профиля. Тестовый TCP-посредник закрывает установленные соединения и на время прерывания отклоняет повторные подключения. После прогона `task webcam:down` освобождает устройство. [Настройка веб-камеры](../README.md#rtsp-эмулятор-с-веб-камерой)
