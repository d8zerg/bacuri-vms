**Статус** - Принято. [План разработки, шаг 0.1](devplan-poc.md#шаг-01-границы-poc-и-проверяемые-решения)

Синтетическая камера используется для воспроизводимой проверки двух потоков. Физический прогон подтверждает совместимость конкретного устройства. Профиль компактного аппаратного узла проверяется отдельно по фактическому потреблению ресурсов.

## Результаты проверки инфраструктуры

С Conan 2.34.0 два независимых разрешения профилей GCC и Clang дали одинаковый lockfile. После перехода с прежних каталогов CMake во всех четырёх тестовых пресетах прошёл 31 тест, включая прогоны с ASan/UBSan и TSan. Полный прогон `task check:report` завершился с кодом 0. На Release отдельная проверка тревоги в Chrome и Firefox открыла эталонный кадр 16. Команда `task build:repro` повторно собрала проект без сети в чистом каталоге того же образа. Все четыре исполняемых файла совпали побайтно. [Границы проверки воспроизводимости](adr/010-build-dependencies.md)

С чистой копии источников `task check:report` завершился с кодом 0. Прошли сборки GCC 14.2 и Clang 19.1, стартовый CTest в обычных и инструментированных сборках с ASan/UBSan и TSan, а также статический анализ. PostgreSQL 17.11 ответил на запрос по сети Compose. Оба H.264-профиля синтетической камеры декодировались в ожидаемом разрешении.

`task stand:check-storage` подтвердил сохранность тестовых данных PostgreSQL и архива после остановки и повторного запуска Compose. Заполнение tmpfs вернуло `ENOSPC` на границе 64 МиБ. При повторном запуске контейнера временный том был пуст.

## Протокол измерений

Функциональный прогон использует одну физическую и одну синтетическую камеру. Для смешанного профиля предусмотрены восемь двухпоточных источников с основным потоком номинально 2 и 4 Мбит/с в отдельных прогонах. Для каждого режима предусмотрены 5 минут прогрева и 30 минут измерений. Во время прогона одновременно работают запись, один клиент эфира, один клиент архива, поиск и тестовые наблюдения с частотой 1 событие/с. Для первого кадра, окна поиска и задержки тревоги собирается не менее 200 проб на режим. Холодный поиск прогоняется отдельно с описанием начального состояния кэша.

Основные условия приёмки приведены в матрице. Ориентир для планирования Basic - до 2 с по p95 для первого кадра эфира, отображения тревоги и первой страницы поиска. В каждом прогоне фиксируются p50, p95, p99, число проб, доля ошибок, потребление ресурсов, глубина очередей, разрывы и объём записи на диске. Стоимость хранения рассчитывается из фактического объёма за единицу времени и ёмкости выбранного носителя. Для каждого сценария отказа фиксируются начало отказа, первый обнаруженный пропуск, момент возвращения проверенной операции и объём невосстановимых данных.

| Поле результата | Что записать |
| --- | --- |
| Воспроизводимость | Ревизия проекта, версии образов и пакетов, оборудование, тип файловой системы, конфигурация сети и источник |
| Нагрузка | Число потоков и клиентов, измеренный битрейт, GOP, частота событий, длительность, объём выборки и условия запуска |
| Наблюдение | Ожидаемый результат, фактический результат, метрики и ссылки на артефакты |
| Сбои | Причина, диапазон пропуска, проверенные копии, потеря данных, длительность восстановления записи, архива и конфигурации |

## Комплект доказательств

Для каждого обязательного требования записывают сценарий, ревизию, ADR, команду или задание, начальное состояние, ожидаемый и фактический результат и расположение материала. Снимки интерфейса и кадры эталона относятся к испытательным материалам. Технические журналы сохраняются без секретов и содержимого видео. В итоговый протокол включают также неудачные попытки и результаты повторной проверки. [Матрица требований](poc-quality.md#требования-к-приёмке)

| Материал для шага 5.3 | Как воспроизвести и что сверить |
| --- | --- |
| Две демонстрации с чистого входа | Ввести физическую камеру и открыть новую запись. Затем под ролью оператора открыть эфир той же точки, подать наблюдение, открыть соответствующий фрагмент и вернуться в ленту. Сохранить версии, идентификаторы, точку, время и результат чтения. На управляемом источнике дополнительно сверить кадр, повтор события и причину известного пропуска |
| Архитектура, код и эксплуатация | Приложить ревью реальных вызовов, отчёт `task check:report`, матрицу прав, протокол медленного клиента и прерываний. Восстановить конфигурацию, права и каталог из описанных исходных материалов. Проверить старую запись, новую запись и отзыв права. Указать RPO/RTO отдельно по функциям |
| Интерфейс и первое использование | Приложить пары «макет и рабочий экран», результаты дизайн-ревью, наблюдения по обеим ролям и подтверждённые до испытания пределы времени. Сопоставить ответ участника с фактом на стенде. [Протокол UX](poc-ui-prototype.md#проверка-первого-использования) |
