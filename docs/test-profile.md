## Окружение

| Параметр | Профиль первого прогона |
| --- | --- |
| Узел | Один Linux x86-64, Intel Core i7-13700H, 20 логических CPU, 15 ГиБ доступной системе RAM. Дистрибутив в контейнерах - Debian 13 |
| Хранилище | ext4 на NVMe на опорном узле. Постоянные тома PostgreSQL и архива разделены. Для воспроизводимой проверки заполнения выделен отдельный tmpfs объёмом 64 МиБ |
| Сеть | Изолированная сеть проекта Docker Compose. На хосте тестовая камера доступна через loopback. Для прогона с физической камерой фиксируются сегмент сети, RTT и пропускная способность |
| Браузеры | Google Chrome и Firefox на Linux. Точные версии и совместимость H.264 фиксируются в протоколе браузерной проверки |
| Синтетическая камера | RTSP/TCP, H.264, основной профиль 1280×720, 25 кадров/с, целевой битрейт 2 Мбит/с. Дополнительный 640×360, 15 кадров/с, целевой битрейт 0,5 Мбит/с. Ключевой кадр запрашивается не реже одного раза в секунду, в кадре видна отметка времени конвейера |
| Веб-камера рабочего узла | Chicony Integrated Camera через V4L2 и тестовый RTSP-сервер. Два H.264-профиля кодируются из одного захвата. [Измерения и матрица совместимости](rtsp-compatibility.md) |
| Физическая IP-камера | Для проверки собственной реализации RTSP устройства требуется камера с двумя H.264-профилями. Модель, прошивка, разрешения, фактические битрейты и GOP вносятся при подключении. Учётные данные хранятся вне паспорта |

Синтетическая камера используется для воспроизводимой проверки двух потоков. Физический прогон подтверждает совместимость конкретного устройства. Профиль компактного аппаратного узла проверяется отдельно по фактическому потреблению ресурсов.

## Автономная установка и доступ

`task install:check SUITE=bookworm` и `task install:check SUITE=trixie` собирают нативный комплект с испытательным ключом и устанавливают его в чистую Debian 12 или 13 amd64 в QEMU/KVM. После первой настройки проверяются версии реально запущенного сервера PostgreSQL и клиента. `task media:check:bookworm` собирает нативные службы на Debian 12 и прогоняет сценарии записи RTSP, выдачи WebRTC в браузерах и обработки тревог на системном GStreamer. Установочный носитель доступен только для чтения, архив размещён на отдельном ext4-диске. QEMU разрешает входящее HTTPS-соединение с браузерного стенда. Внешняя сеть отключена. После установки виртуальная машина перезагружается. Проверка сравнивает идентификаторы загрузок, состояние systemd, версии установленных пакетов и SHA-256 веб-ресурсов с подписанным составом поставки.

| Действие | Ожидаемый результат |
| --- | --- |
| Изменить Debian-пакет на копии носителя | Проверка подписи и хешей прекращает установку до изменения базы dpkg |
| Ввести пароль администратора до привязки | Требуется одноразовый код из локальной консоли. Сессия отсутствует |
| Зарегистрировать ключ и подтвердить запрос в Chrome | Администратор получает доступ к реестру камер. Повторный вход требует пароль и подтверждение ключом |
| Передать неверную подпись, затем верную с тем же запросом | Оба запроса отклонены |
| Выдать и отозвать доступ оператора | Точка появляется и исчезает в одной открытой сессии. Управление камерами остаётся закрытым |
| Назначить оператору роль администратора | Предыдущая сессия отозвана. Для входа требуется привязка ключа |

Каталог отчёта выводится командой. В `installation.json` сохранены матрица, версии браузера и испытательного окружения, в `installed.json` - фактический состав узла. В `bundle/sbom.json` перечислены пакеты, плагины, библиотеки C++ и компоненты веб-клиента. В `build-tools.json` указаны версии инструментов сборки и завершённого испытания, а также SHA-256 подписанного перечня файлов. Для сборки с ключом поставщика используйте `task release:package SIGNING_HOME=/absolute/gnupg SIGNER=<fingerprint> OUTPUT=/absolute/output` с пустым выходным каталогом. [Установка и первичная привязка](install.md) · [Восстановление конфигурации и архива](recovery.md)

## Пакетный ввод и откат каналов

Команда `task camera:commissioning` выполняет два сценария в отдельных базах. В первом браузер открывает записи двух последовательных привязок одной точки. Во втором ONVIF-эмулятор объявляет один блок с четырьмя видеовходами, по два профиля H.264 у каждого входа. Chrome сохраняет шаблон и применяет его к четырём каналам. Проверка сверяет подтверждения рекордера и наличие архивного блока у каждой точки. Протокол `batch.json` содержит исходные и фактические версии, конфликт, частичный отказ и команды изображения. Снимки показывают предварительное сравнение и результаты.

| Модель и прошивка | Возможности и проверка |
| --- | --- |
| Four-input encoder, 2.1, программный эмулятор | Общий endpoint, четыре источника ONVIF, отдельные точки и записи по RTSPS. Три источника поддерживают яркость от 0 до 100. Четвёртый допускает смену профилей без настройки яркости |
| Fixed camera, 3.0, программный эмулятор | Отдельная камера без Imaging обрывает HTTPS-соединение между сравнением и применением. Повтор после восстановления создаёт одну привязку. Откат отключает камеру и сохраняет записанные блоки точки |
| bacuri.vms ONVIF emulator и Camera B, 1.1, программный эмулятор | Замена устройства сохраняет точку. Новая и прежняя записи открываются с привязками 2 и 1 соответственно |

При подготовке обновления сервер отклоняет пару профилей от разных каналов и устаревшую версию шаблона. После потери ответа на запись яркости повтор сверяет фактическое значение. Во второй сессии меняется имя одного канала, другой вход отключается перед применением. Проверка сверяет конфликт версии, адреса, число команд записи яркости, повтор после восстановления связи и откат. Аппаратная серия для моделей и прошивок полного выпуска проводится по [профилю приёмки](release-profile.md#эталонные-устройства).

Дополнительная проверка воспроизводит конфигурацию без идентификатора физического входа. По сохранённому профилю ONVIF сервер находит прежнюю точку, меняет местами основной и дополнительный потоки и добавляет соседний вход отдельной точкой. После восстановления резервной копии проверка сравнивает все поля протоколов партии и всех версий шаблонов.

В прогоне Core 0.1.8 прошли 37 тестов в каждом из четырёх профилей C++ и 136 браузерных тестов. Покрытие строк составило 76,45% для C++, 84,40% для JavaScript и 84,37% для TypeScript рабочего места. Обновление со схемы 21 на 22 и откат на 21 сохранили все 32 проверенных архивных блока.

В дополнительном прогоне с инструментированным RTSP-эмулятором LeakSanitizer обнаружил утечку 320 байт в Fontconfig при выходе эмулятора. Пакетный сценарий с Core и рекордером под ASan/UBSan и отдельным RTSP-эмулятором из сборки GCC Debug прошёл.

## Права и корпоративный вход

`task access:check` поднимает отдельный проект Docker Compose с PostgreSQL, синтетической RTSP-камерой, Chrome и Keycloak 26.8.1 по HTTPS. Два независимых сеанса одного оператора получают одинаковые полномочия после локального и корпоративного входа. Для проверки используются две точки, группа, интервалы записи, раздельные разрешения, маска приватности и фактическая выдача WebRTC и HTTPS. [Сценарий](../tests/access/scenario.py) · [Профиль realm](../tests/access/realm.py)

| Изменение на площадке | Локальный вход | Корпоративный вход | Предел |
| --- | --- | --- | --- |
| Удаление точки из группы, время до последнего SRTP-пакета | 0,218 с | 0,132 с | 5 с |

Перед блокировкой учётной записи Keycloak стенд дождался продления действующей сессии. После блокировки Core отказал в доступе через 3,40 с, последний SRTP-пакет получен через 3,70 с при пределе 60 с. Изолированно проверены совпадающая почта у разных субъектов, обязательный второй фактор администратора (пароль и TOTP, acr 2), локальный WebAuthn при остановленном провайдере, истечение корпоративной сессии, повторный вход после запуска провайдера и исполнитель в аудите. При повторном восстановлении конфигурации сохранились привязка внешнего субъекта и записи аудита, появившиеся после создания копии. Это измерения одиночной площадки. [Управление доступом](ui.md#управление-доступом)

На подписанных комплектах 0.1.6 и 0.1.7 проверены обновление со схемы 20 на схему 21 после прерывания миграции, откат до схемы 20, замена утраченного ключа WebAuthn и восстановление на независимом системном диске Debian. Сохранились все 39 проверенных блоков. Контрольный кадр архива воспроизвёлся через 7,37 с после остановки исходного узла, кадр новой записи - через 9,38 с. Пределы ниже задают условия квалификации комплекта в 12.1. Основания - круглосуточная запись на одной площадке, месячный горизонт расследования и измерения ядра на опорном узле. Целевой узел использует конфигурацию CPU и памяти из паспорта, Debian 13 x86-64, сеть 1 Гбит/с и отдельный локальный том ext4 для архива. Битрейты, длительность серий, число проб и пределы заданы в [проверяемом профиле](../tests/cameras/qualification.json). | Показатель | Предел и основание |
| --- | --- |
| Запись и просмотр | 8 основных потоков H.264 по 2 или 4 Мбит/с, 8 дополнительных по 0,5 Мбит/с. GOP до 1 с. Один зритель эфира и один зритель архива одновременно обслуживают наблюдение и расследование. В архив пишется основной поток |

При 20% запаса для колебаний битрейта и свободного места на видео, контейнер и индекс приходится 11,2 ТБ. 1 ТБ = 10¹² байт. Фактические накладные расходы измеряются на целевом томе |
| Ожидание оператора | p95 до 2 с для первого кадра эфира, доставки тревоги и первой страницы поиска отдельно на холодном и прогретом каталоге. Для первого кадра архива p95 до 3 с, включая поиск точки декодирования. Ошибка позиции до 1 с соответствует максимальному GOP |
| Изоляция | Ноль дополнительных пропусков по сравнению с контрольной записью, при отзыве права остановка выдачи до 5 с. На штатные запросы ожидается ноль ошибок. Преднамеренные отказы учитываются отдельно |
| Конфигурация и права | RPO до 5 минут при наличии сохранной локальной копии с таким интервалом. RTO до 5 минут от потери БД до входа и проверки разрешённой и чужой точек. Бюджет включает развёртывание копии |
| Исторический архив | RPO 0 для исправных завершённых блоков на сохранном томе. RTO до 15 минут до декодирования прежнего кадра, включая сверку каталога. Повреждение блока и полная утрата носителя учитываются отдельно по объёму фактической потери |
| Новая запись | RPO до 30 с по интервалу между блоками и RTO до 60 с от начала контролируемого отказа до первого декодированного нового блока. Предел рассчитан на кратковременные отказы протокола и исправный источник после восстановления. В регрессии малый том дал перерыв до 4,324 с и время до кадра до 5,276 с |

## Результаты проверки инфраструктуры

Ниже зафиксированы выполненные проверки существующего ядра и среды сборки. Выпускной отчёт 12.1 и протокол финальной серии 13.1 формируются на релиз-кандидате.

В полном прогоне с Gitleaks и clang-format покрыты 2827 из 3171 строк продуктового C++ (89,15%) и 577 из 627 строк рабочего JavaScript (92,02%). Gitleaks завершил три проверки без находок. CTest прошёл на GCC, Clang, под ASan/UBSan и TSan, а также в сборке покрытия. Повторный прогон измеряет обе доли заново. [Критерии приёмки](quality.md#автоматические-проверки-кода)

Для шкалы архива и формы подключения камеры `task ui-kit:check` прошёл 44 браузерные проверки в Chromium и Firefox в светлой и тёмной темах. На форму приходятся 24 проверки. Подтверждены фокус первого ошибочного поля, состояние каждого потока, сохранение ввода и однократная отправка при повторе, обработка запоздалого ответа после изменения адреса. Для шкалы проверены границы пропуска, выбор времени и обновление каталога с сохранением позиции. Оба компонента проверены при ширине 320 CSS-пикселей и размере текста 200%. По исходным TS и TSX покрыты 510 из 538 строк (94,80%). Контрольный незагруженный модуль учтён с нулевым покрытием при проверке механизма подсчёта. Для полных экранов действует отдельный сквозной протокол. [Шкала архива](ui.md#шкала-архива-в-ui-kit) · [Форма подключения камеры](ui.md#форма-подключения-камеры-в-ui-kit)

С Conan 2.34.0 два независимых разрешения профилей GCC и Clang дали одинаковый lockfile. После перехода с прежних каталогов CMake во всех четырёх тестовых пресетах прошёл 31 тест, включая прогоны с ASan/UBSan и TSan. Полный прогон `task check:report` завершился с кодом 0. На Release отдельная проверка тревоги в Chrome и Firefox открыла эталонный кадр 16. Команда `task build:repro` повторно собрала проект без сети в чистом каталоге того же образа. Все четыре исполняемых файла совпали побайтно. [Границы проверки воспроизводимости](adr/010-build-dependencies.md)

С чистой копии источников `task check:report` завершился с кодом 0. Прошли сборки GCC 14.2 и Clang 19.1, стартовый CTest в обычных и инструментированных сборках с ASan/UBSan и TSan, а также статический анализ. PostgreSQL 17.11 ответил на запрос по сети Compose. Оба H.264-профиля синтетической камеры декодировались в ожидаемом разрешении.

`task stand:check-storage` подтвердил сохранность тестовых данных PostgreSQL и архива после остановки и повторного запуска Compose. Заполнение tmpfs вернуло `ENOSPC` на границе 64 МиБ. При повторном запуске контейнера временный том был пуст.

## Протокол измерений

Базовый функциональный профиль включает управляемый источник и физическую IP-камеру. Для выпуска 12.1 обязательны все физические конфигурации, зафиксированные в 6.1. Для каждого теста указываются идентификатор комплекта, ожидаемый и фактический результат и код завершения. Ошибка, пропуск обязательной строки или отсутствие устройства блокируют переход к 13.1.

В обязательной автоматической серии 12.1 контрольную запись и смешанную нагрузку сравнивают на одном релиз-кандидате. Стенд использует восемь двухпоточных источников. При номинальном битрейте основного потока 2 Мбит/с выполняют контрольный и смешанный прогоны, затем повторяют оба при 4 Мбит/с. Каждый прогон включает 5 минут прогрева и 30 минут измерений. Во время смешанного прогона одновременно работают запись, один клиент эфира, один клиент архива, поиск и тестовые наблюдения с частотой 1 событие/с. Для первого кадра, окна поиска и задержки тревоги собирается не менее 200 проб каждого вида на каждый битрейт в смешанном прогоне. Холодный поиск прогоняется отдельно с описанием начального состояния кэша.

Основные условия приёмки приведены в матрице. Предел на этом стенде - до 2 с по p95 для первого кадра эфира, отображения тревоги и первой страницы поиска. В каждом прогоне фиксируются p50, p95, p99, число проб, доля ошибок, потребление ресурсов, глубина очередей, разрывы и объём записи на диске. Стоимость хранения рассчитывается из фактического объёма за единицу времени и ёмкости выбранного носителя. Для каждого сценария отказа фиксируются начало отказа, первый обнаруженный пропуск, момент возвращения проверенной операции и объём невосстановимых данных.

| Поле результата | Что записать |
| --- | --- |
| Воспроизводимость | Ревизия проекта, версии образов и пакетов, оборудование, тип файловой системы, конфигурация сети и источник |
| Нагрузка | Число потоков и клиентов, измеренный битрейт, GOP, частота событий, длительность, объём выборки и условия запуска |
| Наблюдение | Ожидаемый результат, фактический результат, метрики и ссылки на артефакты |
| Сбои | Причина, диапазон пропуска, проверенные копии, потеря данных, длительность восстановления записи, архива и конфигурации |

В `postgres-upgrade/result.json` сохраняются образы исходной и обновлённой PostgreSQL, перечень перестроенных индексов, ключи найденных архивных блоков и ожидающей тревоги. Они должны совпасть на исходной базе, на обновлённой копии и после запуска сервера из новой полной резервной копии.

`task regression:check` проверяет функциональный профиль с синтетической RTSP-камерой. Для повтора сохраняются исходники с эталонами, ревизия Git, SHA-256 состава и признак локальных изменений. Новый каталог сборки, отдельная сеть и новые тома исключают использование данных предыдущего прогона. Результаты независимой Release-сборки и сохранности томов учитываются отдельно.

В `core/check.log` находятся результаты CTest, контрактов, ввода по RTSP, записи, эфира, тревог и поиска. В `core/workspace` сохраняются снимки Chrome и Firefox и измерения штатного клиента, в `core/recovery` - прерывания, потери и восстановление. В `core/dependencies` сохраняются фактические компоненты, роли, источники и ревизии сведений, применимые уведомления, исправленные версии и исключения. Критическое уведомление блокирует результат до обновления или успешной автоматической проверки адресной меры защиты. Пропуск сведений о сопровождении и истёкшее исключение также блокируют результат.

При автономном повторе проверяются хеши снимка и применяется момент исходной оценки. Для регрессии ядра срок актуальности снимка ограничен 30 сутками. Перед 12.1 сведения обновляются для конкретного кандидата. Для npm источником сведений служат карточка точной версии в реестре и канал исправлений проекта, для веток Node.js и PostgreSQL - сведения поставщиков. Системные пакеты проверяются по данным дистрибутива. Для компонентов внутри сторонних образов сохраняются также образ и отчёт сканера. [Политика сопровождения](adr/015-technology-lifecycle.md)

Протокол собственной RTSP-реализации физической камеры заполняется на выделенном стенде шага 2.2. Испытание смешанной нагрузки проводится на релиз-кандидате в 12.1. [Границы аппаратного подтверждения](rtsp-compatibility.md)

### Обработка тревог и аудит

`task alerts:check` проверяет одновременное принятие одной тревоги двумя операторами, обрыв HTTPS до получения ответа и повтор с прежним ключом. Сверяются ответственный, версии и число записей истории. Проверяются отказ на чужой точке, запись результата сервисом, запрет другого действия, истечение срока, отзыв поручения и потеря права у инициатора. Поиск проверяется по тексту, идентификатору и курсору следующей страницы.

`task workspace:check` проводит дежурного от тестового события движения к пронумерованному кадру архива. Дежурный принимает тревогу, записывает результат, закрывает её, находит результат в журнале и возвращается к той же позиции архива. Прогон выполняется в Chrome и Firefox. Снимки журнала сохраняются вместе с отчётом рабочего места.

В прогоне `task camera:commissioning` ONVIF-эмулятор отправляет уведомление через PullPoint. Браузер открывает тревогу из WSS, а независимый декодер сверяет показанный кадр с блоком записи RTSP. Затем оператор закрывает эту тревогу и находит свой результат в журнале. Протокол содержит идентификаторы наблюдения, тревоги, блока и трёх записей истории.

### Восстановление установленного узла

`task maintenance:check PREVIOUS=/путь/к/отчёту` принимает сохранённый подписанный комплект и его испытательный ключ. В качестве исходной версии для 0.1.6 поддерживаются 0.1.0 (схема 14), 0.1.1 (схема 15), 0.1.2 (схема 16), 0.1.3 (схема 17), 0.1.4 (схема 18) и 0.1.5 (схема 19). Две виртуальные машины KVM используют независимые системные диски Debian 13 amd64, общий по очереди архивный том ext4 и отдельный носитель копий. На запасной машине предварительно установлен пакет, площадка отсутствует, системный UID рекордера отличается. Источник видео - синтетическая RTSP-камера. [Порядок обслуживания](maintenance.md)

Сценарий записывает видео, создаёт тревогу и выдаёт оператору доступ к точке. Он прерывает транзакцию миграции, сверяет версию схемы и контрольную сумму копии, повторяет обновление и отдельно выполняет откат с подписанным комплектом предыдущей версии. Затем после новой копии отзывает административный ключ. После внезапного выключения исходной машины проверяет доступ по HTTPS, права, историю тревоги, отказ по прежним ключам и сессиям. Для старого кадра сверяется SHA-256 пикселей, для нового браузер декодирует кадр и проверяет наличие тестового изображения.

В `operations.json` сохраняются идентификаторы комплектов, число сохранных блоков, события аудита и сравнение с пределами профиля. Время отсчитывается с отключения работающего узла и включает загрузку подготовленного запасного. Возраст конфигурации считается от начала последней успешной копии, разрыв записи - между концом последнего завершённого блока и началом первого нового. В `diagnostics.json` сохраняются метрики, события и связанные OTLP spans для отключения камеры, остановки выдачи, накопления очереди каталога и заполнения тома.

### Срок хранения и контроль ёмкости

`task retention:check` использует изолированную PostgreSQL, управляемые часы каталога, синтетическую RTSP-камеру и отдельный том tmpfs объёмом 64 МиБ. За микросекунду до границы блок доступен в каталоге. На границе ранее выданная HTTPS-ссылка на этот блок закрывается, в том числе при остановленном рекордере. Следующий блок того же медиапотока читается по своей ссылке. После запуска рекордера проверяются файлы, строки PostgreSQL и локальный журнал. Увеличение срока и восстановление каталога проверяются с ранее истёкшим блоком.

Внешний файл на тестовом томе доводит свободный остаток до уровня предупреждения, затем до резерва. Тест сверяет состояние диагностики, появление пропуска, содержимое защищённого фрагмента по HTTPS и его контрольную сумму на диске. После освобождения места проверяется фиксация нового блока. Отчёт `capacity.json` в каталоге прогона содержит измерения ёмкости, прогноза и результат сверки.

`task test` прерывает процесс после фиксации границы очистки, после переименования каталога блока и после удаления файлов. Каждый вариант открывает том заново и проверяет, что остаётся ровно один действующий блок, а повтор очистки сохраняет его.
